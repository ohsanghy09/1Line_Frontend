# FastAPI·OpenAI 기반 AI 개발 서버 작업 계획

2026-11-06 최신 상태: 홈뿐 아니라 Growth Journey의 실제 DB 문맥·전용 프롬프트(journey-v2)·분류/아이콘 생성·근거 검증 API도 구현했다. 백엔드가 성장 결과 저장·조회를 담당한다. 다음은 빈 DB에서 사용자 입력·화면 검증이며 Journey 자동 모델 호출은 제안 상태다. 아래 ‘별도 Journey 실제 분석’·미구현 설명보다 [최신 인수인계](../../docs/integration/현재_작업_인수인계.md)와 [Journey API](../../docs/journey/성장_분석_API.md)의 최신 절을 우선한다.

최신 구현: [홈 실제 AI 연동](홈_실제_AI_연동.md). 실제 홈 입력 3종과 단일/다중 파일을 OpenAI로 분석하고 활동 생성·초안 보관·백엔드 확정 저장·조회까지 연결했다. 이전의 ‘활동 생성·분석 보관·프론트 미연동’은 아래 단계별 과거 상태다. 다음은 브라우저 조작·추가 파일 형식 품질 검증과 별도 Growth Journey 실제 분석이다.

작성일: 2026-11-06. 최신 상태: 기본 서버·실제 OpenAI 텍스트 분석·기존 DB 직접 조회 구현. `gpt-5.6-sol` 합성 텍스트 호출 1회 통과. [텍스트 분석 API](텍스트_분석_API.md)와 [실행 안내](../README.md)를 먼저 확인한다. 신규 활동 생성·분석 보관·프론트 연동은 아직 미구현이다. 아래는 단계별 계획이며 완료한 범위는 각 구현 기록을 따른다.

최신 진행: [DB 직접 연결](DB_직접_연결.md)을 구현했다. 기존 백엔드와 같은 SQLite를 사용하며 context를 생략한 텍스트 요청에는 실제 활동·확정 기록을 준비한다. 기본 DB 연결·조회·파일 원본 접근을 검증했고 테스트 21개 통과. 신규 활동 생성·분석 저장·프론트 전환은 아직 남아 있다. 아래의 DB 연결 제안·미구현 설명은 계획 작성 당시 내용과 구분한다.

## 1. 목적과 현재 상태

기존 `api-server/`를 백엔드 개발 서버로 유지하고, 같은 최상위 경로의 `ai-api-server/`에 Python·FastAPI 기반 AI 개발 서버를 구현한다. 사용자가 보유한 OpenAI API 키를 서버에서 사용하여 실제 분석을 수행한다.

현재 Python 3.15.2에서 기본 서버·텍스트 분석 API를 구현했고 사용자가 설정한 키와 `gpt-5.6-sol`로 합성 텍스트 분석을 확인했다. 문맥은 기본적으로 DB에서 조회하며 명시적 요청 문맥도 개발 검증용으로 지원한다. 신규 활동 생성·분석 저장·프론트 전환은 미완료다. 키 설정 여부·연결 성공·분석 품질·전체 기록 저장 완료를 구분한다.

기존 백엔드는 Express·SQLite로 입력·파일 보관, 목 분석, 기록 CRUD와 Timeline 처리를 함께 수행한다. 이번 서버를 구현하면서 분석 책임을 분리한다. 단순히 기존 목 함수를 새 서버로 옮기는 것을 실제 AI 분석 완료로 기록하지 않는다.

## 2. 확정한 기술 방향과 역할

| 구분 | 담당 |
| --- | --- |
| 프론트 | 사용자 입력·첨부 전송, 분석 결과 표시, 활동·자료 유형 수정, 백엔드 확정 저장 요청 |
| FastAPI AI 서버 | 분석 문맥·파일 조회/준비, OpenAI 호출, 결과 검증, 기존 활동 연결·신규 활동 DB 생성, 분석 결과 보관·반환 |
| OpenAI 모델 | 제공된 입력과 문맥에 대한 활동 매칭·분류·요약·변화·근거 분석 |
| 기존 백엔드 | 기록·자료 확정 저장, 분류 수정, 아카이브·자료·Timeline 조회와 데이터 검증·트랜잭션 처리 |

OpenAI 모델이 DB에 직접 접속하는 구조가 아니다. AI 서버 코드가 필요한 문맥을 조회해 모델에 전달하고 검증된 판단을 DB에 반영한다. 기존 활동 ID는 실제 DB 값으로 확인하고 신규 활동 ID는 서버에서 발급한다. 모델이 생성한 SQL을 실행하지 않는다.

신규 활동 생성은 AI 서버 책임이고, 사용자가 기록 버튼으로 확정하는 기록 저장은 백엔드 책임이다. 활동 생성 직후 기록을 저장하지 않은 상태의 노출·보존 정책은 구현 전 정한다.

## 3. 구현 순서

### 1단계 — FastAPI 서버 구성

- Python 버전·가상환경·의존성 관리 방식을 정하고 실행 가능한 최소 서버를 만든다.
- FastAPI, 실행 서버, OpenAI 공식 Python SDK, 요청·응답 검증에 필요한 의존성을 구성하고 버전을 기록한다.
- 상태 확인 API와 FastAPI 자동 API 문서를 구성한다. 상태 응답에서 서버 실행 가능 여부·설정 여부·실제 모델 호출 성공을 구분한다.
- 서버 실행 방법, 포트, 프론트 접근 경로·CORS, 환경변수 예시를 README에 작성한다. 포트는 기존 서버·문서 서버와 충돌하지 않도록 확인한다.
- 키는 서버의 `OPENAI_API_KEY`, 모델은 별도 설정으로 관리한다. 실제 키가 없는 예시 파일만 제공하고 `.env`·가상환경·실행 산출물은 저장소에서 제외한다.

완료 기준: 독립 프로세스로 실행하고 상태 확인·API 문서 접근이 가능하다. 모델과 키 설정이 없을 때의 안내가 명확하다.

### 2단계 — 실제 텍스트 분석

- OpenAI Responses API와 Structured Outputs를 사용한다. 사용자가 선택한 `gpt-5.6-sol` 실제 호출을 확인했으며 현재 개발 계약은 [텍스트 분석 API](텍스트_분석_API.md)를 따른다.
- Pydantic으로 입력과 분석 결과를 정의한다. 활동 판단·자료 유형·요약·변화·근거를 구조화한다.
- 기존 활동·기록 문맥을 준비해 실제 사용자 텍스트와 함께 모델에 전달한다. 과거 자료가 없으면 Before나 변화 근거를 임의로 만들지 않도록 한다.
- 정상 응답 외에 인증 실패·호출 제한·시간 초과·거절·불완전 출력·응답 검증 실패를 처리한다. 실패 시 목 성공 응답으로 대체하지 않는다.
- 형식 검증과 분석 내용의 정확도를 구분한다. Structured Outputs를 사용해도 실제 활동 ID·근거 일치 여부는 서비스 코드에서 검증한다.

완료 기준: 실제 OpenAI 호출로 텍스트 분석 결과를 받고 검증된 JSON을 반환한다. 사용한 모델·검증 입력·결과를 비밀값 없이 기록한다.

### 3단계 — 활동 DB 연결과 분석 보관

- 두 서버가 참조할 DB·테이블·ID와 마이그레이션 주체를 정한다. 공통 개발 SQLite 사용은 기존 제안이며 확정·구현된 것으로 취급하지 않는다.
- Python과 Node가 같은 데이터를 처리할 때 DB 스키마·트랜잭션·연결 설정·날짜/JSON 직렬화가 일치하도록 한다. 기존 사용자 DB를 초기화하지 않는다.
- 기존 활동은 DB ID를 확인해 연결하고 신규 활동은 AI 서버 코드에서 생성한 뒤 ID를 반환한다.
- 현재 `match: new`는 ID를 허용하지 않는 프론트·서버 검증을 생성 완료 상태에 맞춰 조정한다. 신규 판단과 DB 생성 완료를 구분한다.
- 분석 ID·원본 입력·분석 결과를 보관하여 백엔드가 기록 확정 시 조회할 수 있게 한다.
- 재시도·동시 요청 시 활동·분석이 중복 생성되지 않도록 하고, OpenAI 호출 중에는 긴 DB 쓰기 트랜잭션을 유지하지 않도록 설계한다.

완료 기준: 기존 활동 연결·신규 활동 생성·분석 보관이 실제 DB에서 동작하고 백엔드가 동일 ID를 조회한다.

### 4단계 — 백엔드·프론트 연동

- 기존 명세를 최신 역할 분담에 맞게 적용한다. AI 서버가 만든 분석·활동·원본 참조를 백엔드 기록 저장에 연결한다.
- 프론트 분석 요청·상태 확인·진행 조회·작업 복원은 AI 서버로, 기록 저장·수정·아카이브 조회는 백엔드로 분리한다.
- 기존 공통 요청 함수의 주소를 변경하여 백엔드 요청까지 AI 서버로 보내는 일이 없도록 의존 관계를 정리한다.
- 카드 수정은 기존 활동·자료 유형만 변경한다. 백엔드의 넓은 기존 수정 계약은 사용처 확인 후 정리한다.
- 기록 저장 성공 이후에만 완료 표시·관련 목록 갱신을 수행한다. 활동 미확정·삭제·저장 실패·중복 요청을 처리한다.

완료 기준: 텍스트 입력 → 실제 분석 → 활동 생성/연결 → 분류 수정 → 확정 저장 → 아카이브·Timeline 조회가 이어진다.

### 5단계 — 파일·링크 확장

- 단일 파일 → 다중 파일 → 링크 순서로 확장한다.
- 원본 업로드·보관 주체와 분석할 내용의 전달/추출 방식을 정한다. DB에서 파일을 읽는 것만으로 OpenAI가 본문을 읽을 수 있는 것은 아니다.
- 실제 파일명·개수·파일 ID를 보존하고 백엔드 저장 이후 원본 다운로드가 가능하게 한다.
- 지원 파일 유형·본문 추출 범위와 링크 수집 방식·실패 처리를 문서화한다. 파일명이나 URL만으로 본문까지 분석했다고 표시하지 않는다.
- 비동기 처리가 필요한 입력은 작업 ID·진행·완료·실패·재진입 계약을 적용한다.

완료 기준: 입력 종류별 분석·원본 연결·저장·조회가 일치하며 지원하지 않는 입력은 명확히 안내한다.

### 6단계 — 검증과 담당자 전달 문서

- 전용 테스트 DB로 신규/기존 활동, 변화 있음/없음, 저장 전/후 수정, 원본 다운로드, 실패·재시도·중복·새로고침 복원을 확인한다.
- 모델 호출 없는 자동 검사와 실제 OpenAI 통합 검증을 구분한다. 연결 성공뿐 아니라 활동 판단·요약·근거의 품질도 확인한다.
- 기존 아카이브·최근 목록·Timeline·세션 보관에 대한 회귀 검사를 수행한다. 자동 검사와 실제 브라우저 조작 결과는 따로 기록한다.
- 검증된 구현을 기준으로 현재 구현 현황·기능 흐름·백엔드/AI API 명세·ERD·데이터 사전·실행 방법을 갱신한다.
- FastAPI가 생성한 OpenAPI와 기존 프론트 `/swagger/` 정적 명세의 연결·생성 방식을 정리하여 명세가 서로 달라지지 않게 한다.

완료 기준: 다른 파트의 agent가 문서로 서버를 실행하고 기능 흐름·DB 접근 책임·요청/응답·검증 결과·남은 작업을 파악할 수 있다.

Growth Journey의 실제 분석 생성·저장과 외부 배포는 핵심 기록 흐름 이후 별도 단계로 진행한다. 현재 모델은 `gpt-5.6-sol`, 텍스트 경로는 `/api/analyze/text`다. DB 공유 방식·전체 입력 연동 계약·파일 처리 범위는 아직 미확정이다.
