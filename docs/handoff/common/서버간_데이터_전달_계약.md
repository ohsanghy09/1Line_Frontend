# 서버 간 데이터 전달 계약

기준일: 2026-11-06. [서버 역할](서버별_역할과_요청_흐름.md) · [공통 데이터](공통_데이터_계약.md) · [AI API](../ai/API_정의서.md)

## 적용 상태와 책임

공개 프론트 API는 현재 화면 호환 규격이다. **이 문서의 내부 전달 규격은 공유 로컬 DB 없이 새로 구현하기 위한 분리 구현용 설계**다. 기존 개발 서버가 이 내부 전송을 이미 지원한다는 뜻은 아니다. 개발 코드는 제공하지 않는다. 양 파트가 별도 협의 없이 같은 인터페이스를 구현할 수 있도록 아래 기본 HTTP 프로파일을 사용한다. 다른 내부 전송으로 바꾸려면 양 파트가 함께 변경해야 하며 한쪽만 임의 경로로 구현하지 않는다. 공개 프론트 요청은 바꾸지 않는다.

## 기본 내부 HTTP 프로파일

Base는 각 서버가 제공하는 /api까지 포함한 내부 HTTPS 주소다. 아래 경로는 Base 뒤에 붙인다. 내부 요청은 본문이 있으면 `Content-Type: application/json`, 인증은 `Authorization: Bearer <INTERNAL_SERVICE_TOKEN>`을 사용한다. 토큰 실제 값은 배포 시 두 서버에 안전하게 설정하고 브라우저에는 전달하지 않는다. 토큰 누락/오류는 401, 인가 범위 위반은 403이다. 사용자 범위는 공개 인증이 결정되면 서버가 검증한 동일 범위를 내부에서도 전달·검증하며 임의 conversationId를 사용자 인증으로 사용하지 않는다.

| 호출 | 메서드·경로 | 요청 | 성공 응답 |
| --- | --- | --- | --- |
| AI → 백엔드 | GET /internal/home-context?conversationId=문자열 | query conversationId 필수, 1~200자·URL 인코딩 | 200, 1절의 문맥 객체를 wrapper 없이 반환 |
| AI → 백엔드 | PUT /internal/chat-jobs/:jobId | 2절 게시 객체 전체 + expectedRevision:0 이상 정수 | 최초 201/재조회·갱신 200, {job:JobSnapshot} |
| AI → 백엔드 | GET /internal/chat-jobs/:jobId | 본문 없음 | 200 {job:JobSnapshot}, 없음 404 |
| 백엔드 → AI | POST /analyze/activities/:activityId | 4절의 활동 스냅샷 객체 | 200, AI API 정의서의 근거 포함 metadata 응답 |
| 백엔드 → AI | POST /analyze/journey | 5절의 성장 문맥 객체 | 200, AI API 정의서의 성장 응답 |
| 백엔드 → AI | POST /analyze/records/:recordId/exclude-file | 6절의 남은 원본 객체 | 200 {reply,recordReply,fileIds} |

JobSnapshot은 2절 게시 필드에서 expectedRevision을 제외하고 revision(1 이상의 정수)을 추가한 객체다. revision은 백엔드가 생성하며 reply가 수정/퇴역 general로 바뀔 때도 증가한다. AI는 공개 작업 GET 결과를 만들 때 정본 스냅샷을 조회하거나 같은 revision임을 확인한 캐시만 사용한다. 내부 응답의 원본 bytes는 공개 JobResponse로 복사하지 않는다.

PUT의 최초 게시 expectedRevision은 0이다. 같은 requestId·fingerprint의 접수 재전송은 새 작업을 만들지 않고 기존 job을 200으로 돌려준다. 다른 입력은 409다. 이후 갱신은 마지막으로 받은 revision을 expectedRevision으로 전달하며 현재 revision과 다르면 409 후 GET으로 현재값을 확인한다. 이미 반영한 동일 갱신의 재전송은 현재 스냅샷을 200으로 반환할 수 있지만 이전 reply로 되돌리지 않는다. 새 갱신 성공 시 revision을 증가시키고 영속 보관 후 응답한다.

본문/필드 검증 실패는 400, 없는 참조는 404, 진행·버전 충돌은 409, 내부 인증 실패는 401/403이다. 오류는 {error:string,code:string}이며 입력 원문·키는 노출하지 않는다. 내부 연결은 서버 전용으로 보호하고 공개 프론트 라우팅에 노출하지 않는다. 이 표는 새 분리 구현의 기준이며 기존 개발 서버의 지원 여부를 나타내지 않는다.

| 데이터·작업 | 최종 책임 | 조건 |
| --- | --- | --- |
| 활동·확정 기록·Timeline·Journey | 백엔드 | 생성·수정·삭제·권한·원자성 관리 |
| 홈 분석 작업·진행 | AI 서비스 | 접수·모델·진행·실패·재조회 관리. 영속 저장 위치는 선택 가능 |
| 분석 초안·원본 | 백엔드에서 조회 가능한 영속 저장 | AI 접수·완료 게시와 같은 analysisId 사용. 저장·직접 수정 때 실제 데이터 확인 |
| 기존 활동/기록 문맥 | 백엔드 | 사용자 범위·조회 한도·스냅샷 일관성 보장 |
| 활동/성장 분석 | AI | 받은 문맥만 분석·검증, 결과 반환. 확정 DB 수정하지 않음 |
| 입력 변경 판정 | 백엔드 | 분석에 넘긴 스냅샷과 현재 상태를 대조해 저장 여부 결정 |

## 1. 홈 문맥 조회 작업

AI가 분석 전에 백엔드에 conversationId(문자열)와 적용 중인 사용자 범위를 전달한다. 인증에서 추출한 사용자 범위를 임의 클라이언트 값으로 덮어쓰지 않는다. 현재 인증은 별도 연결 사항이며 이 문서가 기존 사용자 ID 필드를 추가하는 것은 아니다.

응답은 아래 필드를 모두 가진다.

| 필드 | 구조·제약 |
| --- | --- |
| context.activities | 최대 50개. 각 id,name 필수 비빈 string, category/summary/role/status/startDate/endDate는 키를 포함하고 string 또는 null. status는 진행 중/완료/null |
| context.records | 최대 50개. 각 id,activityId 필수, message/summary는 string 또는 null. activityId는 포함된 활동 ID여야 함 |
| selection | activitiesTotal/activitiesIncluded/recordsTotal/recordsIncluded는 0 이상 정수, truncated:boolean |
| activeActivityId | 실제 포함 활동 ID 또는 null |
| activeActivityPending | boolean. 직전 활동 제안이 미확정이면 true |
| recentMessages | 최대 12개 {role:user/assistant,content:string}. 최근 완료 요청 6개의 입력·응답, 각 content 최대 2000자 |

활동은 최근 변경순, 기록은 포함 활동 중 최초 저장 최신순으로 고른다. 같은 시각의 정렬은 각 서버가 안정적인 보조키로 고정한다. rowid 같은 특정 DB 내부 열을 요구하지 않는다. context의 UTF-8 JSON 문자열 문자 수가 100000자를 넘으면 오류로 처리하며 초과 부분을 몰래 잘라 전 기록을 비교한 것처럼 표시하지 않는다.

최근 확정 기록의 활동, 직접 수정된 활동, 기존 활동 제안으로 activeActivityId를 정한다. 직전 new/unresolved 제안이 저장되지 않았다면 다른 기존 활동을 현재 대상으로 선택하지 않는다. 문맥 조회는 모델 호출과 데이터 변경을 하지 않는다.

```json
{"context":{"activities":[],"records":[]},"selection":{"activitiesTotal":0,"activitiesIncluded":0,"recordsTotal":0,"recordsIncluded":0,"truncated":false},"activeActivityId":null,"activeActivityPending":false,"recentMessages":[]}
```

## 2. 홈 접수·진행·완료 게시 작업

AI는 requestId의 중복을 검사하고 analysisId·ai- 접두사 jobId·conversationId·fileId를 발급한다. 접수 시 다음 정보를 백엔드에서 확인 가능한 저장소에 영속 보관하고 확인을 받은 뒤 비동기 접수 성공을 응답한다. 이때 활동과 확정 records는 만들지 않는다.

| 필드 | 구조·제약 |
| --- | --- |
| jobId,analysisId,conversationId,requestId | 비빈 string, jobId는 ai- 접두사. 한 job↔한 analysis, requestId 유일 |
| requestFingerprint | 입력 중복 검증값. message/sourceUrl/conversationId와 실제 파일명·MIME·bytes를 반영. 임시 파일 ID만 달라졌다고 새 입력으로 취급하지 않음 |
| kind,status,phase | kind=chat/link. 저장 status=queued/running/completed/failed. phase=preparing/analyzing/persisting/completed |
| message | 입력 원문 string. 링크 요청은 URL. 최대 20000자 |
| sourceUrl | URL string 또는 null |
| reply | 접수 때 null, 완료 때 화면용 ChatReply 또는 activity-update 중간 reply. 실패 때 완료 reply로 위장하지 않음 |
| files | [{id,name,mimeType,size,contentBase64}]. id/name/mimeType:string, size:byte 수, contentBase64:string. 업로드 한도 준수 |
| error | 실패 때 {code:string,error:string}, 그 외 null |
| createdAt,updatedAt | UTC ISO 시각 |

contentBase64는 분리 전송용 표현이며 공개 프론트 완료 응답의 attachments에 넣지 않는다. 같은 내부 작업을 객체 저장소로 전달하면 bytes 대신 접근 가능한 fileId와 저장소 참조를 사용할 수 있지만 백엔드는 확정 전에 실제 원본 존재·byte 크기·접근 권한을 검증해야 한다. 비밀 URL을 프론트 응답에 노출하지 않는다.

내부 JSON에 base64를 포함하면 총 전송량은 원본 25MiB보다 커진다. 각 파일의 base64 길이는 4×ceil(byte수/3)이고 이 합계에 메타정보·JSON 크기를 더해야 한다. 공개 백엔드의 1MiB 제한을 이 내부 경로에 적용하지 않는다. 내부 한도는 최대 업로드의 인코딩 증가분과 메타정보를 수용하게 잡거나 원본을 분리 전송한다. 크기 제한은 디코딩 뒤 실제 bytes 기준도 함께 검사한다.

진행 전환은 같은 작업에 대해 단조롭게 적용한다. 완료·실패 작업을 뒤늦은 running 알림으로 되돌리지 않는다. 동일 requestId+동일 입력은 기존 job, 다른 입력은 409다. 서버 재시작 후 미완료 작업은 실패 상태와 재전송 안내로 복구하며 새 완료를 임의 생성하지 않는다.

모델 완료 후에는 분석 reply·원본 관계·completed 상태를 일관되게 게시한다. **완료 게시가 영속 확정됐음을 확인하기 전 공개 status=completed/result를 반환하지 않는다.** 공개 result의 analysisId로 바로 records POST나 apply-chat-update POST를 실행할 수 있어야 한다. 완료 게시 실패는 persisting 상태의 재확인 또는 failed로 처리하며 ‘저장 가능한 완료’로 알리지 않는다.

## 3. 백엔드의 초안 조회와 변경 반영

백엔드는 analysisId로 message,reply,원본 파일 목록,작업 kind/status,conversationId,생성 시각을 조회할 수 있어야 한다. 초안이 없으면 404, 완료 전/실패면 409, 이미 확정한 초안이면 중복 저장 409다. 프론트가 제출한 임의 reply로 초안 검증을 우회하지 않는다.

직접 활동 수정 적용 후에는 정본 reply를 general 완료로 바꾸며 같은 analysisId의 재조회도 수정 완료 결과를 돌려준다. 자료/활동 삭제 후에는 해당 정본 초안을 삭제 안내 general로 바꾼다. AI가 별도 DB에 결과를 캐시했다면 정본 변경을 반영하거나 재조회하여 오래된 분석 카드를 반환하지 않는다. 같은 ID의 데이터가 서로 다른 서버에 독립된 사본으로만 존재하는 상태를 완료로 간주하지 않는다.

## 4. 활동 전체 종합 요청

백엔드 → AI POST /api/analyze/activities/:activityId. 분리 구현에서는 JSON 본문에 아래 문맥을 직접 보낸다. ID만 보내고 AI가 작성자의 SQLite를 조회하는 방식은 사용하지 않는다.

| 필드 | 구조 |
| --- | --- |
| activity | {id,name,category:string/null} |
| previous | {summary,status,role,start_date,end_date}, 각 값 string/null |
| records | [{id,message,summary,changes,savedAt,updatedAt}]. message는 빈 문자열 허용, summary는 비빈 string, changes는 공통 Change 배열 |
| files | [[recordId,fileId,name], ...]. 문자열 3개 배열. 원본 bytes가 아닌 관계·이름 메타정보 |
| recordCount | records.length, 1~100 |
| sourceFingerprint | 백엔드가 해당 스냅샷에서 발급한 SHA-256 64자리 소문자 hex |

JSON 문자 수 250000 이하. 한도를 넘으면 422. AI는 원본 파일을 다시 읽지 않으며 받은 기록의 message/summary에서만 근거를 인용한다. 응답은 [AI 정의서](../ai/API_정의서.md)의 metadata 형식이다. sourceFingerprint는 요청값을 그대로 돌려준다.

## 5. 성장 분석 요청

백엔드 → AI POST /api/analyze/journey. 분리 구현 JSON 본문은 {records,recordCount,sourceFingerprint}다.

records 각 항목은 id,activityId,activityName,message,summary,changes,savedAt,updatedAt,activity,files를 가진다. activity는 {category,role,summary,startDate,endDate}이며 값은 string/null, files는 [{id,name}]다. 각 ID와 이름·summary·시각은 필수 string이며 message는 '' 허용이다. 기록 1~100개·JSON 250000자 이하. 미저장 초안·빈 활동·원본 bytes는 포함하지 않는다.

응답은 sourceFingerprint,recordCount,model,promptVersion=journey-v5,result를 가진다. AI는 요청 fingerprint를 그대로 반환한다. 결과 스키마·근거·정규화·날짜 규칙은 [분석 정의](../ai/분석_입출력과_검증_규칙.md)에 있다. AI는 성장 결과를 직접 확정 저장하지 않는다.

v5의 근거 카탈로그는 AI 서버 내부에서 생성한다. 백엔드는 기존 records를 그대로 보내며 카탈로그를 생성하거나 evidenceId를 저장할 필요가 없다. AI는 모델이 고른 evidenceId를 정확한 {recordId,quote}로 복원한 뒤 응답한다. 백엔드의 원문·현재 스냅샷 재검증은 유지한다. 후보 생성 뒤 실제 모델 입력이 250000자 또는 후보 2000개를 넘는 경우에도 모델 호출 전 422를 반환한다.

## 6. 남은 원본 재분석 요청

백엔드 → AI POST /api/analyze/records/:recordId/exclude-file. 분리 구현의 JSON 본문은 다음과 같다.

| 필드 | 구조·조건 |
| --- | --- |
| fileId | 삭제 대상 ID, 비빈 string |
| recordReply | 삭제 전 확정 reply의 JSON 원문 string. AI는 해석·재직렬화해서 바꾸지 말고 응답에 그대로 돌려줄 것 |
| activity | {id,name,category:string/null} |
| files | 삭제 대상을 제외한 남은 실제 파일 [{id,name,mimeType,size,contentBase64}]. 입력 순서 고정, 1개 이상 |

삭제 대상 bytes·이전 대화·기록 요약은 분석 문맥에 넣지 않는다. recordReply는 동시 변경 검증용이며 모델 입력에 포함하지 않는다. AI는 남은 원본만 분석해 reply,recordReply,fileIds를 돌려준다. fileIds는 받은 files의 ID 순서이며 reply에는 sourceUrl이 없고 changes=[]다. 새 분석을 저장하기 전에 백엔드가 삭제 전 활동 스냅샷과 현재 스냅샷을 비교한다. 실패·불일치면 실제 원본을 삭제하지 않는다.

## 7. 스냅샷·트랜잭션·권한

sourceFingerprint는 백엔드가 발급하고 현재 입력으로 재계산하는 변경 검증 토큰이다. AI가 DB 행을 같은 언어로 직렬화해 재계산할 필요는 없다. 백엔드는 활동 분석의 활동 ID/이름/유형·기록 내용/시각·파일 ID/이름, Journey의 기록/활동 메타정보/파일 관계를 안정된 정렬·UTF-8 직렬화로 해시에 반영한다. 기존 직렬화 함수를 재현하라는 요구가 아니다. 한 구현에서 정렬·직렬화 규칙이 바뀌면 기존 fingerprint가 그대로 유효하다고 가정하지 않는다.

백엔드는 분석 전 발급값·AI 반환값·저장 직전 재계산값과 기록 수를 대조한다. 불일치는 409이며 기존 결과를 보존한다. 원문 근거도 현재 기록에서 재검증한다. AI 종합 결과 자체를 입력으로 넣어 무한 재분석하지 않는다.

내부 전달은 인증·권한·전송 크기·기한을 적용한다. 프론트에서 내부 문맥/원본/완료 게시 작업을 호출하게 만들지 않는다. 다중 인스턴스는 공통 잠금·유일키·영속 상태로 중복 저장과 삭제 후 결과 부활을 막는다. 여러 저장소에 걸친 저장은 DB 트랜잭션과 임시 원본/완료 마커 등으로 동일한 원자성 효과를 구현한다.

각 파트는 위 경로·헤더를 기본으로 구현하고 실제 Base·토큰 설정 방법을 자신의 배포 안내에 명시한다. 공개 프론트 연결 전에 내부 게시·재조회·버전 충돌·원본 전달을 함께 시험한다. 새 내부 규격을 기존 개발 서버가 이미 제공하는 API로 잘못 호출하지 않는다.
