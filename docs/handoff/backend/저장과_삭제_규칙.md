# 저장과 삭제 규칙

기준일: 2026-11-06. [API](API_정의서.md) · [DB](데이터베이스_정의서.md) · [오류](../common/상태와_오류_처리.md)

## 초안과 확정 저장

AI 접수 시 초안·원본·작업 queued 상태를 일관되게 영속 보관한다. 저장소 구성과 원자성 구현 방법은 자유이며 [서버 간 전달 계약](../common/서버간_데이터_전달_계약.md)을 따른다. 모델 호출 동안 DB 쓰기 트랜잭션을 열어 두지 않는다. 완료 시 저장된 실제 활동을 다시 확인하고 analyses.reply와 작업 completed를 함께 갱신한다. 이 단계에는 새 활동·records·Timeline 생성이 없다.

사용자가 POST /records를 실행하면 초안 존재·작업 완료·기존 확정 여부를 검증하고 서버의 reply를 사용한다. 파일·링크 자료면 records.message를 빈 문자열로 만든다. 분류 변경은 analysis.materialType·files[].materialType·groups에 반영한다.

확정 트랜잭션은 다음을 함께 수행한다.

1. 새 활동은 이름 중복 검증 후 UUID 활동을 생성하고 제안한 이름·유형을 적용한다. 기존 활동은 실제 ID로 찾는다.
2. 확정 reply의 활동 정보를 실제 활동 정보로 교체한다. 새 활동은 activityCreated=true다.
3. records를 생성하고 changes마다 timeline_events를 생성한다. 신규 이벤트의 is_turning_point는 0이다.
4. 활동 updated_at을 확정 시각으로 갱신한다. 실패는 전체 롤백한다.

성공 뒤 실행 서버는 활동 메타정보 분석을 예약한다. 이 후속 분석 실패가 앞선 기록 저장을 취소하지 않는다. 같은 analysisId는 최대 한 기록으로 확정한다. 데이터 저장 유일성과 요청 처리를 함께 사용해 경쟁 요청도 중복 생성하지 않는다. 클라이언트의 임의 reply 저장 경로는 요구하지 않는다.

## 분류 수정·활동 이동

저장 전 수정은 카드와 세션에만 반영한다. analysisId 확정 시 선택 ID와 classification을 전달한다. 저장 후 PATCH는 records.reply와 activity_id·updated_at을 변경한다. 현재 분류 수정 계약은 연결 활동과 자료 유형만 바꾸며 기존 변화 이벤트는 보존한다. 다른 활동으로 이동하면 기존·새 활동 updated_at을 갱신하고 양쪽 종합을 예약한다. 초안의 analyses.reply가 자동으로 확정 복사본과 같아지는 구조가 아니다.

## 대화로 직접 수정

완료 AI chat 작업과 연결된 analysisId만 받는다. 파일 첨부나 link 작업은 거절한다. 허용 필드는 role/status/summary/startDate/endDate, 최대 5개·중복 불가다. 일부 날짜만 바꿔도 기존 반대쪽 날짜와 함께 유효성을 검사한다.

같은 트랜잭션에서 값·표시 기간·updated_at을 바꾸고 metadata_status=idle로 만든 뒤 초안을 완료 general로 교체한다. 재호출은 완료 general을 반환하므로 수정 시각을 다시 바꾸지 않는다. 실행 중 종합 큐는 취소하며 새로운 기록·타임라인·정정 이력을 만들지 않는다. 이후 자료 저장의 자동 종합은 허용한다. value=null은 명시적 필드 삭제다.

## 활동 정보 자동 종합

활동별 짧은 지연(기존 동작 500ms)으로 연속 저장을 묶고 진행 중 변경은 후속 분석 대상으로 표시한다. 백엔드는 활동·확정 기록·파일 메타정보와 sourceFingerprint를 한 스냅샷으로 만들어 [서버 간 전달 계약](../common/서버간_데이터_전달_계약.md)의 활동 종합 JSON을 AI에 보낸다. AI는 같은 로컬 DB를 읽지 않고 전달받은 문맥으로 분석하며 fingerprint를 그대로 반환한다. 지연/큐 기술은 자유지만 저장 누락과 오래된 결과의 덮어쓰기를 막아야 한다.

저장 직전 초기·현재·응답 fingerprint와 기록 수를 대조하고 각 값의 근거 recordId/quote를 검사한다. summary는 새 값, role/status/날짜가 null이면 기존 값을 보존한다. 이전 AI 출력은 해시 입력에 넣지 않으며 종합 성공은 metadata_updated_at을 바꾼다. 자료 저장 시각과 구분한다.

기록 이동으로 해당 활동 기록이 0개가 된 큐 처리에서는 이전 AI가 생성한 정보만 비우고 idle로 돌린다. 수동 설정 값을 무조건 지우지 않는다. 프로세스 재시작 시 queued/running은 failed가 된다. 새 구현의 큐 방식은 자유이며 다중 인스턴스에서는 공유 작업 상태와 잠금을 사용한다.

## 활동 전체 삭제 ARCHIVE-04

홈 작업 queued/running이 있으면 409. 트랜잭션 안에서 활동 존재·정확한 활동명 confirmation을 검증한다. 연결 확정 기록의 원본 files를 삭제하고 분석 초안은 ‘삭제됨’ general로 교체한다. records 삭제와 함께 해당 Timeline을 제거한다. DB CASCADE 또는 동등한 원자성 처리를 사용한다. 미확정 초안·직접 수정 응답 중 삭제 활동을 가리키는 카드도 general로 바꾼 뒤 activities를 삭제한다.

대화 analyses와 작업 이력은 보존한다. 아직 확정되지 않은 별도 입력 원본을 활동 확정 자료로 간주해 일괄 삭제하지 않는다. 삭제 후 해당 활동 종합 큐를 취소한다. 같은 이름으로 새 활동을 만들어도 ID는 새로 발급한다.

## 자료 개별 삭제 ARCHIVE-05

자료는 확정 기록에 실제 연결됐는지 먼저 확인한다. 같은 기록의 동시 삭제를 잠금으로 막고 겹치면 409다. 잠금 저장 방식은 선택 가능하다.

- 같은 기록에 파일이 더 남으면 원본에서 대상 파일만 제외하고 AI 재분석을 먼저 요청한다. 이전 기록 요약·대화·삭제 파일은 모델 문맥에 넣지 않는다. 응답의 recordReply(기존 JSON 원문), 남은 fileIds 순서, 이름·스키마·sourceUrl 없음·changes=[]를 대조한다.
- 연결 실패·응답 불일치면 502이며 실제 삭제하지 않는다. 분석 중 활동 입력 해시가 바뀌면 트랜잭션에서 409로 거절한다.
- 검증 성공 시 files에서 해당 원본을 지우고 기존 초안을 퇴역 general로 바꾼다. 남은 파일이 있으면 records.message=''와 새 reply·시각을 저장하며 기존 Timeline을 비운다. 마지막 파일 또는 링크면 해당 records를 삭제한다.
- 활동 전체 요약·상태·역할·기간·metadata 상태를 비우고 updated_at을 갱신한다. 남은 기록이 있으면 실행 서버가 종합을 다시 예약한다. 활동 행 자체는 유지한다.

파일 원본을 지우기 전 유료 분석이 발생할 수 있다. 실패하면 원본을 보존한다는 것이 원자성의 경계이며 모델 호출을 롤백한다는 뜻은 아니다.

## 성장 결과 무효화·저장

추가·수정·활동 정보 변경은 입력 fingerprint 변화로 stale을 계산한다. Journey 입력에는 활동 status와 period 표시 문자열은 없고 category/role/summary/start_date/end_date가 포함된다. 따라서 상태만 직접 변경한 경우 그 값만으로 stale이 바뀌는 계약은 아니다.

자료·활동 삭제는 모든 journey_analyses의 요약을 삭제 안내로 교체하고 배지·이벤트·분류를 비우며 source_fingerprint를 deleted:UUID로 바꾼다. 삭제된 근거를 표시하지 않도록 과거 스냅샷도 모두 정리한다. DB 기록 행을 유지하므로 예전 record_count는 남으며 현재 수와 구분한다.

새 Journey 분석은 AI 결과의 fingerprint·기록 수·인용·분류·활동·월·비교 근거를 검증한 다음 새 스냅샷을 INSERT한다. 이벤트·배지 ID는 UUID로 재발급한다. 분석은 Timeline이나 홈 기록을 변경하지 않는다. 실패는 이전 스냅샷을 보존한다.

## 전체 데이터 삭제 SETTINGS-01

confirmation은 ‘전체 삭제’와 정확히 같아야 한다. 공통 저장 범위에서 Journey·활동 종합·AI 홈 queued/running 상태를 확인하고 진행 중이면 409다. 삭제 중 새 작업이 끼어들지 않게 동일 범위 잠금을 적용한다. Timeline·기록·원본·작업·성장 결과·초안·활동을 모두 제거하며 참조 제약에 맞춰 자식부터 처리한다. 실패 시 일부만 삭제된 성공을 반환하지 않는다. 별도 원본 저장소도 완료 마커/보상 등으로 같은 결과를 보장한다. 성공 응답 이후 프론트가 현재 탭 세션을 제거한다. 사용자별 운영 범위는 배포 문서에 따라 일관되게 적용한다.
