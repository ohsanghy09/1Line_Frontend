# 개발 규칙 · 홈 AI 채팅

최종 정리: 2026-11-04

현재 구현 상태는 [통합 현황](chat/현재_구현_상태.md)을 먼저 참고한다. 아래 작업 방식은 유지하되, 저장·수정·링크는 후속 사용자 요청으로 구현했고 홈은 로컬 REST API와 연결했다.

이 문서는 이번 대화에서 확인한 사용자 요구와 현재 구현 원칙을 구분해서 기록한다. **사용자의 최신 요청이 이 문서보다 우선한다.** 아래 규칙을 근거로 불필요한 승인 단계를 만들지 않는다.

현재 구현 상태와 다음 진행 방향은 [개발 기록](chat/개발_기록.md)을 참고한다.

2026-11-11 후속 정리: 백엔드·AI 개발 서버와 src/mocks의 초기 예시는 프론트 저장소에서 제거했다. 아래 목 분석·서버 경로 설명은 초기 개발 당시 이력이다. 현재 화면은 HTTP API 응답을 사용하고, 프론트 계약·세션 검사용 합성 데이터만 tests/fixtures에 유지한다. 최신 작업 상태는 [프론트 연동 정비](../frontend-integration/README.md)를 따른다.

## 1. 사용자가 직접 강조한 작업 방식

### 기능은 하나씩 진행한다

사용자는 채팅을 직접 이해하고 확인하면서 단계적으로 개발하기를 원한다. 현재 요청한 기능을 완성하고, 관련 없는 기능이나 스타일을 함께 바꾸지 않는다.

“다른 것들은 조정하지 말고”라고 요청하면 지정한 범위만 수정한다. “다시 되돌려줘”는 문맥상 직전 변경을 되돌리는 뜻으로 해석하고, 이전 작업 전체를 초기화하지 않는다.

### 코드의 역할이 보이게 작성한다

- 상태·이벤트·비동기 처리·화면 영역의 목적을 한국어 주석으로 설명한다.
- 역할이 바뀌는 부분에는 적절한 빈 줄을 두어 읽기 쉽게 한다.
- 목데이터에는 각 응답과 주요 필드가 무엇을 표시하는지 설명한다.
- 사용자가 수정한 설명 주석을 필요 없이 제거하거나 전체 파일을 재포맷하지 않는다.

### 설명은 작게 끊어서 한다

사용자가 코드 설명을 요청하면 동작 순서대로 한 부분씩 설명한다. 한 번에 전체 코드를 길게 설명하지 않는다. 사용자가 “다음”이라고 하면 이어지는 부분을 설명한다.

## 2. API 연결에 대한 사용자 요구

최종 목표는 AI의 대답과 분석 결과를 실제 AI API에서 받는 것이다. 현재는 목데이터로 흐름을 확인하고, 이후 교체하기 쉽게 구성한다.

사용자가 지정한 우선 목표는 **텍스트 경험 입력·파일 업로드·변화 없는 파일 및 텍스트·다중 파일 일괄 업로드를 실제 AI API 연결 후에도 원본과 같은 결과 구성으로 사용할 수 있게 하는 것**이다. 당분간 API 응답 자리는 목데이터로 유지하고, 시나리오별 채팅 흐름을 단계적으로 완성한다. 저장 기능이나 링크 입력을 이 목표보다 먼저 진행해야 하는 것으로 간주하지 않는다.

- 화면은 `getChatReply`·`getLinkReply`와 기록 서비스를 호출한다. 화면용 구조로의 변환은 서비스 경계에서 처리한다.
- 홈 목 분석과 진행은 `api-server/src/mock-reply.js`, `progress.js`에 둔다. `src/mocks/Home/`는 독립 미리보기 등 기존 개발용 예시다.
- 응답은 HTML이 아닌 JSON에 대응하는 데이터로 관리한다.
- 카드의 문구·활동·분류·개수·변화·근거를 응답 데이터에서 표시한다.
- UI 디자인과 로딩 애니메이션은 프론트엔드가 담당한다.
- API 응답 초안과 확정된 서버 명세를 구분한다.
- 실제 API 연결 후 활동·자료 유형·주요 변화 여부의 판단은 API 응답에 따른다. 프론트엔드의 목 분류 규칙을 실제 분석으로 계속 적용하지 않는다.
- 변화 없는 텍스트도 별도 검토한다. 모든 텍스트를 기능 축소나 Turning Point 발견으로 처리하지 않는다.

`Promise<ChatReply>`를 유지하는 서비스 경계는 현재 구현 방식이다. 실제 API 명세가 달라지면 서비스에서 화면용 구조로 변환할 수 있다.

### 카드와 다른 UI에도 적용할 개발 방식 — 2026-11-03 사용자 확인

앞으로 카드와 다른 화면 기능도 **실제 사용자 입력 → 서비스 함수 → 타입이 있는 목 응답 → 응답 데이터로 화면 표시**하는 현재 방식을 따른다. API 연결 전에는 분석 결과를 목데이터로 준비하고, 실제 연결 시 서비스에서 실제 응답을 화면용 구조로 변환한다.

- 파일명·첨부 개수·입력한 글·전송/응답 시각처럼 실제 입력과 동작으로 알 수 있는 값은 유지한다. 예시 파일명으로 덮어쓰지 않는다.
- 활동·자료 유형·단계·관련 자료·AI 요약·Before/After 등 분석 항목은 목 응답 데이터에 둔다. 컴포넌트에는 특정 활동이나 예시 분석 문장을 직접 고정하지 않는다. 제목·버튼·정보 라벨과 같은 UI 문구는 컴포넌트가 담당한다.
- 같은 종류의 입력은 같은 카드 구조를 사용한다. 단일 파일에서 특정 이름만 원본 형식의 카드로 보내고 나머지는 별도 일반 카드로 보내는 방식을 다시 도입하지 않는다.
- 중요 변화가 없는 응답은 `changes: []`처럼 데이터로 구분하고, 비교 카드나 변화 배지를 억지로 생성하지 않는다.
- 목 분석은 실제 파일 내용 분석과 구분한다. 예시 활동·자료 유형·요약이 표시되더라도 실제 입력의 의미를 판단했다는 뜻이 아니다.
- 프론트 예시는 `src/mocks/`, 서버 목 분석은 `api-server/src/`, 요청 경계는 `src/services/`, 공통 화면 구조는 `src/types/`, 화면 표시는 페이지와 컴포넌트에 둔다. 새 기능은 필요한 범위부터 만든다.
- 진행 상태도 현재는 목 서비스에서 제공한다. 실제 API 연결 후에는 서버가 제공하는 상태를 표시하고, 최종 결과만 제공한다면 일반 로딩을 사용한다.
- 시연 시나리오 영역과 전용 호출 코드는 사용자 요청으로 제거했다. 실제 입력 경로를 완성하며, 이후 요청 없이 시연 UI를 다시 추가하지 않는다.

사용자 요청으로 카드 작업용 독립 페이지와 라우트는 제거했다. 실제 홈 입력으로 동작을 확인하며 시연 UI나 가짜 성공 처리를 추가하지 않는다.

위 원칙은 개발 방식의 합의이며, 아직 구현하지 않은 카드·수정·저장·다른 화면을 모두 완성하라는 지시는 아니다.

## 3. 원본 디자인과 사용자 수정의 우선순위

기준은 [원본 HTML](../common/references/1Line_reference.html)이다. 사용자 요청이 없는 문구·색상·배치·버튼을 임의로 바꾸지 않는다. 다만 이후 사용자가 요청한 반응형·너비 조정은 원본보다 우선한다.

**원본 HTML 파일은 수정하지 않는다.** 대화 중 어색한 반응이나 누락된 상호작용을 발견하면 현재 구현 중인 `src/pages/Home.tsx`에서 개선한다. 기존 구조상 필요한 경우 연결된 컴포넌트·서비스·목데이터도 조정하되, 개선을 위해 원본을 먼저 고치는 방식은 사용하지 않는다.

원본의 결과 카드와 시나리오 의도는 유지한다. 입력과 맞지 않는 답변, 근거 없는 주요 변화 생성, 저장 전 저장 완료 안내처럼 부자연스러운 흐름은 구현 화면에서 보완한다. 실제 입력 내용과 목 시연 응답의 한계를 구별해서 설명한다.

다중 파일 카드는 다음 구성을 유지한다.

1. “총 N개의 자료를 확인 후 일괄 그룹화했어요.”
2. 활동명과 “N개 파일 자동 매칭” 배지
3. 자료 유형과 개수 박스
4. 💡 버전 연결 안내
5. “전체 저장”, “자료 확인”
6. 실제 응답 시각과 “Growth AI” 표시

이 카드에 사용자 요청 없이 별도 활동 제목, 전체 파일 목록, 수정·다른 활동 선택 버튼을 다시 추가하지 않는다. 데이터가 달라지면 개수와 요약은 실제 응답에 맞춰 바뀔 수 있다.

응답 대기 표시는 원본의 **Bot 아이콘 + 회색 말풍선 + 움직이는 점 3개**를 유지한다.

이후 사용자 요청으로 AI 카드 최대 너비는 기본 85%, `sm` 이상 80%로 줄였다. 사용자 말풍선 최대 너비는 80%, 하단 시각과의 간격은 4px다. 하단 시각은 ‘방금 전 → N분 전 → 시각/날짜’로 표시하고 AI 카드에는 ‘ · Growth AI’를 붙인다. 현재 표시는 30초마다 갱신한다.

## 4. 자료 유형 박스의 줄바꿈 규칙

사용자가 말한 “다른 글자도 한 줄”은 **자료 유형 문구**에 대한 요청이다. 카드 제목이나 하단 안내까지 한 줄로 고정하라는 뜻이 아니다.

- ‘와이어프레임 2개’처럼 유형명과 개수를 한 줄로 표시한다.
- ‘2’와 ‘개’가 서로 다른 줄로 떨어지지 않도록 한다.
- 유형이 1개든 2·3·4개든 남은 공간을 자연스럽게 활용한다.
- 공간이 부족하면 문구를 쪼개는 대신 박스 전체를 다음 줄로 보낸다.
- 아주 긴 유형명은 현재 박스 내부 가로 스크롤로 확인한다. 문구를 임의로 잘라내지 않는다.
- 분류 1개일 때 좌우 12px 마진을 추가한 변경은 사용자가 취소했다. 다시 넣지 않는다.
- 제목·활동명·하단 안내에 적용했던 `truncate`와 `title` 기반 말줄임 변경도 취소했다. 자료 유형 변경을 다른 문구에 확대 적용하지 않는다.

과거의 다중 파일 카드 전용 `28rem` 제한은 제거했다. 현재는 위 3절의 공통 카드 최대 너비를 적용한다.

## 5. 파일 입력 규칙

파일을 **선택·드롭하는 단계**와 **전송하는 단계**를 구분한다.

- 파일 여러 개를 입력창에 첨부할 수 있어야 한다.
- 선택한 파일은 먼저 전송 전 첨부 목록에 보인다.
- 보내기 버튼 또는 Enter로 전송한 뒤 파일명을 사용자 말풍선에 표시한다.
- 파일 선택이나 드롭만으로 자동 전송하지 않는다.
- 첨부한 파일명을 목데이터의 고정 파일명으로 바꾸지 않는다.
- 파일만 보내기, 텍스트와 함께 보내기, 전송 전 개별 삭제를 유지한다.
- 드롭 영역은 현재 입력창·첨부 영역이다. 사용자 요청 없이 전체 화면 드롭으로 확대하지 않는다.

## 6. 현재 구현에서 유지할 구분

이 절은 사용자의 직접 발언을 그대로 옮긴 규칙이 아니라, 현재 코드와 연동 구조를 보존하기 위한 구현 원칙이다.

- 목 분석을 실제 AI 분석으로 설명하지 않는다. 파일 원본 업로드·보관은 현재 로컬 서버에서 실제 수행하며 분석과 구분한다.
- 현재 파일명 분류 규칙을 실제 AI의 분석 기준으로 확정하지 않는다.
- 예시 활동명 ‘1호선톤’을 실제 사용자 활동 매칭으로 간주하지 않는다.
- 버전 연결이 있다는 사실만으로 주요 변화나 Turning Point를 만들지 않는다.
- 분석 결과를 받은 것과 사용자가 기록을 저장한 것은 별도 상태다.
- 아직 저장되지 않은 결과를 저장 완료로 표시하지 않는다.
- 저장·수정 API가 없다는 이유로 임의의 가짜 성공 동작을 추가하지 않는다. 사용자가 목 저장 흐름을 요청하면 그 범위에서 구현한다.
- 최신 비동기 응답만 반영하는 보호와 한글 조합 중 Enter 처리를 유지한다.

## 7. 캡처 확인과 문서 관리

문서와 참고 자료는 `docs/` 아래에 프로젝트별로 모아 관리한다. 프론트 문서는 `docs/frontend/`, 백엔드 문서는 `docs/backend/`, AI 문서는 `docs/ai/`, 공통 계약·연동 계획은 `docs/common/`에 둔다. 전체 문서 위치는 [문서 목록](../README.md)을 따른다. 원본 HTML·기능명세서·캡처는 `docs/common/references/`에 둔다. 앱 배포 자산으로 import하지 않는다.

채팅 문서·변경 이력은 `docs/frontend/chat/`, 채팅 컴포넌트는 `src/components/chat/`, 전용 모달은 그 아래 `modals/`에 둔다. 공통 규칙은 현재 문서에 유지하며 다음 기능은 별도 폴더로 구분한다.

사용자 캡처는 `docs/common/references/screenshots/`에 둔다. 경로 오류가 표시돼도 실제 파일이 있는지 확인하고, 존재하면 이미지를 직접 열어 확인한다. 이번에 확인한 파일은 `image1.PNG`다.

새 작업을 시작할 때는 관련 소스와 최신 캡처를 함께 본다. 과거에 제안했다가 취소한 스타일을 다시 적용하지 않는다.

의미 있는 기능이나 API 구조가 바뀌면 [개발 기록](chat/개발_기록.md)과 해당 API 문서를 갱신한다. 검증은 수행한 범위만 적고, 미구현 기능은 완료로 기록하지 않는다.

구현한 기능은 [구현 기능 목록](chat/구현_기능/README.md)의 해당 기능 문서에도 기록한다. 현재 동작·데이터 위치·실제 입력과 목 값의 구분·API 교체 지점·검증 결과·남은 작업을 함께 남겨 다음 작업자가 이어갈 수 있게 한다.

## 8. 공통 React 구조와 데이터 원칙

기존 Vite·Tailwind 환경을 다시 초기화하지 않는다. 원본의 Tailwind CDN 설정·Lucide 전역 스크립트·DOM 치환 코드를 React 앱에 붙이지 않고 기존 플러그인과 React 아이콘을 사용한다. 2026-11-11 사용자 지정에 따라 프로젝트·화면 브랜드는 Growth AI이며 설명 문구는 ‘나의 경험을 성장으로’다.

MainPage는 Sidebar와 Outlet을 갖는 부모 화면이다. pages의 위치와 src/main.tsx의 BrowserRouter를 유지하고 라우터를 중복 생성하지 않는다. 공통 레이아웃을 위한 layouts·app·components/layout 계층을 별도로 추가하지 않는다. Sidebar 활성 상태는 NavLink와 URL로 관리한다. 이후 상세 페이지의 경로·이름은 구현할 때 정하며 기존 제안 주소를 확정 사양으로 취급하지 않는다.

컴포넌트는 독립 상태·반복 사용·복잡도가 생긴 범위부터 분리한다. 작은 정적 조각이나 향후 기능의 모든 타입·서비스를 미리 파일로 만들지 않는다. JSX 파일은 tsx, 일반 타입·로직은 ts를 사용하고 타입 전용 참조는 import type으로 가져온다. 공통 타입을 중복 정의하지 않는다.

표시 이름과 영속 ID를 구분한다. 선택·펼침·수정 대상은 배열 순서나 표시 문구 대신 안정적인 ID로 연결한다. 필터·정렬·개수는 데이터에서 계산하고 원본 배열을 직접 sort하거나 목 객체를 수정하지 않는다. 부분 조회에서는 서버 총계와 현재 로드한 개수를 구분하며 개수를 맞추려고 빈 자료를 만들지 않는다. 실제 버전 관계는 서버 식별자·관계로 연결하고 목 파일명 규칙을 실제 분석으로 사용하지 않는다.

저장·수정 성공 후 관련 화면 데이터는 재조회하거나 공유 상태를 갱신해 일치시킨다. Project Timeline과 Growth Journey는 별도 데이터이며 기록 저장만으로 양쪽 이벤트를 무조건 생성하지 않는다. 원본의 alert-only 저장·수정이나 모든 파일에 같은 상세를 표시하는 동작은 그대로 이식하지 않는다.

## 9. 접근성·시각 검증 원칙

사용자 텍스트·파일명·URL은 일반 데이터로 렌더링한다. HTML 문자열 조합이나 dangerouslySetInnerHTML로 원본 채팅을 재현하지 않고 React의 자동 이스케이프를 유지한다.

이동은 링크, 조작은 버튼을 사용하고 button을 중첩하지 않는다. 아이콘 버튼에는 접근 가능한 이름, 입력에는 label, 필터에는 선택 상태, 펼침에는 aria-expanded/aria-controls를 제공한다. 메시지·진행 안내는 상태 변화 중심으로 알리고 과도한 반복 알림을 피한다.

오버레이를 만들 때 최초 초점·초점 제한·Escape·닫은 뒤 초점 복귀·배경 스크롤 제어·내부 스크롤을 확인한다. 원본 모달은 배경 클릭 닫기가 없으므로 임의로 추가하지 않는다. 기본은 활성 오버레이 하나이며 중첩이 필요하면 레이어와 초점 소유권을 정한다. 이 항목은 개발·검증 기준이며 현재 모든 항목을 브라우저에서 검증했다는 뜻은 아니다.

폰트 선언만으로 웹폰트 파일이 로드되는 것으로 간주하지 않는다. 기존 Pretendard 로드와 테마를 유지하고 색상 토큰 명명만 바꾸기 위한 일괄 변환은 하지 않는다. 원본 CDN과 현재 Tailwind의 기본 그림자·모서리·링 차이가 있을 수 있으므로 같은 클래스만으로 시각 일치를 판정하지 않는다. 원본의 slate/indigo/emerald 차이를 모두 하나의 브랜드 색으로 치환하지 않는다.

검증 시 320/375/768/1024/1440px의 가로 넘침·긴 파일명/URL·오버레이·키보드·초점·reduced-motion을 확인한다. 새 hover/모션을 임의로 확대하지 않는다. 실제 동작 검사는 저장 중복 방지·변화 없음 이벤트 미생성·수정 대상 연결·취소·복합 필터/정렬 등에 집중하며 정적 마크업을 반복하는 테스트를 늘리지 않는다.

구현 가이드라인에서 중복되지 않는 원칙을 위 항목에 통합했다. 후속 화면의 설계 제안과 원본 데이터 검토사항은 [후속 화면 검토사항](후속_화면_검토사항.md)에 분리하며 새 기능 구현 지시로 간주하지 않는다.
