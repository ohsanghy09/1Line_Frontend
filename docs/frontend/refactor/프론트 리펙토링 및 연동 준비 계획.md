# 프론트 리팩토링 및 원격 API 연동 준비 계획

목표는 **기존 프론트 기능을 유지하면서 로컬 개발 서버 의존성을 제거하고, 원격 백엔드·AI에 연결할 준비를 하는 것**이다.

이 문서는 작업 계획이며, 작성만으로 코드 변경이나 서버 분리가 수행된 것은 아니다. 실제 원격 서버 연동 검증은 다른 파트의 서버가 준비된 뒤 별도로 진행한다.

## 작업 진행 기준

사용자가 변경 이유와 영향을 이해하면서 진행할 수 있도록, 각 작업은 아래 순서를 따른다.

1. **계획 설명**: AI가 이번에 확인할 범위와 목적, 예상 진행 순서를 먼저 설명한다.
2. **사용자 이해와 질문**: 사용자가 계획을 파악하고 질문할 시간을 갖는다. 사용자가 이해하기 전에 다음 단계로 앞서가지 않는다.
3. **현재 코드 검사**: 사용자가 검사 진행을 요청하면 AI가 현재 코드와 의존성을 확인하고 결과를 설명한다. 이 단계에서는 코드를 수정하지 않는다.
4. **검사 결과와 변경 방향 확인**: 사용자가 검사 결과를 파악할 수 있도록 유지할 부분, 변경할 부분, 변경 이유와 기존 기능에 미칠 영향을 설명한다.
5. **수정과 검증**: 사용자가 변경 진행을 요청하면 해당 범위만 작은 단위로 수정한다. 기존 기능에 영향이 없는지 관련 검사를 수행하고 변경 내용·검증 결과·남은 한계를 설명한다.

**계획 설명·코드 검사·실제 수정을 구분한다.** 계획 전체를 작성하거나 문서를 읽어 달라는 요청을 전체 구현에 대한 요청으로 해석하지 않는다. 한 작업을 확인한 뒤 다음 작업도 같은 순서로 진행한다.

다음 세션에서는 이 문서를 먼저 읽고, 사용자가 마지막으로 확인한 단계와 실제 변경 상태를 확인하여 이어간다. 진행한 작업과 검사 결과, 다음 시작 지점을 기록하여 이미 끝난 작업을 반복하지 않는다.

## 1. 현재 상태와 보존할 기능 정리

- [ ] 현재 변경과 검사 결과를 기준점으로 남긴다.
- [ ] 전달한 마크다운 명세를 기능 보존 기준으로 사용한다.
- [ ] 기존 Swagger 미갱신과 Node 시간 표시 차이는 이번 변경으로 생긴 문제와 구분한다.
- [ ] 화면 확인은 **홈 → 나의 발자국 → Growth Journey** 순서로 진행한다.

모든 서버 내부 코드를 먼저 이해할 필요는 없다. **프론트가 무엇을 요청하고, 어떤 응답으로 화면을 바꾸는지**를 중심으로 확인한다.

## 2. 로컬 서버 의존성 목록 작성

현재 코드에서 다음 연결을 찾는다.

| 확인 대상 | 대표적인 의존성 |
| --- | --- |
| 실행·빌드 | Swagger 자동 생성이 백엔드 소스를 읽음 |
| 검사·스크립트 | 일부 검사가 로컬 서버 구현을 직접 가져옴 |
| API 설정 | 로컬 주소로 고정된 Vite 프록시 |
| 안내·패키지 | 로컬 서버 실행을 전제하는 설명과 의존성 |

- [ ] 각 항목을 **유지·교체·분리·제거** 중 어떻게 처리할지 정한다.

## 3. 프론트 API 설정 정리

- [ ] 기존 백엔드·AI Base URL 환경변수를 활용한다.
- [ ] 서버 주소와 API 경로를 분리해 관리한다.
- [ ] 명세와 일치하는 기존 API 경로·요청·응답은 유지한다.
- [ ] 개발용 프록시를 사용할 때와 원격 주소를 직접 사용할 때의 설정을 정리한다.
- [ ] AI 주소의 `/api`가 중복되거나 빠지지 않는지 확인한다.

실제 주소·인증 방식이 미정이면 임의로 정하지 않고 협의 항목으로 남긴다.

## 4. 실행·검사를 로컬 서버 소스에서 분리

- [ ] `predev`, `prebuild`의 Swagger 자동 생성 연결을 해제한다.
- [ ] Swagger 작성은 사용자가 API 흐름을 확인한 이후로 미룬다.
- [ ] 서버 구현을 직접 가져오는 프론트 검사는 **독립적인 API 대역과 계약 데이터**를 사용하도록 바꾼다.
- [ ] 서버 전용 검사는 서버 쪽에 보존한다.
- [ ] 기존 동작을 확인하는 유효한 검사를 단순 삭제하지 않는다.

이 단계의 목표는 **서버 소스 없이 프론트 실행·빌드·관련 검사가 가능하도록 만드는 것**이다.

## 5. 필요한 범위만 프론트 리팩토링

- [ ] 공통 API 설정·HTTP 요청·오류 처리의 책임을 정리한다.
- [ ] 채팅 접수·폴링·응답 검증·복원 로직을 필요한 단위로 나눈다.
- [ ] 사용하지 않는 코드·목업·타입·패키지는 참조를 확인한 뒤 제거한다.

디자인, 저장 방식, 사용자 기능과 공개 API 계약은 임의로 바꾸지 않는다. 기능 단위로 작게 변경하고 관련 검사를 진행한다.

## 6. 개발 서버 폴더 분리와 최종 로컬 검증

의존성을 해소한 뒤 다음을 진행한다.

- [ ] 서버 소스·DB·첨부 원본·`.env` 등의 보존 방법을 정한다.
- [ ] 백엔드·AI 개발 서버 폴더를 프론트 작업 폴더에서 분리한다.
- [ ] 서버 폴더 없이 개발 서버 실행·빌드·코드 검사·관련 검사가 가능한지 확인한다.
- [ ] 성공 응답뿐 아니라 오류·시간 초과·중복 저장 방지·조회 복원을 검증한다.

**프론트가 실행된다는 것과 실제 데이터를 사용할 수 있다는 것은 구분해야 한다.** 서버가 준비되기 전 기능 검증은 API 대역으로 수행하고, 실제 연결 성공으로 보고하지 않는다.

## 7. 원격 서버 준비 후 실제 연동 검증

다른 파트가 서버를 준비하면 실제 주소를 설정하고 다음을 확인한다.

- [ ] CORS·인증·파일 업로드·시간 제한
- [ ] 분석 → 초안 보관 → 확정 저장
- [ ] 조회·수정·삭제·성장 분석
- [ ] 실패·재접속·중복 요청 시 데이터 일관성

백엔드와 AI 사이의 공유 DB 제거와 내부 API 구현은 해당 파트가 담당하고, 프론트는 명세에 맞는 요청과 응답 처리를 검증한다.

## 첫 작업

**첫 실제 작업은 1~2단계, 현재 기준점과 로컬 서버 의존성 목록을 정리하는 것**이다. 그 목록을 사용자와 함께 확인한 뒤 가장 작은 변경부터 진행한다.
