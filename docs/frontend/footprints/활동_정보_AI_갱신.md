# 활동 전체 정보 AI 자동 갱신

후속 기능: [대화로 활동 정보 직접 수정](../chat/구현_기능/대화로_활동_정보_수정.md)을 추가했다. 요청한 필드만 DB에서 바로 변경하며 새 기록은 만들지 않는다. 그 순간의 기존 자동 분석은 무효화하지만 영구 잠금은 두지 않아 이후 자료 저장의 자동 종합에서는 다시 갱신될 수 있다.

## 사용자 흐름

홈의 신규 활동 저장 또는 기존 활동 자료 저장이 성공하면 백엔드가 별도의 활동 전체 분석을 예약한다. 사용자는 전체 요약·상태·기간·역할을 입력하지 않는다. 자료 저장은 먼저 완료하고 ‘활동 정보를 정리하고 있어요’를 표시한다. 분석이 완료되면 발자국·최근 활동·활동 상세에서 DB의 최신 정보를 조회한다.

- 전체 요약: 해당 활동의 확정 기록을 종합한 목적·진행 내용·결과 설명이다. 이번 자료 한 건의 요약과 구분한다.
- 상태: 진행 중/완료 중 실제 근거로 판단한다. 개별 작업 완료나 발표 예정만으로 활동 전체 완료를 만들지 않는다.
- 기간: 명시된 실제 활동 시작·종료일을 YYYY-MM 또는 YYYY-MM-DD로 정규화한다. 업로드일·저장일·문서 작성일을 활동 기간으로 쓰지 않는다.
- 역할: 사용자가 직접 맡은 역할만 판단한다. 팀 전체 업무나 다른 사람의 역할을 가져오지 않는다.
- 근거가 부족한 상태·기간·역할은 null로 반환하고 서버가 기존 값을 보존한다. 기존 값도 없으면 화면은 미설정으로 표시한다. 새로운 명시적 근거가 있으면 갱신한다.

새 활동인지 기존 활동인지는 여전히 카드에서 사용자가 선택한다. AI 종합 정보 갱신은 선택한 자료의 확정 저장 뒤에만 실행한다. 일반 채팅·미저장 제안·단순 화면 조회는 이 분석을 호출하지 않는다. 일반 텍스트 채팅의 한 번 요청 방식은 유지되며, 확정 저장 시 활동 정보용 모델 호출이 별도로 추가된다.

## 분석 입력과 검증

AI 서버는 공유 DB에서 선택한 활동의 확정 records만 읽는다. 입력 글, 저장된 자료 요약·변화, 기록 ID·시각, 연결 파일 ID·이름, 기존 활동 정보를 전달한다. 파일 원본 BLOB은 다시 모델에 보내지 않는다. 따라서 원본에만 있고 저장된 글·요약에 빠진 사실은 이번 분석에서 확인할 수 없으며 추정하지 않는다. 이를 보완하기 위해 홈 요약 프롬프트에 자료에 명시된 기간·사용자 역할·완료 여부의 핵심 사실을 짧게 남기는 규칙을 추가했다.

AI는 각 새 값에 실제 recordId와 연속 원문 quote를 반환한다. Python과 백엔드가 모두 원문 존재 여부를 검사한다. 날짜 형식·실제 날짜·기존 값을 보존한 뒤의 기간 역전도 검사한다. 원문 검증은 인용 출처 검증이며 의미 판단 전체의 정확도를 보장하지 않는다.

기록·파일 메타정보와 활동 식별 정보의 SHA-256 해시를 Python/Node가 동일하게 계산한다. 분석 중 원본 기록이 달라졌거나 응답의 해시·기록 수가 일치하지 않으면 결과를 적용하지 않는다. 활동 정보 AI 출력 자체는 해시에 넣지 않아 자기 갱신으로 재분석이 반복되지 않는다. 현재 한도는 활동당 기록 100개·JSON 문맥 250000자다. 초과 시 일부 기록으로 몰래 분석하지 않고 실패 처리해 기존 정보를 보존한다.

## 자동 실행과 실패 처리

- 실제 실행 서버 `api-server/src/server.js`는 `autoActivityAnalysis: true`로 구동한다. 앱 생성 함수 기본값은 false로 검사·재사용 시 의도하지 않은 유료 호출을 막는다.
- 기록 POST 후 해당 활동을 예약한다. 기록 PATCH 후에는 변경 전·후 활동을 예약해 자료 이동도 반영한다. 아직 개별 삭제 API는 없으므로 삭제 기능의 자동 연결은 후속 작업이다.
- 같은 활동의 연속 저장은 기본 500ms 동안 묶는다. 진행 중 추가 변경은 겹쳐 실행하지 않고 완료 후 최신 입력으로 한 번 더 분석한다.
- 같은 입력의 네트워크·모델·검증 실패는 자동으로 유료 재시도하지 않는다. 기록과 이전 활동 정보는 유지한다.
- 홈의 저장 카드 또는 활동 상세에서 ‘활동 정보 다시 분석’으로 재시도한다. 상태 조회 실패는 ‘상태 다시 확인’으로 조회만 다시 한다.
- 활동 정보 접수 단계의 DB 오류도 이미 성공한 자료 저장을 실패로 바꾸지 않는다. 오류 상태 기록까지 불가능하면 기존 해시와의 차이(stale)로 재시도를 안내할 수 있다.
- 서버 재시작 시 queued/running은 중단 실패로 표시하며 자동 유료 복구를 하지 않는다. 진행 중 활동 분석이 있으면 설정의 DB 전체 삭제를 거절한다.
- 기록 이동으로 자료가 없어진 활동은 모델을 호출하지 않는다. 이전 AI 종합이 있는 활동의 요약·상태·기간·역할을 비우고 idle로 바꾼다.

작업 큐는 한 백엔드 프로세스의 메모리에서 관리한다. 여러 서버 간 분산 잠금·영속 작업 큐는 구현하지 않았다. 이전 기록을 화면 진입만으로 일괄 재분석하지 않는다. 기존 활동은 새 자료 저장/수정 또는 상세의 수동 분석에서 갱신한다.

## 저장과 화면

기존 activities에 `metadata_status`, `metadata_fingerprint`, `metadata_error`, `metadata_model`, `metadata_updated_at` TEXT 열을 추가한다. 테이블은 추가하지 않으며 기존 DB의 데이터는 보존한다. 백엔드 시작 시 기존 마이그레이션 절차에서 열을 준비하므로 백엔드를 먼저 재시작한다. AI 서버도 새 라우터·프롬프트 반영을 위해 재시작한다.

요약·상태·역할·기간과 성공 상태·해시·모델·시각은 한 트랜잭션으로 갱신한다. 실패하면 기존 값들을 함께 보존한다. AI 메타정보 갱신 시 활동의 최근 기록 시각을 현재 서버 시각으로 덮어쓰지 않는다. Project Timeline 이벤트는 여기서 만들지 않는다. 활동 정보 변경으로 기존 Growth Journey 결과의 원본 해시는 달라질 수 있으며, 기존 수동 갱신 흐름을 유지한다.

홈 저장 카드와 활동 상세는 queued/running일 때만 1.5초 간격으로 상태를 조회한다. 발자국 목록도 진행 중인 활동이 있을 때만 재조회한다. 완료 알림으로 최근 목록·상세를 갱신한다. 상태 GET에는 모델 호출이 없다.

- 백엔드 35개 통과(Swagger 전용 4개 제외). 신규 9개는 자동 갱신·추가 기록 병합·오래된 결과 거절·실패 보존·수동 재시도·미확인 값 보존·기록 이동·원본 없는 활동 미호출·재시작·접수 실패 후 저장 성공 등을 확인했다.
- 프론트 서비스/세션 회귀 검사 통과. TypeScript 및 Vite 빌드를 직접 실행해 통과했다. npm의 Swagger 선행 생성은 실행하지 않았다. lint는 기존 경고 3개만 남는다.
- 검사 DB는 메모리 또는 임시 파일이다. 실제 공유 DB를 검사 목적으로 초기화하지 않았으며 이번 작업에서 유료 모델 분석·브라우저 직접 조작 검증은 하지 않았다.

다음 확인은 실제 신규 자료 저장 → 분석 상태 → 요약·상태·기간·역할 반영 → 추가 자료 저장 → 갱신 → 실패/재시도 순서다. 첫 자료의 명시적 날짜·역할과 근거가 없는 자료를 함께 확인한다.
