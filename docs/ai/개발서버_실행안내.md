# AI API 개발 서버

대화 수정(2026-11-06): 홈 모델은 일반/분석/활동 수정 응답을 구분한다. 역할·상태·기간·전체 요약 수정 명령은 실제 활동 ID와 요청 필드만 반환하고 백엔드가 직접 적용한다. 같은 대화의 최근 완료 요청 6개를 문맥으로 참고한다. 새 기록·정정 이력·확인 모달은 없다. [처리·검증](../frontend/chat/구현_기능/대화로_활동_정보_수정.md) 참고. 서버 재시작 후 적용한다.

활동 정보 자동 갱신(2026-11-06): 확정 저장 뒤 백엔드가 POST `/api/analyze/activities/{activity_id}`로 활동 전체 요약·상태·기간·역할을 요청한다. AI는 공유 DB를 읽고 근거 검증 결과만 반환하며 저장은 백엔드가 맡는다. `app/prompts/activity_metadata.md`를 사용한다. [기능·제한·검증](../frontend/footprints/활동_정보_AI_갱신.md)을 따른다. 백엔드 스키마 준비 후 AI 서버를 재시작한다. Swagger 갱신은 이번 범위에서 제외했다.

현재 모델 설정(2026-11-06): 로컬 `.env`와 `.env.example`은 `OPENAI_MODEL=gpt-5.4-mini`다. 홈·Journey의 공용 모델이며 서버 재시작 후 적용한다. 모델 메타정보 조회로 접근 권한을 확인했으나 경량 모델의 실제 분석 품질 검사는 아직 하지 않았다. 아래 `gpt-5.6-sol` 검증 기록은 이전 모델의 결과다. 파일 없는 텍스트는 `Prefer: respond-sync` POST 한 번에서 결과를 받고, 파일·링크는 비동기 접수·조회한다.

최신 홈 동작: 분석 시 신규 활동을 자동 생성하지 않는다. 일반 대화와 분석을 구분하고 새 활동은 사용자 확인 후 백엔드가 기록과 함께 생성한다. [응답 구분·확인 저장](../frontend/chat/구현_기능/홈_응답_구분_및_활동_확인_저장.md)을 참고한다. 홈 프롬프트·서버 코드를 갱신한 상태로 사용한다.

Growth Journey도 실제 분석으로 연결했다. GET `/api/journey/context`는 확정 기록만 조회하고 POST `/api/analyze/journey`는 `app/prompts/journey.md`로 실제 모델을 호출해 근거 검증 후 결과를 반환한다. 결과 DB 쓰기는 백엔드 POST `/api/journey/analyze`가 담당한다. [성장 분석 API](../frontend/journey/성장_분석_API.md)의 최신 절을 따른다. 검사: 루트에서 `node scripts/check-live-ai.mjs --journey`(임시 DB·실제 모델·추가 호출 비용).

다음 작업 진입점: [현재 작업 인수인계](../common/integration/현재_작업_인수인계.md). 실제 화면 시나리오 확인 단계이며 연결 오류·재전송 수정과 바탕화면 자료 위치를 포함한다.

프로젝트 최상위 `api-server/`와 같은 위치에서 관리하는 Python·FastAPI 기반 AI 개발 서버다. 실제 OpenAI API를 사용하여 입력 분석과 활동 매칭·신규 활동 생성을 수행한다.

현재 홈의 텍스트·파일·다중 파일·링크를 실제 OpenAI 분석으로 전환했고 신규 활동 생성·분석 초안·원본 보관·백엔드 기록 저장까지 연결했다. 최신 동작과 실행·검증은 [홈 실제 AI 연동](development/홈_실제_AI_연동.md)을 먼저 읽는다. 아래 `/api/analyze/text`는 저장하지 않는 별도 분석 진단 API다.

## 설치와 실행 — Windows PowerShell

프로젝트 루트에서 AI 서버 폴더로 이동한다. Python Install Manager에 Python 3.15가 설치된 환경을 기준으로 한다.

```powershell
cd ai-api-server
py -3.15 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

현재 PC에는 위 가상환경과 라이브러리를 준비했다. 다른 PC에서 처음 구성할 때 위 명령을 사용한다. `requirements.in`은 직접 의존성 목록이고 `requirements.txt`는 이번 Python 3.15.2 환경에서 검증한 전체 설치 버전이다. 의존성을 변경할 때는 설치·검사 후 고정 버전도 갱신한다.

`.env`가 없다면 예시를 복사한다. 기존 `.env`는 덮어쓰지 않는다.

```powershell
Copy-Item .env.example .env
```

실제 키와 모델 ID는 사용자가 `.env`에 직접 입력한다. 현재 사용자 설정의 `gpt-5.6-sol` 실제 호출을 확인했다. OS 환경변수가 `.env`보다 우선하며, `.env`는 실행 위치와 관계없이 AI 서버 폴더에서 읽는다. 설정 변경 후 서버를 재시작한다.

| 환경변수 | 기본값·의미 |
| --- | --- |
| OPENAI_API_KEY | 비어 있음. 서버용 키, 응답에는 값이 노출되지 않음 |
| OPENAI_MODEL | 현재 예시와 로컬 설정은 `gpt-5.4-mini`. 홈·Journey 공용 모델 |
| OPENAI_TIMEOUT_SECONDS | 45초. 1~120초 설정 가능, 자동 재시도 없음 |
| AI_CORS_ORIGINS | `http://localhost:5173,http://127.0.0.1:5173`. 허용 프론트 주소를 쉼표로 구분 |
| AI_DB_PATH | `../api-server/data/1line.db`. 상대 경로는 AI 서버 폴더 기준이며 백엔드가 사용하는 파일과 같아야 함 |
| AI_DB_TIMEOUT_SECONDS | 5초. SQLite 잠금 대기 시간, 0.1~30초 |

기본 DB 경로라면 `.env`에 DB 설정을 추가하지 않아도 된다. 다른 DB를 사용하는 경우 백엔드 `DB_PATH`와 AI 서버 `AI_DB_PATH`가 같은 실제 파일을 가리키도록 맞춘다. DB 생성·스키마 마이그레이션은 백엔드가 담당하므로, 처음 구성한 PC에서는 프로젝트 루트에서 `npm.cmd --prefix api-server run dev`를 먼저 실행한다. AI 서버는 없는 파일에 빈 DB를 생성하지 않는다.

서버를 실행한다. 가상환경 활성화나 PowerShell 실행 정책 변경은 필요 없다.

```powershell
.\dev.cmd
```

[dev.cmd](../../ai-api-server/dev.cmd)는 AI 서버 폴더로 이동한 뒤 가상환경의 Uvicorn을 실행한다. 기본 주소는 127.0.0.1:8000이며 app 폴더의 코드 변경 시 자동 재시작한다. 가상환경이 없으면 생성·설치 명령을 안내한다. 추가 Uvicorn 인자도 전달할 수 있다(예: `.\dev.cmd --help`). `.env` 설정을 변경하면 서버를 직접 재시작한다.

중지는 `Ctrl+C`다. 기본 프론트 프록시는 AI 8000, 백엔드 3001을 사용한다. 포트를 바꾸면 Vite 프록시나 VITE_AI_API_BASE_URL도 맞춘다. 백엔드를 재시작하여 ai_chat_jobs 스키마를 준비한 후 AI와 프론트를 실행한다.

- 상태 확인: http://127.0.0.1:8000/api/health
- DB 활동·기록 문맥 확인: http://127.0.0.1:8000/api/context (OpenAI 호출 없음)
- Swagger UI: http://127.0.0.1:8000/docs
- OpenAPI JSON: http://127.0.0.1:8000/openapi.json

연결 오류 진단: http://127.0.0.1:8000/api/chat/health?checkConnection=true . 실행 중인 AI 서버가 OpenAI에 HTTPS로 도달하는지만 검사하며 키를 전송하거나 모델을 호출하지 않는다. 키 없는 요청이므로 httpStatus 401도 connectionStatus=reachable이면 정상적인 네트워크 도달이다. 기본 ‘AI 분석 설정 준비됨’은 설정·DB 검사 결과이며 실제 모델 호출 성공 보장이 아니다. 자세한 오류와 재전송은 [연동 문서](development/홈_실제_AI_연동.md)의 연결 오류 진단을 따른다.

Swagger UI의 브라우저 렌더링은 외부 CDN 리소스 접근이 필요하다. `/openapi.json`은 서버 자체에서 제공한다. 프론트 `/swagger/`는 FastAPI 명세 스냅샷을 포함한다. 갱신 방법은 최신 연동 문서를 따른다.

## 상태 확인 응답

```json
{
  "status": "ok",
  "service": "ai-api-server",
  "database": { "status": "connected", "code": null },
  "openai": {
    "apiKeyConfigured": false,
    "modelConfigured": false,
    "connectionStatus": "not_checked"
  }
}
```

`status: ok`는 서버가 요청에 응답한다는 의미다. 키·모델이 없어도 200으로 응답한다. 설정 여부는 값 존재만 확인하며 키 유효성·모델 사용 가능 여부·실제 OpenAI 연결 성공을 보장하지 않는다. 상태 확인은 외부 요청이나 비용을 발생시키지 않고, 이전 분석의 연결 성공 상태도 보관하지 않는다.

database.status는 실제 연결·스키마 검사 결과다. DB가 없거나 접근하지 못하면 `unavailable`과 오류 코드를 반환한다. 이 경우에도 서버 자체 상태 확인은 200이며 DB 문맥 조회·DB 기반 분석은 503으로 실패한다.

## 실제 텍스트 분석

Swagger의 `POST /api/analyze/text`에서 아래 JSON을 실행한다. 실제 OpenAI 요청이 발생한다. 프론트 홈은 아직 이 API에 연결하지 않았다.

```json
{
  "input": { "kind": "text", "message": "1호선톤 회의록을 정리했습니다. 별도의 기획 변경은 없었습니다." }
}
```

`context` 생략/null이면 DB의 활동·확정 기록을 조회한다. 명시적으로 context를 전달하면 이전 합성 입력 검증처럼 요청 문맥만 사용한다. 응답의 contextSource는 database/request이며 DB 조회 개수·일부 조회 여부는 contextSelection으로 확인한다. 신규 활동 판단이 나와도 이번 단계에서는 생성하지 않고 activityPersisted/analysisPersisted는 false다. requestId를 백엔드 저장용 analysisId로 사용하면 안 된다.

상세 요청·응답·오류와 검증 범위는 [텍스트 분석 API](development/텍스트_분석_API.md)에 정리했다.

## 검증

AI 서버 폴더에서 실행한다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
```

검증 결과와 범위는 [기본 서버 구현 기록](development/기본_서버_구현.md)을 참고한다. 이번 HTTP 검증용 프로세스는 종료했으며 서버를 계속 사용하려면 위 실행 명령으로 시작한다.

실제 OpenAI 연결을 수동으로 다시 검증하려면 아래 명령을 사용한다. 합성 입력 1회가 전송되며 API 사용료가 발생할 수 있다. 일반 자동 검사에는 포함되지 않는다.

```powershell
.\.venv\Scripts\python.exe -m scripts.check_openai
```
