# 나의 발자국 검색 API

작성: 2026-11-04. 개발 서버에 검색·필터·정렬을 연결했다. 정식 백엔드 교체 시 `src/services/footprints.ts`의 요청/응답 변환을 교체하면 된다.

## 검색 범위

검색 결과는 활동 카드다. 다음 중 하나가 일치하면 해당 활동을 한 번 반환한다.

- 활동명과 저장된 활동 전체 요약
- 확정 기록에 속한 실제 파일명 또는 자료 이름
- 사용자가 입력하고 확정 저장한 글·URL
- 확정 기록에 저장된 AI 요약(현재는 목 분석일 수 있음)

미저장 초안은 포함하지 않는다. **PDF를 포함한 파일 원본 BLOB·파일 내부 본문은 조회·추출·검색하지 않는다.** 이미 DB에 저장된 이름·입력 글·요약만 비교한다. 파일에만 있는 문구는 검색 결과에 나타나지 않는다. 원본 파일은 수정하지 않는다.

검색어와 대상 문구의 NFC·영문 대소문자·앞뒤 및 연속 공백을 정규화하고 부분 문자열로 비교한다. `%`, `_` 등을 와일드카드로 해석하지 않는다. 활동 카드의 자료 수는 전체 확정 자료 수이며 일치한 자료 개수로 바꾸지 않는다.

## API 계약

```text
GET /api/archive/activities?q=회의록&category=all&status=all&sort=recent
```

| 조건 | 기본값·범위 |
| --- | --- |
| q | 빈 문자열, 최대 500자 |
| category | all 또는 활동 유형 문자열(최대 200자) |
| status | all / 진행 중 / 완료 |
| sort | recent / materials / oldest |

검색·유형·상태는 AND다. 정렬은 최근 업데이트 내림차순·자료 수 내림차순·업데이트 오래된 순이며 동률은 DB 활동 응답 순서를 유지한다. 알려진 시각이 없으면 최근순에서 뒤로 간다. 배열은 복사해 처리한다. 잘못된 조건·중복 쿼리·길이 초과는 400이다.

응답은 기존 배열에서 아래 객체로 확장했다. 쿼리 없이 호출해도 같은 계약이다.

```json
{ "items": [], "total": 5 }
```

items는 모든 조건과 정렬을 적용한 카드 배열이다. total은 **조건 적용 전 DB 활동 전체 개수**로, 일치한 개수는 items.length다. 현재 페이지네이션은 없다. total=0인 빈 목록과 total>0/items=[]인 조건 결과 없음을 구분한다. 카드 필드와 상세/Drawer ID는 기존과 같다.

## 프론트 연결

`searchFootprintActivities(filters, signal)`이 URLSearchParams로 조건을 인코딩하고 응답·총계를 검증한다. `getFootprintActivities()`는 기본 조건 조회 후 items를 반환하는 호환 함수다. 서버 검색 결과를 활동명/요약만으로 다시 필터링하지 않는다. 이전 `src/utils/footprints.ts`의 클라이언트 목록 필터는 제거하고 서버로 이동했다.

검색어 입력 변경만 250ms 대기하고 요청한다. 최초 진입·유형/상태 필터·정렬·재시도는 즉시 요청한다. 한글 조합 중 요청은 미루며 조건 변경·페이지 이탈 시 이전 요청과 타이머를 취소한다. 이전 응답은 생존 상태 검사로 무시한다. 로딩·오류·빈 목록·조건 결과 없음을 구분한다. 입력 힌트는 사용자 요청 문구를 유지하고 그 아래에 파일 내부 본문은 검색하지 않는다는 안내를 표시한다.

## 로딩 표시와 대기 시간 확인

최초 조회는 최소 높이 280px의 안내 카드에 큰 회전 아이콘과 ‘활동 목록을 불러오고 있어요.’를 표시한다. 성공한 목록이 있으면 검색·필터 재조회 중 기존 목록을 40%로 옅게 유지하고 그 위에 ‘조건에 맞는 활동을 찾고 있어요.’를 표시한다. 입력 대기 250ms 중에는 기존 목록을 유지하고 실제 요청이 시작될 때만 재조회 표시를 켠다.

재조회 중 이전 결과는 inert와 pointer-events로 키보드/마우스 이동을 막는다. 목록은 aria-busy, 안내는 그 바깥의 role=status를 사용한다. 모션 감소 설정에서는 회전하지 않는다. 실패는 오류와 ‘다시 불러오기’ 버튼을 표시한다. 로딩을 오래 보여주기 위한 추가 최소 시간은 넣지 않았다.

변경 전 로컬 읽기 전용 측정: 활동 5개·기록 5개·파일 9개의 검색 함수를 10회 호출한 평균 약 0.73ms(첫 호출 1.35ms), 실행 중 API 직접 조회 1회 약 30.69ms, Vite 프록시 경유 1회 약 21.56ms였다. 전체 조회에 붙어 있던 프론트 250ms 대기를 확인해 검색 입력에만 남겼다. 이 수치는 해당 측정 시점의 로컬 결과이며 브라우저 렌더링 시간이나 사용자가 느낀 전체 지연을 측정한 것은 아니다. 실제 사용자 DB는 읽기 전용으로만 열었고 값은 변경하지 않았다.

## 코드·검증

- `api-server/src/archive-search.js`: DB 메타정보 검색·조건·정렬.
- `api-server/src/validation.js`, `app.js`: 쿼리 검증·응답 계약.
- `src/services/footprints.ts`, `src/pages/Footprints.tsx`: 호출·취소·화면 상태.
- 서버 검색 HTTP 검사: 활동명/파일명/입력/요약·NFC/공백/대소문자, AND, 정렬, 전체 자료 수 보존, 빈 결과, 미저장 초안 제외, 잘못된 조건, PDF 원본 내부에만 있는 문구 미검색·원본 보존.
- 프론트 서비스→Vite→API→임시 DB 검사: 파일명/입력 검색, total과 빈 결과, 요청 취소.
- 순수 검색/정렬 검사는 `tests/footprints.test.mjs`에서 서버 함수를 검사한다. build/lint와 기존 아카이브·홈·채팅 검사를 함께 수행했다. 이번 검색 UI의 실제 브라우저·한글 조작 확인은 아직 수행하지 않았다.
- 로딩 후속 변경 뒤 build/lint 및 `node --test tests/footprints.test.mjs tests/footprint-file-timeline.test.mjs tests/recent-activity-time.test.mjs` 16개가 통과했다. 이는 화면의 회전·흐림·이동 차단·초점·한글 입력을 실제 브라우저에서 검사한 결과는 아니다. 다음 확인에서는 최초 즉시 요청, 검색어만 250ms 대기, 필터/정렬 즉시 요청, 취소된 이전 응답 무시, 실패 재시도와 목록 클릭 차단을 확인한다.
