작성일: 2026-11-14  
제안자: 백엔드 담당자(프론트 담당 겸임)  
수신: AI 담당자

> 통합 테스트의 공동 이슈 F19·F11을 아래 방식으로 해결하고자 합니다. 저는 백엔드의 원본 전달·검증·저장·삭제와 필요한 프론트 변경을 맡겠습니다. AI 파트에서는 남은 원본 분석, 파일 해시 계산·중복 조회, 제안한 형식의 결과 반환을 부탁드립니다. 구현상 제약이 있다면 해당 항목의 대안을 알려 주세요.

## 1. 범위와 현재 확인 사항

2026-11-13 「Growth AI 통합 테스트 결과 보고서」의 F19·F11을 대상으로 합니다. AI 단독 품질 개선과 프론트 일반 개선은 별도입니다.

- F19는 보고서와 로컬 코드에서 원인 경로를 확인했습니다. F11은 보고서상 원인 추정이므로 실제 AI 업로드 경로 확인이 필요합니다. 운영 AI 구현·배포 상태는 직접 확인하지 않았습니다.

## 3. F19 — 부분 삭제 재분석 정책 제안

### 현재 문제

현재 `POST /api/analyze/records/:recordId/exclude-file` 계약은 `reply.analysis.changes=[]`를 요구합니다. 로컬 `ArchiveDelete`도 비어 있지 않은 changes를 거절합니다. 이어서 `ApiController.syncEvents`가 해당 기록의 이벤트를 삭제하고 changes로 재생성하므로, 정상 처리해도 그 기록의 타임라인이 비게 됩니다.

따라서 AI가 changes만 반환하도록 고치는 것으로는 해결되지 않습니다. 백엔드 검증과 양쪽 계약을 함께 수정하겠습니다.

### 제안하는 처리 정책

1. 삭제 대상을 제외한 **같은 기록의 남은 원본**과 현재 활동만 모델 입력에 사용합니다. 다른 기록의 비교 문맥 확장은 이번 단계에서 제외합니다.
2. 남은 원본으로 입증할 수 있는 변화만 다시 생성합니다. 삭제 전 이벤트 수·ID의 유지까지 보장하지 않습니다.
3. 삭제 대상만 근거로 하는 변화는 제거합니다. 이전 타임라인을 무조건 복원하지 않습니다.
4. 재분석 성공과 검증 완료 후 파일 삭제·기록 교체·타임라인 갱신·Journey 무효화를 원자적으로 반영합니다.
5. 정상적으로 변화가 없으면 빈 changes를 허용합니다. 분석 실패·파싱 실패·누락을 빈 배열로 바꾸지 않습니다.
6. 실패·시간 초과·구버전 응답·근거 오류·동시 변경이면 삭제 전 데이터를 유지합니다.

제약: 남은 파일에 전후 비교 근거가 없으면 기존 변화가 사라질 수 있습니다. 다른 기록까지 비교해서 보존해야 하는 경우는 별도 문맥 확장이 필요합니다.

### 요청·응답 제안

경로와 기존 필드는 유지하고, 요청·응답 최상위에 `schemaVersion: "exclude-file-result-v2"`를 추가합니다. 새 필드는 현재 운영 API가 이미 지원한다는 뜻이 아닙니다.

요청 예시 — 식별자와 내용은 가상 예시입니다:

```json
{
  "schemaVersion": "exclude-file-result-v2",
  "fileId": "file-a",
  "recordReply": "{\"id\":\"reply-old\"}",
  "activity": { "id": "activity-1", "name": "테스트 활동", "category": null },
  "files": [
    { "id": "file-b", "name": "B.txt", "mimeType": "text/plain", "size": 11, "contentBase64": "YmVmb3JlOiAzMAo=" },
    { "id": "file-c", "name": "C.txt", "mimeType": "text/plain", "size": 9, "contentBase64": "YWZ0ZXI6IDgK" }
  ]
}
```

`recordReply` 예시는 문자열 전달 방식만 보여 줍니다. 실제 요청에서는 삭제 전 확정 reply JSON 원문 전체를 전달합니다. AI는 이를 모델 입력에 넣거나 재직렬화하지 않고 응답에 그대로 돌려줍니다. `fileIds`는 남은 files의 ID 순서를 유지합니다.

응답은 기존 `{reply, recordReply, fileIds}`에 아래 필드를 추가합니다. 다음 JSON은 **추가 필드와 기존 reply 안의 변화 부분을 설명하는 발췌**이며 완전한 성공 응답이 아닙니다. 실제 reply는 기존 필수 필드를 모두 유지합니다.

```json
{
  "schemaVersion": "exclude-file-result-v2",
  "reply": {
    "analysis": {
      "changes": [
        { "before": "측정값 30", "after": "측정값 8", "category": "효율성 개선", "evidence": ["B.txt", "C.txt"] }
      ]
    }
  },
  "recordReply": "{\"id\":\"reply-old\"}",
  "fileIds": ["file-b", "file-c"],
  "changeEvidence": [
    {
      "changeIndex": 0,
      "before": [{ "fileId": "file-b", "quote": "before: 30" }],
      "after": [{ "fileId": "file-c", "quote": "after: 8" }]
    }
  ]
}
```

| 필드 | 제안 규칙 |
| --- | --- |
| schemaVersion | 위 문자열과 정확히 일치. 누락·다른 값이면 결과 미적용 |
| reply.analysis.changes | 필수 배열, 최대 100개. 기존 변화 필드 형식 유지 |
| changeEvidence | 필수 배열. changes의 각 인덱스마다 정확히 한 항목. 중복·누락·범위 밖 인덱스 거절 |
| changeIndex | 0부터 시작하는 정수. changes와 연결 |
| before / after | 각각 1~20개 근거. 각 근거는 비어 있지 않은 fileId·quote. quote 최대 2000 코드 포인트 |
| fileId | 요청의 남은 files ID 중 하나. 같은 이름이어도 ID로 구분 |
| quote | 해당 원본 추출 본문의 실제 인용. 전후 주장을 각각 뒷받침. 근거 없는 비교는 생성하지 않음 |

정상 빈 결과는 `reply.analysis.changes: []`, `changeEvidence: []`를 **모두 명시**합니다. `sourceUrl` 금지, 남은 파일 이름·순서 일치, recordReply 원문 일치 등 기존 검증은 유지합니다.

인용 비교는 CRLF·CR을 LF로 통일한 뒤 연속 부분문자열로 검사하는 방식을 제안합니다. 그 외 공백·문장·숫자는 바꾸지 않습니다. TXT 외 형식은 AI의 추출기·버전을 문서화하고 동일 fixture로 검증합니다. 백엔드에서 독립적인 원문 추출 검증이 불가능한 형식은 검증 완료로 간주하지 않고, 동일 추출기/검증 방식 확보 후 적용합니다. AI가 보낸 인용문만으로 원본 검증을 대신하지 않습니다.

### 백엔드 담당 체크리스트

- [ ] 실제 남은 바이트·파일 ID·크기·순서 검증 및 전달.
- [ ] changes 비어 있음 강제 조건 제거, 새 버전·근거 스키마 검증 추가.
- [ ] 변화별 근거 ID 저장 및 상세 조회·자료 링크 반영. 파일명 기반 연결은 ID 기반으로 보완.
- [ ] 인용 검증을 위한 원문 추출 방식·fixture 마련.
- [ ] 반영 직전 스냅샷 충돌 검사와 원자적 데이터 반영 유지.
- [ ] 마지막 파일 삭제는 기존 정책 유지, AI 재분석 생략.
- [ ] 실패 시 파일·기록·타임라인 보존. AI/응답 실패는 공개 502, 반영 충돌은 409.

### AI 담당 체크리스트

- [ ] 요청 버전·원본·삭제 대상 제외 여부 확인.
- [ ] recordReply·삭제 원본·이전 대화를 모델 문맥에서 제외.
- [ ] 남은 원본의 변화와 전후 근거를 반환. 근거 없는 비교 생성 금지.
- [ ] 원문 추출기·정규화 규칙 문서화와 fixture 공유.
- [ ] 정상 빈 결과와 오류 분리. 읽기 불가능한 원본은 422, 모델 장애는 502로 오류 반환.
- [ ] 오류 응답은 `{ "code": "source_unreadable", "error": "남은 원본을 읽을 수 없어요." }` 형태 사용. 모델 장애 code는 `analysis_failed`, 미지원 버전은 HTTP 422·`unsupported_schema_version`.
- [ ] recordReply 원문과 fileIds 순서를 그대로 반환. 실제 삭제·확정 DB 수정은 수행하지 않음.

## 4. F11 — 동일 파일 중복 처리 정책 제안

### 제안하는 정책

- 원본 **바이트**의 SHA-256을 64자리 소문자 hex로 사용합니다. 파일명·base64 문자열·요약을 해시하지 않습니다.
- 같은 사용자/접근 범위의 **같은 활동** 안에서만 중복 저장을 차단합니다. 다른 활동에 같은 파일을 저장하는 것은 허용합니다.
- 활동 미확정 상태는 `pending`으로 표시합니다. 다른 활동의 일치 자료는 참고 정보이며 곧바로 중복으로 확정하지 않습니다.
- 파일을 제외한 신규 텍스트는 별도로 분석합니다. 중복 파일만을 새 변화 근거로 만들지 않습니다.
- 중복+신규 혼합 요청은 **부분 저장하지 않고 전체 저장을 거절**합니다. 프론트에서 중복 파일을 빼고 신규 자료만 다시 보내도록 안내합니다. 이번 단계에서는 자동 자료 연결·기존 reply 부분 재작성은 구현하지 않습니다.
- 같은 요청 안에 동일 해시 파일이 반복된 경우도 저장 전 거절합니다. 다른 이름이어도 동일합니다.
- requestId 기반 요청 재전송 방지는 별개로 유지합니다. 이미 저장된 같은 확정 요청을 재전송하면 기존 성공 결과를 반환하고 새 중복 오류로 바꾸지 않습니다.

### 백엔드에서 제공할 내부 조회 API 제안

`POST /api/internal/file-duplicates/check` — **신규 제안 API**입니다. 기존 서버 간 Bearer 인증과 데이터 접근 범위를 유지합니다. 브라우저에서 호출하지 않습니다.

요청:

```json
{
  "schemaVersion": "file-dedup-v1",
  "activityId": "activity-1",
  "files": [
    { "inputIndex": 0, "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef", "size": 1024 }
  ]
}
```

`activityId`는 필수 키이며 비어 있지 않은 ID 또는 null입니다. null이면 허용 범위의 기존 자료에서 일치 항목을 조회하되 판정은 pending입니다. files는 1~10개, inputIndex는 원본 업로드 순서의 고유한 0~9 정수, size는 1~10MiB 정수입니다. 일치 판정은 SHA-256과 크기를 사용합니다. 요청의 사용자 ID로 접근 범위를 임의 변경하지 않습니다.

성공 응답 예시:

```json
{
  "schemaVersion": "file-dedup-v1",
  "activityId": "activity-1",
  "files": [
    {
      "inputIndex": 0,
      "status": "duplicate",
      "matches": [{ "activityId": "activity-1", "recordId": "record-1", "fileId": "file-old" }]
    }
  ]
}
```

- 응답은 요청의 각 inputIndex에 정확히 한 항목을 같은 순서로 반환합니다.
- activityId가 있으면 `duplicate` 또는 `new`, null이면 `pending`을 반환합니다.
- matches는 파일별 최대 20개입니다. 정렬은 activityId·recordId·fileId 오름차순. 최대 개수를 넘으면 결과를 잘라 반환하지 않고 HTTP 422·`duplicate_lookup_limit`로 실패합니다.
- `new`는 matches가 빈 배열이고, `duplicate`는 같은 대상 활동의 matches가 1개 이상입니다. pending은 matches 유무와 관계없이 활동 확정 전임을 의미합니다.
- 400은 입력 오류, 401/403은 인증·접근 오류, 404는 지정 활동 없음, 422는 버전/조회 한도 오류입니다. 원본 해시 계산·조회 장애는 HTTP 503·`duplicate_lookup_unavailable`로 반환합니다. 실패를 new로 대체하지 않습니다.
- 기존 홈 문맥의 활동/기록 개수 제한 때문에 자료가 누락되지 않도록 별도 해시 조회를 사용합니다. 기존 파일은 실제 원본에서 해시를 계산·보완합니다.

### AI 결과 게시·공개 응답 확장 제안

AI가 분석 후 결정한 대상 활동을 기준으로 내부 조회를 수행합니다. 활동이 바뀌면 다시 조회하며, 사용자 최종 선택은 백엔드가 저장 시 재검사합니다.

작업 게시의 reply와 공개 reply에 선택 필드 `deduplication`을 추가합니다. v1 기능으로 파일을 분석한 결과에서는 필수이며, 텍스트 전용 응답에는 넣지 않습니다. 내부 작업 게시 및 백엔드/프론트 reply 검증 스키마도 함께 확장해야 합니다.

```json
{
  "deduplication": {
    "schemaVersion": "file-dedup-v1",
    "activityId": "activity-1",
    "files": [
      { "inputIndex": 0, "status": "duplicate", "matches": [{ "activityId": "activity-1", "recordId": "record-1", "fileId": "file-old" }] }
    ],
    "saveBlocked": true
  }
}
```

이 JSON은 reply에 추가하는 필드만 나타냅니다. 기존 reply 필수 필드는 유지합니다. 해시는 내부 요청에서만 사용하고 공개 reply에는 넣지 않습니다. 파일별 inputIndex는 저장 원본 및 reply.analysis.files의 업로드 순서와 대응시킵니다. 표시 이름으로 연결하지 않습니다.

- 전체 중복: 새 changes는 빈 배열, 기존 자료 안내, saveBlocked=true.
- 일부 중복: 신규 파일·텍스트만의 분석은 가능하지만 saveBlocked=true. 신규 자료만 다시 보내도록 안내합니다.
- 대상 활동 미확정: pending, 중복 없음으로 단정하지 않음. saveBlocked는 확인된 duplicate 또는 요청 내 동일 바이트 반복이 있으면 true, 그 외 false입니다. false도 저장 가능 보장이 아니며 백엔드가 최종 검사합니다.
- 요청 내 동일 바이트 반복은 AI가 먼저 감지합니다. 후속 항목에 선택 필드 `duplicateOfInputIndex`로 최초 항목을 참조하고 status=duplicate, matches=[]를 허용합니다. 최초 항목은 기존 자료 조회 결과를 유지합니다.
- 같은 파일에 신규 텍스트가 있어도 파일 포함 저장은 차단합니다. 텍스트만 다시 보내거나 파일을 제거해 재분석하도록 안내하며 신규 텍스트를 임의 폐기하지 않습니다.
- 내부 조회 실패: 성공 reply를 만들지 않고 작업을 실패 처리합니다. 작업 재조회 정본·revision 규칙을 유지합니다.

### 저장 시 최종 판정 제안

백엔드는 AI 플래그만 신뢰하지 않고, 확정 활동과 보관 원본으로 트랜잭션/동시성 제어 안에서 다시 검사합니다. 기존 파일이나 요청 안에서 중복이 발견되면 전체 요청을 HTTP 409로 거절합니다. 새 활동 생성까지 포함해 변경을 되돌리고 원본 초안은 기존 보관 정책에 따라 유지합니다.

```json
{
  "code": "duplicate_files",
  "error": "이미 저장되었거나 중복 첨부된 자료가 있어요. 중복 파일을 제외하고 다시 보내 주세요.",
  "duplicates": [
    { "inputIndex": 0, "matches": [{ "activityId": "activity-1", "recordId": "record-1", "fileId": "file-old" }] }
  ]
}
```

요청 내 반복 파일만 해당하면 matches=[]와 duplicateOfInputIndex를 사용합니다. 프론트는 이 구조로 중복 항목을 안내합니다. 저장 재시도·동시 저장을 검사하고, 원본 바이트 일치 확인과 직렬화된 저장 또는 동일한 효과의 잠금으로 중복 삽입을 막습니다. 경고만 띄우고 저장하는 방식은 이번 제안에 포함하지 않습니다.
