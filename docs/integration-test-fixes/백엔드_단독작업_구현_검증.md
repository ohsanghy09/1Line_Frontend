# 백엔드 단독 작업 구현·검증

작성일: 2026-11-14  
범위: BE-01(F20), BE-02(F22), BE-03(AI 호출 로그)  
상태: 로컬 구현·검증. 실제 AI·운영 DB·EC2 배포 확인은 별도.

## F20 — 삭제 후 활동 정보 처리

- 같은 활동에 기록이 남아 있으면 상태·역할·시작일·종료일·기간을 일괄 NULL 처리하지 않는다.
- 활동 요약과 분석 스냅샷은 무효화하고, 보존한 속성은 새 DB 열 `activities.metadata_review_fields`에 재확인 대상으로 기록한다.
- 상태 조회의 기존 `stale`·`error`로 삭제 전 정보를 임시 보존 중임을 안내한다. 응답 필드는 추가하지 않았다.
- 새 AI 응답에서 원문 근거 검증을 통과한 항목만 재확인을 해제한다. null 응답으로 기존 값을 지우거나 새로 확인된 값으로 취급하지 않는다.
- 사용자가 대화로 명시적으로 수정한 필드는 해당 항목의 재확인을 해제한다. 수정하지 않은 반대쪽 날짜 등은 별도로 남긴다.
- 마지막 기록이 삭제되면 활동 요약·상태·역할·기간과 재확인 표시를 모두 비운다.
- 삭제 재분석 자체가 실패하면 삭제 전 데이터를 보존한다. 삭제 성공 뒤 후속 활동 분석이 실패하면 삭제는 유지하고 임시 속성과 실패 상태를 남긴다.

기존 DB에는 필드별 출처 이력이 없으므로 삭제한 자료에만 있던 값과 사용자 입력값을 완벽하게 자동 구분하지 않는다. 보존값을 확정 정보로 표시하지 않도록 재확인 상태를 유지하는 범위다. 향후 자료 저장의 자동 분석이 사용자 수정값을 갱신할 수 있는 기존 동작은 유지하며, 영구 사용자 잠금은 추가하지 않았다.

F19의 `changes=[]` 규칙과 타임라인 재생성은 이번에 변경하지 않았다. 새 변화 반환 계약은 AI 공동 작업이다.

## F22 — 미저장 원본 정리

기본 정책은 **마지막 실제 갱신 후 24시간 보관, 5분마다 최대 25개 분석 정리**다. 원본 파일이 있는 미저장 분석만 대상으로 하며 텍스트 대화 전체를 정리하지 않는다.

| 설정 | 기본값 | 용도 |
| --- | --- | --- |
| `UNSAVED_ANALYSIS_RETENTION_MS` | 86400000 | 환경변수로 보관 기간 지정. 양수 밀리초 |
| `oneline.unsaved-retention-ms` | 환경변수 또는 86400000 | Spring 속성으로 지정 시 환경변수보다 우선 적용 |
| `oneline.unsaved-cleanup-interval-ms` | 300000 | 정리 주기. 양수 밀리초 |

- `analysis_retention`에 백엔드 수신/갱신 시각을 저장한다. AI의 createdAt/updatedAt을 정리 기준으로 신뢰하지 않는다.
- 기동 시 기존 분석에는 첫 도입 시점부터 보관 기간을 부여한다. 기존 보관 시각은 재시작으로 초기화하지 않는다.
- 접수·진행·완료·실패의 실제 갱신, 만료·재시작 복구 시 보관 시각을 갱신한다. 단순 조회·동일 게시 재전송은 기간을 연장하지 않는다.
- 미종료 AI 작업, 구형 작업의 완료 대기 중 원본, 정식 records에 연결된 분석은 보호한다.
- 저장 요청과 같은 EventLoop·DB 트랜잭션에서 대상 판정과 삭제를 수행한다. 단일 연결·단일 인스턴스 기준이며 다중 인스턴스 검증은 별도다.
- 파일 BLOB·미저장 분석·관련 작업을 함께 정리한다. 작업 ID 해시 tombstone으로 늦은 재게시를 차단한다.
- 정리 후 과거 초안 저장·작업 재조회는 404, 퇴역 작업 재게시는 409다. 새 요청으로 다시 분석해야 한다.
- DB 실패 시 삭제를 롤백하고 다음 주기에 재시도한다.

BLOB 삭제 공간은 이후 쓰기에서 재사용된다. DB 파일을 즉시 축소하는 VACUUM은 자동 실행하지 않는다. tombstone에는 원본·토큰 대신 해시만 남지만 tombstone 자체의 장기 보관 정책은 별도다.

## AI 호출 로그

남은 원본·활동 정보·Journey 분석에 다음 형태의 완료 로그를 기록한다.

```text
AI call operation=exclude_file request_id=... target_ref=... http_status=200 outcome=applied duration_ms=...
```

- operation: `exclude_file`, `activity_metadata`, `journey`.
- request_id: 백엔드 로그 추적용 UUID. AI와 공유하는 새 요청 ID를 정의한 것은 아니다.
- target_ref: 기록/활동 ID 또는 Journey 스냅샷 해시의 UTF-8 SHA-256 앞 16자리. 원본 문자열은 남기지 않는다.
- outcome: `applied`, `http_error`, `timeout`, `cancelled`, `connection_failed`, `validation_or_apply_failed`, `not_sent_or_transport_failed`.
- HTTP 200도 검증·DB 반영에 실패하면 applied로 기록하지 않는다.
- 성공 INFO, 실패 WARN. 토큰·URL·본문·파일명·AI 오류 원문·예외 본문은 기록하지 않는다.
- 파일 정리는 분석 수와 보관 시간만 집계 로그로 남긴다.

## 검증·서버 전달

최종 결과: 백엔드 테스트 69개(실패·오류 0), 실행 JAR bootJar 빌드 통과. 프론트 테스트 63개와 채팅 세션 검사도 통과했다. 커밋·푸시·배포는 수행하지 않았다.

JDK 21과 기존 Gradle 캐시, 임시 DB·가짜 AI 서버를 사용한다. 실제 운영 데이터나 유료 모델은 사용하지 않는다.

- 부분 삭제 후 임시 보존, 마지막 기록 삭제 시 초기화.
- AI null·실패 응답 후 보존, 새 근거 확인, 사용자 수정 필드별 해제.
- 미저장 실패/완료 정리, 진행 중·정식 저장·보관 기간 보호.
- 구형 데이터 유예, 재시작 시각 보존, 저장/정리 순서, DB 실패 롤백.
- 스케줄러 실행, 정리 후 늦은 게시 거절, 재전송 시 보관 기간 불변.
- 로그의 HTTP/반영 결과 구분 및 민감정보 비노출.

최종 결과는 [작업 계획](README.md)에 기록한다. 서버 적용 시 DB 백업·설정 확인 후 재배포하고 실제 AI 응답과 보관·정리 상태를 확인한다. busy_timeout=0과 F19·F11 공동 계약은 그대로 유지한다.
