# 공동 작업 백엔드 연동 안내

작성일: 2026-11-14  
기준: [공동 책임 범위 제안서](통합테스트_공동작업_책임범위.md)  
상태: 사용자 확인에 따라 제안서 v1 기준으로 백엔드·관련 프론트를 구현했다. AI 구현·배포 완료나 실제 연결 성공을 의미하지 않는다.

## AI 담당자에게 전달할 자료

- [완전한 요청·응답·작업 게시 예시](examples/joint-file-exchange.json)
- [AI OpenAPI](../frontend-integration/openapi/ai.openapi.json)
- [백엔드 OpenAPI](../frontend-integration/openapi/backend.openapi.json)

기존 공유 Bearer 토큰·내부 API Base를 사용한다. 새 토큰이나 사용자 ID 필드를 추가하지 않았다. 현재 서비스는 기존 단일 데이터셋 범위이며 다중 사용자 격리를 새로 구현한 것은 아니다. 요청의 userId 등 임의 범위 필드는 거절한다.

## F19 — 남은 원본 재분석

기존 경로 `POST /api/analyze/records/:recordId/exclude-file`을 유지한다.

- 요청·응답의 schemaVersion은 `exclude-file-result-v2`다.
- 요청에는 삭제 대상 ID, recordReply 원문, 현재 활동, 삭제 대상을 제외한 남은 원본이 포함된다.
- 응답은 `schemaVersion, reply, recordReply, fileIds, changeEvidence`를 모두 포함한다.
- changes의 각 항목은 정확히 한 changeIndex와 연결되고, before/after에 각각 1~20개 fileId·quote 근거가 필요하다. quote는 최대 2000 코드 포인트다.
- 정상 변화 없음은 changes=[]와 changeEvidence=[]를 모두 명시한다. 구버전·누락·틀린 근거를 정상 빈 결과로 바꾸지 않는다.
- recordReply는 원문 문자열 그대로 반환하고 모델 문맥에 포함하지 않는다. fileIds와 reply.analysis.files 이름은 남은 원본 순서와 일치해야 한다.
- sourceUrl과 이전 업로드의 deduplication을 응답에 넣지 않는다. 삭제로 파일 순서·범위가 바뀌었으므로 이전 중복 판정을 재사용하지 않는다.

백엔드는 남은 파일의 근거 ID·실제 인용을 검증하고, 삭제·기록 교체·이벤트 및 근거 저장·Journey 무효화를 같은 트랜잭션에서 반영한다. 응답 대기 중 원본 바이트가 바뀐 경우에도 409로 거절한다. 실패 시 삭제 전 데이터를 유지한다.

이벤트 조회에는 선택 필드 `changeEvidence: {before, after}`를 추가했다. evidenceFileIds는 저장한 근거 ID에서 만들며 이름이 같은 파일도 구분한다. 프론트 자료 상세에서 원문 인용을 펼쳐 볼 수 있다. 구형 이벤트는 기존 이름 기반 연결을 유지한다.

### 원문 검증의 현재 지원 범위

현재 독립 검증기는 **UTF-8 원문 텍스트**의 txt/md/json/csv/tsv/xml/html/py/js/ts를 지원한다. JSON·HTML을 별도로 파싱해 재구성하지 않고 원문 문자열 그대로 비교한다. CRLF·CR만 LF로 통일하며 공백·문장·숫자·유니코드 정규화는 추가하지 않는다.

**PDF·Office·이미지·UTF-8이 아닌 인코딩은 추출기·버전·정규화 fixture가 필요하므로 현재 부분 삭제를 502로 거절하고 원본을 보존한다.** 변화가 빈 경우도 미지원 형식을 성공으로 간주하지 않는다. 해당 형식의 일반 업로드·저장, 마지막 자료 삭제·활동 전체 삭제까지 차단하는 것은 아니다.

AI 파트의 추출 방식과 실제 fixture가 준비되면 동일한 독립 검증을 추가해야 한다. 이 범위가 남아 있으므로 F19의 전체 파일 형식 지원은 완료로 표시하지 않는다.

## F11 — 중복 조회와 저장

### 내부 조회

`POST /api/internal/file-duplicates/check`

- schemaVersion은 `file-dedup-v1`이다.
- activityId는 ID 또는 null이며, files는 1~10개다. 파일별 inputIndex(0~9, 고유), 원본 바이트 SHA-256(소문자 hex 64자리), size(1~10MiB)를 보낸다.
- 응답은 동일한 inputIndex 순서로 반환한다. 대상 활동이 정해졌으면 new/duplicate, 미확정이면 pending이다.
- matches는 activityId·recordId·fileId로 구성되며 활동/기록/파일 ID 순으로 정렬한다. 파일별 20개 초과는 422 duplicate_lookup_limit으로 실패한다.
- 같은 활동의 확정 자료만 중복 차단 대상으로 본다. activityId=null의 다른 활동 일치는 참고 정보다.
- 요청 오류 400, 인증·접근 오류 401/403, 활동 없음 404, 버전/한도 오류 422, 원본 무결성·조회 실패 503이다. 실패를 new로 해석하지 않는다.
- Cache-Control: no-store를 사용한다. 원본·해시를 공개 reply로 복사하지 않는다.

### AI 게시·재조회

파일 분석의 reply에 선택 필드 deduplication을 확장했다. FILE_DEDUP_ENABLED=true이면 파일이 있는 completed 게시에서 필수다. 텍스트 전용·general 응답에는 넣지 않는다.

- files는 원본 업로드 전체 순서를 0부터 빠짐없이 포함한다.
- saveBlocked는 duplicate가 하나라도 있으면 true다.
- 요청 안의 반복 첨부는 후속 항목에 duplicateOfInputIndex로 앞선 동일 바이트 파일을 참조한다. 이 경우 matches=[]이며 백엔드도 바이트 일치를 검증한다.
- 대상 활동의 기존 파일 중복은 matches를 제공한다. 미확정 활동은 pending으로 두고 최종 저장 대상은 백엔드가 다시 검사한다.
- 중복 파일 자체를 새 변화로 만들지 않는다. 일부 중복·신규 혼합은 신규분만 분석할 수 있지만 전체 저장은 차단한다.
- 내부 게시·정본 재조회·공개 reply·프론트 세션 검증에서 같은 구조를 유지한다.

### 확정 저장

백엔드는 AI 플래그나 전달 해시를 신뢰하지 않고 보관 원본의 해시로 재검사한다. 기존 파일 해시는 별도 file_hashes에 관리하며, 원본 content/size가 바뀌면 DB 트리거가 캐시를 무효화한다. 기존 files 테이블의 열 수는 바꾸지 않았다.

- 같은 활동의 동일 바이트·동일 요청 안의 반복 첨부는 HTTP 409 duplicate_files로 전체 롤백한다. 새 활동 생성·신규 자료·타임라인도 부분 반영하지 않는다.
- 같은 이름·다른 바이트는 허용하고, 다른 활동의 같은 바이트 재사용도 허용한다.
- 저장 또는 활동 이동 시 재검사한다. 두 저장이 동시에 도착해도 직렬 처리와 트랜잭션으로 중복 삽입을 막는다.
- 기능 활성화 후 새로 저장한 analysisId의 동일한 저장 요청은 200으로 기존 기록을 반환한다. 다른 선택은 409다. 기존 데이터에 저장 요청 서명이 없으면 과거처럼 이미 저장됨 409를 유지한다.
- 프론트는 중복 판정 시 저장을 차단하고 신규 자료 재전송을 안내한다. 다른 활동으로 선택을 바꾸면 이전 판정을 저장 허가/거절로 재사용하지 않고 백엔드에서 재검사한다.

## 배포 전환

| 환경변수 | 기본값 | 효과 |
| --- | --- | --- |
| EXCLUDE_FILE_V2_ENABLED | false | true면 v2 재분석. false면 여러 원본이 있는 기록의 부분 삭제를 AI 호출 전에 503으로 거절 |
| FILE_DEDUP_ENABLED | false | true면 파일 완료 게시의 deduplication 필수, 저장·이동 중복 검사와 저장 재시도 처리 활성화 |

Spring 속성 oneline.exclude-file-v2-enabled / oneline.file-dedup-enabled로도 지정할 수 있다. 내부 중복 조회 API는 인증 후 사용할 수 있으며 별도 활성화를 요구하지 않는다.

1. AI 담당자가 이 문서·완전한 JSON 예시로 수신·반환·게시를 맞춘다.
2. 준비 환경에서 양쪽 구현을 연결한다. 운영 전환 전 진행 중인 구버전 작업을 마무리하고 새 기능의 계약이 준비됐는지 확인한다.
3. 프론트가 새 응답을 처리하는 버전을 배포하고 서버 담당자가 설정을 켠 뒤 재시작한다.
4. 정상·빈 결과·거절·실패·동시 변경과 지원 파일 형식을 실제 AI로 검증한다.

구버전 응답으로 조용히 되돌리는 동작은 없다. 실제 AI 연동·PDF 등 추출기 검증이 남아 있으므로 코드 구현과 운영 완료를 구분한다. 운영 서버 설정·재배포·실제 모델 호출은 이번 로컬 작업에서 수행하지 않았다.

## 로컬 검증

백엔드 전체 80개 통과 후 최종 활동 범위 조정은 공동 검사 11개로 재검증했다. 프론트 67개·채팅 세션 검사·빌드·린트와 실행 JAR 빌드가 통과했다. 실제 AI 호출·운영 배포는 하지 않았다.

AI 대역·임시 DB로 변화·파일 ID 근거 보존, 버전/인용/동시 변경 거절, DB 실패 롤백, 중복 조회·해시 캐시 무효화·한도·인증, 혼합 업로드·새 활동 롤백·동시 저장·재시도, deduplication 게시·재조회와 공유 JSON을 검사한다. 프론트는 손상 응답 거절·중복 안내·다른 활동 선택·원문 인용 데이터 보존을 회귀 검사한다.

최종 검사 결과와 남은 작업은 [작업 계획](README.md)에 기록한다. 커밋·푸시·실제 배포는 별도다.
