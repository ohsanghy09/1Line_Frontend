# 상태와 오류 처리

기준일: 2026-11-06. [공통 계약](공통_데이터_계약.md) · [검증 시나리오](../integration/handoff/연동_검증_시나리오.md)

## 오류 형식과 시간 제한

백엔드 오류는 `{error:string}`이다. 입력 검증 실패는 400, 없는 대상 404, 충돌 409, 처리 불가 422, 연결/공급자 502·503, 시간 초과 504를 사용한다. 일반 500 오류 원문은 사용자 응답에서 숨긴다. 기존 공개 백엔드 JSON 요청의 한도는 1MiB다. 이는 파일 multipart나 base64 원본을 담는 새 내부 전달 요청의 한도가 아니다. 내부 전송 제한은 별도로 설정한다.

AI 도메인 오류는 `{error:string,code:string}`이다. 기존 API에는 요청 검증 오류가 422 `{detail:[...]}`로 반환되는 경우도 있었다. 새 구현은 가능한 한 `{error,code}`로 통일하고 도메인/검증 상태 코드와 프론트 오류 처리를 확인한다. 특정 프레임워크의 기본 예외 형식을 그대로 요구하지 않는다. 현재 프론트는 error 문자열이 없으면 일반 오류를 표시하고 status만 별도 보존한다. AI 작업 접수 후 분석 실패는 HTTP 200/202의 `status:failed` envelope일 수 있으므로 HTTP 성공만으로 분석 성공 처리하지 않는다.

| 경계 | 제한·처리 |
| --- | --- |
| 일반 프론트 HTTP | 30000ms. 시간 초과 뒤 서버 처리 여부가 불명확하므로 확인 후 재요청 안내 |
| 동기 텍스트 POST | 150000ms. 완료까지 대기, 파일 없는 텍스트에만 respond-sync 사용 |
| 파일·링크 작업 조회 | 400ms 순차 요청, 전체 120000ms. 시간 초과 시 jobId 유지·작업 재조회 가능 |
| 활동 상태 UI 조회 | queued/running 동안 1500ms. 상태 GET은 모델 호출 안 함 |
| Journey | 프론트 145000ms, 백엔드→AI 135000ms |
| 자료 삭제 | 프론트 165000ms, 남은 파일 분석 서버 호출 150000ms |
| 활동 종합 서버 호출 | 150000ms. UI 재시도 POST는 일반 HTTP 제한 |
| 실제 모델 | 기본 45초, 설정 범위 1~120초. 자동 재시도 0회, 모델 검증 실패 시 자동 재호출 없음 |

사용자가 화면을 떠나거나 조회를 취소해도 이미 접수된 서버 작업이 취소되는 계약은 없다. ‘대화 초기화’도 서버 취소 API를 부르지 않는다.

## 홈 상태

DB는 queued→running→completed 또는 failed. 응답은 queued도 running으로 표시한다. phase는 preparing/analyzing/persisting이며 미래 단계를 가짜 완료로 표시하지 않는다. 재시작 시 진행 중 작업은 failed/server_restarted로 바뀐다. 기존 개발환경의 홈 동시 모델 실행 수는 2개였다. 새 서버는 처리량에 맞춰 설정하되 진행 상태·기한·중복 방지 계약을 지킨다.

확정 실패(status=failed, 또는 활동 수정 적용 400/404/409/422)는 pendingJob을 해제한다. 네트워크 실패·시간 초과는 작업 ID가 있으면 유지하고 ‘진행 상태 다시 확인’으로 복구한다. ID를 받기 전 중단된 요청은 자동 재전송하지 않는다. 같은 analysisId/id의 완료 카드는 중복 추가하지 않는다.

동일 requestId·동일 fingerprint는 기존 작업을 반환한다. 현재 서비스는 사용자가 새로 보내면 새 requestId를 만든다. 따라서 사용자의 재전송 전체가 영구적으로 멱등하다고 가정하지 않는다. 확정 저장은 analysis_id UNIQUE와 사전 확인으로 중복을 막고 409를 반환한다.

## 활동 정보 상태

idle/queued/running/ready/failed와 stale을 분리한다. 기록 저장 성공 뒤 종합 실패가 발생해도 기록 저장을 실패로 되돌리지 않는다. 이전 정보는 유지하며 동일 입력을 무한 자동 재호출하지 않는다. 실행 중 새 저장이 발생하면 dirty를 표시하고 최신 입력으로 후속 분석을 예약할 수 있다. 직접 대화 수정은 기존 큐를 취소하고 이후 자료 저장의 자동 종합은 허용한다. 재시작 당시 queued/running은 failed로 바꾼다.

## Journey 상태

journey-v5에서 AI 내부 근거 선택/연결 검증 실패는 502 journey_evidence_invalid이며 오류 메시지의 진단 ID로 안전한 서버 로그의 reason/location을 찾는다. 백엔드 공개 응답은 기존 {error}를 유지한다. 근거 후보 2000개 또는 실제 모델 문맥 250000자 초과는 호출 전 422 journey_context_limit, 후보 없음은 422 journey_evidence_missing이다. 실패를 가짜 성공이나 자동 모델 재시도로 숨기지 않는다. 카탈로그와 모델 스키마·프롬프트는 함께 배포한다.

GET은 마지막 결과와 현재 fingerprint를 비교해 stale을 계산한다. 결과 없음과 이벤트 없음은 별개다. 분석 실패는 이전 결과를 유지하며 UI는 ‘마지막으로 저장된 분석’임을 알린다. 통신 실패 시 모델을 다시 부르지 않고 GET으로 확인한다. 분석 중 기록이 바뀌면 저장 직전 409로 거절한다. 동일 범위의 동시 분석은 409로 거절한다. 잠금의 구현 방식은 자유지만 여러 인스턴스에서 공유돼야 한다.

## 삭제 충돌과 원자성

활동/자료 삭제는 queued/running 홈 작업이 있으면 409다. 같은 기록의 자료 삭제가 진행 중이면 409를 반환하며 잠금 저장 방식은 자유다. 삭제 전 재분석 중 활동 입력이 바뀌면 fingerprint 불일치로 409, 실제 삭제는 하지 않는다. 전체 삭제는 홈·Journey·활동 종합이 진행 중이면 거절한다. 상세 범위는 [저장·삭제 규칙](../../backend/handoff/저장과_삭제_규칙.md)을 따른다.

브라우저 URL에 남은 이전 활동 ID의 404는 삭제·없는 대상 상태다. Journey 분류 검증 실패와 같은 원인이라고 단정하지 않는다. 이전 요청 ID가 어디에서 유래했는지는 확인된 근거 없이 세션 스토리지 탓으로 기록하지 않는다.
