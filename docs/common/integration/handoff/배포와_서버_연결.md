# 배포와 서버 연결

기준일: 2026-11-06. [구현 환경](../../handoff/개발환경과_구현_범위.md) · [서버 간 계약](../../handoff/서버간_데이터_전달_계약.md) · [검증](연동_검증_시나리오.md)

## 전달받는 대상

서버 실행 코드나 로컬 DB 없이 이 문서 묶음만 제공한다. 각 파트는 선택한 환경에서 서버를 새로 구현하고 자신의 설치·실행·마이그레이션·배포 안내를 제공한다. 작성자의 Windows 명령·가상환경·로컬 경로·포트를 따라야 한다는 요구는 없다.

프론트 배포 주소는 https://1-line-frontend.vercel.app/ 이다. 이 주소에서 백엔드·AI 운영 연결을 검증했다는 의미는 아니다. 프론트 배포 설정 변경은 프론트 담당자가 수행한다.

## Base URL과 프론트 설정

| 연결 | 주소 규칙 | 예시 |
| --- | --- | --- |
| 브라우저 → 백엔드 | 정의서의 /activities 등을 덧붙일 Base. /api까지 포함 | https://backend.example.org/api |
| 브라우저 → AI | 정의서의 /chat 등을 덧붙일 Base. /api까지 포함 | https://ai.example.org/api |
| 백엔드 → AI | 브라우저와 별개의 내부 연결 가능. 전체 분석 경로를 전달 | POST https://ai-internal.example.org/api/analyze/journey |
| 서버 간 문맥/초안 | 공개 프론트 API와 분리된 보호 경계 | 전달 계약의 작업을 자체 내부 API 또는 동등한 전송으로 구현 |

프론트의 현재 설정 이름은 VITE_API_BASE_URL(백엔드), VITE_AI_API_BASE_URL(AI)다. 이는 프론트 담당자가 설정한다. 백엔드·AI가 같은 환경변수 이름을 써야 하는 것은 아니다. Base에 /api를 두 번 넣거나 빠뜨리지 않는다.

로컬 개발 때 사용했던 /api와 /ai-api 상대경로는 개발 프록시 별칭이었다. AI 실제 서버 경로는 /api/chat이며 /ai-api/chat을 구현하라는 뜻이 아니다. 정적 프론트 호스팅이 이 별칭을 자동 프록시한다고 가정하지 않는다. 실제 HTTPS 주소를 직접 연결하거나 배포용 프록시를 별도로 설정한 뒤 API 응답이 JSON인지 확인한다.

## 각 파트가 제공할 연결 정보

| 항목 | 제공 내용 |
| --- | --- |
| 서버 주소 | 공개 Base·내부 Base·환경 구분·상태 확인 주소 |
| 실행 환경 | 선택 언어/런타임/프레임워크 실제 버전, 설치·기동·마이그레이션·중지·로그 확인 방법 |
| 인증·사용자 | 인증 헤더 또는 쿠키 방식, 사용자 식별·권한, 만료·갱신·401/403 처리. 현재 프론트에는 적용 규약이 없으므로 연결 전에 프론트 담당자와 맞출 것 |
| 서버 간 전달 | 문맥 제공 주체·초안/원본 저장 주체·완료 게시/재조회·스냅샷 검증·내부 인증 방식 |
| 제한 | 업로드 10개·각 10MiB·합계 25MiB 수용, HTTP와 모델/큐 제한, 비동기 복구 방식 |
| 검증 | 기능 ID별 수행 결과·실패 보존·중복·삭제 후 재추가·미검증 항목 |

비밀키는 서버에서만 관리하며 프론트 환경변수나 API 응답에 넣지 않는다. 모델 설정·DB URL·원본 저장소·큐 설정 이름은 각 파트가 정한다. 작성자의 .env 파일을 복사하는 방식은 없다.

## 외부 서버 연결 전에 필요한 조건

- HTTPS와 실제 프론트 origin을 허용한다. AI는 GET/POST·Content-Type/Prefer, 백엔드는 GET/POST/PATCH/DELETE와 Content-Type을 수용한다. 실제 인증 헤더가 추가되면 preflight 허용 목록도 맞춘다.
- 쿠키 인증을 선택하면 현재 프론트의 credentials 전송 설정까지 별도로 반영해야 한다. 인증이 이미 구현돼 있다고 가정하지 않는다.
- 홈 분석이 완료되기 전에 analysisId·완료 초안·원본이 백엔드에서 조회 가능한지 확인한다. ID 문자열만 같고 각 서버 DB에 데이터가 따로 없으면 저장에 실패한다.
- 내부 분석 요청의 문맥·원본은 서버 간 계약으로 전달한다. 같은 PC의 SQLite 파일을 양 서버가 볼 수 있다고 가정하지 않는다.
- 여러 인스턴스를 사용하면 작업·분석·삭제 잠금을 공유하고, 연결 끊김·중복 요청·재시작 뒤에도 일관성을 지킨다. 메모리 잠금만으로 운영 전체 잠금을 보장하지 않는다.
- 인증·사용자 범위가 정의되기 전에는 공유 개발 데이터 삭제를 사용자별 삭제로 바꿔 설명하지 않는다. 사용자 분리를 추가하면 문맥·초안·작업·원본·기록·성장 결과·삭제에 같은 범위를 적용한다.
- 기존 개인 개발 DB나 데이터는 전달 대상이 아니다. 실제 사용자 데이터를 이관해야 하는 별도 상황이 생기면 이관 범위·ID·원본·근거·보존 정책을 먼저 정한다.

## 연결 완료 판정

1. 각 서버를 자체 환경에서 기동하고 공개·내부 주소와 인증 규약을 전달한다.
2. 프론트 담당자가 두 Base 및 필요한 배포 라우팅·인증 전송을 반영한다.
3. 배포 프론트에서 정상·빈 상태·실패·중복·삭제·재추가·분석 중 변경을 검증한다.
4. 실제 연결 성공 뒤 개발용 서버 의존성 정리는 프론트 담당자가 수행한다. 수신자가 전달받지 않은 저장소에서 개발 폴더를 삭제하거나 파일을 수정할 필요는 없다.

이 문서 작업은 실행 코드·프론트 화면·DB·Swagger를 변경하지 않는다.
