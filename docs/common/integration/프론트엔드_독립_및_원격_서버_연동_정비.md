## 다음 작업자를 위한 지침

이 문서는 이후 세션에서 작업을 이어가기 위한 실행 계획이다. 사용자가 이 문서를 기준으로 작업을 요청하면 현재 코드와 저장소 지침을 다시 확인하고 아래 순서로 진행한다. 이미 끝난 항목은 결과를 확인한 뒤 중복 작업하지 않는다.

**실제 원격 서버 연동 검증은 이번 작업에서 제외한다.** 백엔드·AI 담당자는 각자의 서버를 구현 중이다. 원격 주소가 없어도 진행 가능한 프론트 분리·설정·문서화·로컬 검증을 완료한다. 실제 연결 성공을 이번 작업의 완료 조건으로 삼지 않는다.

## 목표

1. 작업 폴더를 프론트엔드 전용으로 정리한다.
2. 다른 파트가 구현하는 원격 백엔드·AI API를 설정으로 연결할 수 있게 준비한다.
3. 사용자가 화면별 요청·응답·저장 흐름과 각 서버의 책임을 이해할 수 있도록 설명한다.
4. 불필요한 프론트 코드와 로컬 서버 의존성을 제거하고 유지보수하기 쉽게 리팩토링한다.

## 범위와 담당

| 구분 | 이번 작업 |
| --- | --- |
| 프론트 | API 연결 설정, 서비스·상태·컴포넌트 정리, 응답 검증, 오류 처리, 데이터 흐름 문서화 |
| 백엔드·AI 계약 | 기존 정의와 실제 프론트의 차이 확인, 연동 요구사항 및 협의 필요 사항 정리 |
| 로컬 개발 서버 | 의존성을 먼저 해소하고 소스·설정·데이터의 보존 방안을 확인한 뒤 작업 폴더에서 분리 |
| 다른 파트의 서버 구현 | 담당 범위 밖. 내부 DB·큐·모델·서버 간 통신 구현을 프론트에서 대신하지 않음 |
| 실제 원격 연동 검증 | 이번 범위 제외. 양 파트 구현 완료 후 별도 작업 |

계약 확인은 프론트↔백엔드, 프론트↔AI, 백엔드↔AI의 데이터 흐름을 모두 포함한다. 기존 공개 API와 화면 동작을 기준으로 진행하며, 협의가 필요한 변경은 확정된 것처럼 적용하지 말고 미확정 목록에 남긴다.

## 현재 구조와 확인된 의존성

아래 내용은 작성 시점의 확인 결과다. 실행 전 현재 파일을 다시 대조한다.

| 위치 | 역할·확인 사항 |
| --- | --- |
| `src/` | React·TypeScript 프론트. `services/`, `types/`, `pages/`, `components/` 등 |
| `api-server/` | 로컬 백엔드 개발 서버 |
| `ai-api-server/` | 로컬 AI 개발 서버 |
| `vite.config.ts` | `/api` → `127.0.0.1:3001`, `/ai-api` → `127.0.0.1:8000/api` 개발 프록시 |
| `src/services/chat.ts` | 공통 HTTP 요청, API Base 설정, 채팅 접수·폴링·복원·응답 검증·활동 수정 적용이 함께 있음 |
| `scripts/build-swagger.mjs` | `api-server/docs/openapi.js`를 import. `predev`·`prebuild`에서 실행되어 서버 폴더 제거 시 실행·빌드에 영향 |
| `scripts/`, `tests/` | 일부 검사가 `api-server/src`와 `api-server/test-support`를 참조 |
| `docs/common/handoff/`, `docs/backend/handoff/`, `docs/ai/handoff/`, `docs/common/integration/handoff/`, `docs/common/review/` | 다른 파트에 전달할 공개 API·내부 전달·데이터·배포 규격 |

프론트는 `VITE_API_BASE_URL`과 `VITE_AI_API_BASE_URL`을 지원한다. 기본값 `/api`, `/ai-api`는 개발용 프록시 별칭이며 정적 배포에서 자동으로 연결되지 않는다. AI 실제 서버의 경로는 `/api/...`이므로 Base의 `/api` 중복·누락에 주의한다.

현재 로컬 서버는 SQLite를 공유한다. 기존 서버 간 전달 계약 문서는 공유 DB 없이 새로 구현하기 위한 설계이며, 해당 내부 HTTP 통신이 기존 서버에 모두 구현됐다는 뜻이 아니다.

## 작업 순서

### 1. 현재 구조와 데이터 흐름 정리

- [ ] Git 상태·브랜치·저장소 지침을 확인하고 사용자 변경을 보존한다.
- [ ] 화면별 서비스 함수·API 호출·로컬 상태·저장소 사용을 조사한다.
- [ ] 빌드·문서 생성·검사·설정에서 서버 폴더를 참조하는 곳을 목록화한다.
- [ ] 현재 검사를 확인하고 가능한 범위에서 변경 전 상태를 기록한다.
- [ ] 화면별 데이터 흐름을 실제 코드와 대조하여 문서화한다.

데이터 흐름 문서에는 다음 정보를 포함한다.

| 사용자 행동 | 프론트 함수 | 호출 서버·메서드·경로 | 요청 필드 | 응답 필드 | 저장 주체·시점 | 화면 갱신·오류 |
| --- | --- | --- | --- | --- | --- | --- |
| 실제 코드에서 확인한 사례 작성 | | | | | | |

핵심 ID인 `conversationId`, `requestId`, `jobId`, `analysisId`, 기록 `id`, `activityId`, `fileId`의 생성 주체·용도·수명을 확인한다. 필수·선택·생략·null, 날짜·상태 값도 구분한다. 실제로 확인되지 않은 동작을 추정해서 확정하지 않는다.

대표 흐름은 입력 → AI 분석 → 초안·원본 보관 → 결과 카드 → 사용자 확정 → 백엔드 기록 저장 → 목록 갱신이다. 분석 초안 보관과 확정 기록 저장을 구분하고, 활동 정보 수정 등 별도 분기도 설명한다. `sessionStorage`의 화면 복원 정보와 서버 영속 데이터를 구분한다.

### 2. API 계약과 원격 연결 준비

- [ ] 공개 API 정의와 프론트의 실제 요청·응답 검증을 대조한다.
- [ ] AI의 `analysisId`에 해당하는 초안·원본을 백엔드가 확보해야 하는 요구사항을 명시한다.
- [ ] 작업 진행·완료·실패·재조회·중복 요청·저장 충돌 규칙을 확인한다.
- [ ] 로컬 DB 공유를 전제하는 부분과 새 내부 전달 규격의 구현 책임을 구분한다.
- [ ] Base URL 설정, 환경변수 예시, 개발·배포 연결 방법을 정리한다.
- [ ] CORS·인증·파일 및 시간 제한 등 다른 파트와 확인할 항목을 미확정 목록으로 정리한다.

인증 방식이나 원격 주소가 미정이면 임의로 정하지 않는다. 서버 비밀키·내부 서비스 토큰은 프론트 환경변수에 넣지 않는다. 계약 확인만으로 실제 서버 연동이 성공했다고 보고하지 않는다.

### 3. 프론트 전용으로 분리

- [ ] Swagger 명세를 서버 실행 코드와 독립된 계약 파일로 옮겨 문서 생성 기능을 유지한다.
- [ ] 서버 구현을 참조하는 스크립트·검사를 프론트 검증과 서버 전용 작업으로 구분한다.
- [ ] 프론트에 필요한 검증은 독립된 API 대역·계약 데이터로 전환한다. 유효한 검사를 단순 삭제하지 않는다.
- [ ] 로컬 개발 서버 실행을 전제하는 안내·설정·불필요한 의존성을 정리한다.
- [ ] 서버 코드·DB·원본 파일·개인 환경설정의 보존 방안을 확인한 뒤 서버 폴더를 분리한다.
- [ ] 서버 폴더 없이 프론트 실행·빌드·문서 생성·관련 검사가 가능한지 확인한다.

서버 폴더부터 삭제하지 않는다. Git 추적 여부를 확인하고, 추적되지 않는 DB·원본·`.env`·키를 일괄 삭제하지 않는다. 보존 위치나 분리 방식이 결정되지 않았다면 의존성 해소를 먼저 완료하고 필요한 결정 사항을 남긴다. 비밀값은 문서·로그·커밋에 포함하지 않는다.

### 4. 프론트 코드 리팩토링

- [ ] 공통 API 설정·HTTP 요청·오류 처리를 역할에 맞게 분리한다.
- [ ] 채팅의 접수·폴링·복원·응답 검증을 관리 가능한 단위로 정리한다.
- [ ] 큰 컴포넌트와 중복 로직은 실제 필요에 따라 분리한다.
- [ ] 사용하지 않는 코드·목업·타입·패키지는 참조를 확인한 뒤 제거한다.
- [ ] 기존 화면 동작과 공개 API 계약을 유지한다.

변경은 기능 단위로 작게 진행한다. 시간 초과 시 서버 처리 여부 불확실성, 중복 저장 방지, 취소, 재조회, 잘못된 응답 거절 등 기존 동작을 보존한다. 리팩토링을 이유로 화면 기능이나 데이터 계약을 임의로 바꾸지 않는다.

### 5. 이번 범위의 로컬 검증과 후속 작업 기록

- [ ] `npm run lint`, `npm run build` 및 변경과 관련된 검사를 실행한다.
- [ ] 계약 기반 API 대역으로 주요 요청 본문·응답 처리·실패 분기를 검증한다.
- [ ] 개발 서버 실행과 Swagger 문서 제공이 서버 폴더 없이 가능한지 확인한다.
- [ ] 실제 서버를 사용하지 않고 검증한 범위를 명시한다.
- [ ] 변경 내용·검사 결과·남은 협의 사항·후속 원격 검증 목록을 기록한다.

로컬 검증은 실제 AI 호출이나 개인 DB 변경을 전제하지 않는다. 기존 검사 실행 전 부작용을 확인한다. 단순 구조 정리에 의미 없는 검사를 추가하지 말고, 변경으로 깨질 수 있는 계약·동작을 중심으로 검증한다.

## 이번 작업의 완료 기준

- [ ] 작업 폴더가 프론트 전용으로 정리되어 있다.
- [ ] 로컬 백엔드·AI 소스와 공유 DB 없이 프론트 실행·빌드·관련 검사가 가능하다.
- [ ] 원격 백엔드·AI Base URL을 설정으로 지정할 수 있고 예시·안내가 있다.
- [ ] 화면별 요청·응답·저장 흐름과 ID의 의미를 문서로 이해할 수 있다.
- [ ] 기존 공개 API 계약과 사용자 기능이 보존되어 있다.
- [ ] 실제 확인한 불필요 코드·중복·복잡한 책임이 정리되어 있다.
- [ ] 검증 결과와 미확정 사항을 명시했으며 실제 원격 연동 성공으로 과장하지 않았다.

## 별도 후속 작업: 실제 원격 연동 검증

이번 이슈에서 실행하지 않는다. 다른 파트의 구현과 테스트 환경이 준비되면 별도 작업으로 진행한다.

- 실제 HTTPS 주소·CORS·인증·업로드·시간 제한 확인
- 텍스트·파일·링크 분석과 작업 진행·재접속 복구 확인
- 분석 초안·원본의 서버 간 전달 및 확정 저장 확인
- 조회·검색·수정·삭제·성장 분석 확인
- 중복 요청·시간 초과·실패 후 재조회와 데이터 일관성 확인

## 작업 재개·완료 기록

작업을 진행한 뒤 아래를 갱신하여 다음 세션이 이어받을 수 있도록 한다.

- 진행한 단계:
- 변경 파일과 이유:
- 검증 명령·결과·검증 범위:
- 서버 소스·설정·데이터 보존 및 분리 결과:
- 다른 파트와 협의할 사항:
- 미완료 항목과 다음 시작 지점:
