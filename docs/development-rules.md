# 개발 규칙 · 홈 AI 채팅

최종 정리: 2026-11-01

이 문서는 이번 대화에서 확인한 사용자 요구와 현재 구현 원칙을 구분해서 기록한다. **사용자의 최신 요청이 이 문서보다 우선한다.** 아래 규칙을 근거로 불필요한 승인 단계를 만들지 않는다.

현재 구현 상태와 다음 진행 방향은 [개발 기록](development-log.md)을 참고한다.

## 1. 사용자가 직접 강조한 작업 방식

### 기능은 하나씩 진행한다

사용자는 채팅을 직접 이해하고 확인하면서 단계적으로 개발하기를 원한다. 현재 요청한 기능을 완성하고, 관련 없는 기능이나 스타일을 함께 바꾸지 않는다.

“다른 것들은 조정하지 말고”라고 요청하면 지정한 범위만 수정한다. “다시 되돌려줘”는 문맥상 직전 변경을 되돌리는 뜻으로 해석하고, 이전 작업 전체를 초기화하지 않는다.

### 코드의 역할이 보이게 작성한다

- 상태·이벤트·비동기 처리·화면 영역의 목적을 한국어 주석으로 설명한다.
- 역할이 바뀌는 부분에는 적절한 빈 줄을 두어 읽기 쉽게 한다.
- 목데이터에는 각 응답과 주요 필드가 무엇을 표시하는지 설명한다.
- 사용자가 수정한 설명 주석을 필요 없이 제거하거나 전체 파일을 재포맷하지 않는다.

### 설명은 작게 끊어서 한다

사용자가 코드 설명을 요청하면 동작 순서대로 한 부분씩 설명한다. 한 번에 전체 코드를 길게 설명하지 않는다. 사용자가 “다음”이라고 하면 이어지는 부분을 설명한다.

## 2. API 연결에 대한 사용자 요구

최종 목표는 AI의 대답과 분석 결과를 실제 AI API에서 받는 것이다. 현재는 목데이터로 흐름을 확인하고, 이후 교체하기 쉽게 구성한다.

사용자가 지정한 우선 목표는 **텍스트 경험 입력·파일 업로드·변화 없는 파일 및 텍스트·다중 파일 일괄 업로드를 실제 AI API 연결 후에도 원본과 같은 결과 구성으로 사용할 수 있게 하는 것**이다. 당분간 API 응답 자리는 목데이터로 유지하고, 시나리오별 채팅 흐름을 단계적으로 완성한다. 저장 기능이나 링크 입력을 이 목표보다 먼저 진행해야 하는 것으로 간주하지 않는다.

- 화면은 공통 서비스 함수 `getChatReply`를 호출한다.
- 목 분석과 지연 처리는 `src/mocks/Home/`에 둔다.
- 응답은 HTML이 아닌 JSON에 대응하는 데이터로 관리한다.
- 카드의 문구·활동·분류·개수·변화·근거를 응답 데이터에서 표시한다.
- UI 디자인과 로딩 애니메이션은 프론트엔드가 담당한다.
- API 응답 초안과 확정된 서버 명세를 구분한다.
- 실제 API 연결 후 활동·자료 유형·주요 변화 여부의 판단은 API 응답에 따른다. 프론트엔드의 목 분류 규칙을 실제 분석으로 계속 적용하지 않는다.
- 변화 없는 텍스트도 별도 검토한다. 모든 텍스트를 기능 축소나 Turning Point 발견으로 처리하지 않는다.

`Promise<ChatReply>`를 유지하는 서비스 경계는 현재 구현 방식이다. 실제 API 명세가 달라지면 서비스에서 화면용 구조로 변환할 수 있다.

## 3. 원본 디자인과 사용자 수정의 우선순위

기준은 [원본 HTML](../references/1Line_reference.html)이다. 사용자 요청이 없는 문구·색상·배치·버튼을 임의로 바꾸지 않는다. 다만 이후 사용자가 요청한 반응형·너비 조정은 원본보다 우선한다.

**원본 HTML 파일은 수정하지 않는다.** 대화 중 어색한 반응이나 누락된 상호작용을 발견하면 현재 구현 중인 `src/pages/Home.tsx`에서 개선한다. 기존 구조상 필요한 경우 연결된 컴포넌트·서비스·목데이터도 조정하되, 개선을 위해 원본을 먼저 고치는 방식은 사용하지 않는다.

원본의 결과 카드와 시나리오 의도는 유지한다. 입력과 맞지 않는 답변, 근거 없는 주요 변화 생성, 저장 전 저장 완료 안내처럼 부자연스러운 흐름은 구현 화면에서 보완한다. 실제 입력 내용과 목 시연 응답의 한계를 구별해서 설명한다.

다중 파일 카드는 다음 구성을 유지한다.

1. “총 N개의 자료를 확인 후 일괄 그룹화했어요.”
2. 활동명과 “N개 파일 자동 매칭” 배지
3. 자료 유형과 개수 박스
4. 💡 버전 연결 안내
5. “전체 저장”, “자료 확인”
6. “방금 전 · Growth AI 분석 완료”

이 카드에 사용자 요청 없이 별도 활동 제목, 전체 파일 목록, 수정·다른 활동 선택 버튼을 다시 추가하지 않는다. 데이터가 달라지면 개수와 요약은 실제 응답에 맞춰 바뀔 수 있다.

응답 대기 표시는 원본의 **Bot 아이콘 + 회색 말풍선 + 움직이는 점 3개**를 유지한다.

## 4. 자료 유형 박스의 줄바꿈 규칙

사용자가 말한 “다른 글자도 한 줄”은 **자료 유형 문구**에 대한 요청이다. 카드 제목이나 하단 안내까지 한 줄로 고정하라는 뜻이 아니다.

- ‘와이어프레임 2개’처럼 유형명과 개수를 한 줄로 표시한다.
- ‘2’와 ‘개’가 서로 다른 줄로 떨어지지 않도록 한다.
- 유형이 1개든 2·3·4개든 남은 공간을 자연스럽게 활용한다.
- 공간이 부족하면 문구를 쪼개는 대신 박스 전체를 다음 줄로 보낸다.
- 아주 긴 유형명은 현재 박스 내부 가로 스크롤로 확인한다. 문구를 임의로 잘라내지 않는다.
- 분류 1개일 때 좌우 12px 마진을 추가한 변경은 사용자가 취소했다. 다시 넣지 않는다.
- 제목·활동명·하단 안내에 적용했던 `truncate`와 `title` 기반 말줄임 변경도 취소했다. 자료 유형 변경을 다른 문구에 확대 적용하지 않는다.

현재 바깥 카드 최대 너비 `28rem`은 구현 값이다. 이 숫자를 사용자가 직접 지정한 고정 규칙으로 취급하지 않는다.

## 5. 파일 입력 규칙

파일을 **선택·드롭하는 단계**와 **전송하는 단계**를 구분한다.

- 파일 여러 개를 입력창에 첨부할 수 있어야 한다.
- 선택한 파일은 먼저 전송 전 첨부 목록에 보인다.
- 보내기 버튼 또는 Enter로 전송한 뒤 파일명을 사용자 말풍선에 표시한다.
- 파일 선택이나 드롭만으로 자동 전송하지 않는다.
- 첨부한 파일명을 목데이터의 고정 파일명으로 바꾸지 않는다.
- 파일만 보내기, 텍스트와 함께 보내기, 전송 전 개별 삭제를 유지한다.
- 드롭 영역은 현재 입력창·첨부 영역이다. 사용자 요청 없이 전체 화면 드롭으로 확대하지 않는다.

## 6. 현재 구현에서 유지할 구분

이 절은 사용자의 직접 발언을 그대로 옮긴 규칙이 아니라, 현재 코드와 연동 구조를 보존하기 위한 구현 원칙이다.

- 목 응답을 실제 AI 분석이나 실제 파일 업로드 완료로 설명하지 않는다.
- 현재 파일명 분류 규칙을 실제 AI의 분석 기준으로 확정하지 않는다.
- 예시 활동명 ‘1호선톤’을 실제 사용자 활동 매칭으로 간주하지 않는다.
- 버전 연결이 있다는 사실만으로 주요 변화나 Turning Point를 만들지 않는다.
- 분석 결과를 받은 것과 사용자가 기록을 저장한 것은 별도 상태다.
- 아직 저장되지 않은 결과를 저장 완료로 표시하지 않는다.
- 저장·수정 API가 없다는 이유로 임의의 가짜 성공 동작을 추가하지 않는다. 사용자가 목 저장 흐름을 요청하면 그 범위에서 구현한다.
- 최신 비동기 응답만 반영하는 보호와 한글 조합 중 Enter 처리를 유지한다.

## 7. 캡처 확인과 문서 관리

사용자 캡처는 `references/screenshots/`에 둔다. 경로 오류가 표시돼도 실제 파일이 있는지 확인하고, 존재하면 이미지를 직접 열어 확인한다. 이번에 확인한 파일은 `image1.PNG`다.

새 작업을 시작할 때는 관련 소스와 최신 캡처를 함께 본다. 과거에 제안했다가 취소한 스타일을 다시 적용하지 않는다.

의미 있는 기능이나 API 구조가 바뀌면 [개발 기록](development-log.md)과 해당 API 문서를 갱신한다. 검증은 수행한 범위만 적고, 미구현 기능은 완료로 기록하지 않는다.
