# 공통 JSON 계약 초안

작성일: 2026-11-12 · 상태: 제안, 구현 미적용

이 문서는 변경 방향을 기록한 초안이다. 아래 예시는 전체 스키마를 대체하지 않으며, 구현 전 기존 handoff·OpenAPI와 대조해 필수 필드와 미확정 정책을 확정한다.

## 성장 유형

| ID | 화면 표시 | 판단 기준 |
| --- | --- | --- |
| capability_expansion | 능력 확장 | 이전에 수행하지 않았던 기술·역할·업무를 실제 수행 |
| performance_improvement | 성과 향상 | 비교 가능한 조건에서 결과·성과 개선 |
| experience_accumulation | 경험 축적 | 기존 기록에서 확인되지 않았던 새로운 활동·경험 수행 |
| efficiency_improvement | 효율성 | 유사한 결과 수준에서 시간·자원 절감 |
| experience_transfer | 경험 전이 | 이전 활동의 지식·경험·피드백을 다른 활동에 실제 활용 |

유형 ID·라벨은 서비스가 고정 관리한다. AI가 자유 생성하지 않는다. 성장 분야(axis)는 기존의 별도 분류로 유지한다.

## 호출 흐름

1. React → Spring: `POST /api/journey/analyze`. 프론트가 저장 기록을 다시 보내지 않는다.
2. Spring → AI: `POST /api/analyze/journey`. DB에서 구성한 records, recordCount, sourceFingerprint와 기준 버전을 JSON으로 전달한다.
3. AI → Spring: 분석 결과와 요청 해시·기록 수·모델·프롬프트·기준 버전을 반환한다.
4. Spring: 응답과 현재 DB를 검증한 뒤 저장하고 React에 반환한다.
5. React → Spring: `GET /api/journey`는 저장된 결과만 조회한다. 조회만으로 AI를 호출하지 않는다.

`records`의 기존 전체 필드와 입력 제한은 [서버 간 데이터 전달 계약](../common/handoff/서버간_데이터_전달_계약.md)을 바탕으로 유지한다. 실제 요청 예시와 전체 스키마는 계약 확정 시 추가한다.

## 이벤트 변경 예시

기존 이벤트의 단일 type 및 최상위 evidence/comparison을 유형별 판단 배열로 옮기는 제안이다.

```json
{
  "id": "event-01",
  "occurredAt": "2026-11",
  "activity": { "id": "activity-01", "name": "Growth AI" },
  "axis": "backend",
  "title": "배포 시간을 줄였어요.",
  "description": "동일한 테스트를 통과하며 배포를 자동화했어요.",
  "growthAssessments": [
    {
      "type": "efficiency_improvement",
      "reason": "같은 테스트를 통과하면서 배포 시간을 30분에서 5분으로 줄였어요.",
      "comparison": {
        "before": "배포 30분, 테스트 10개 통과",
        "after": "배포 5분, 같은 테스트 10개 통과"
      },
      "evidence": [
        { "recordId": "record-01", "quote": "배포에 30분이 걸렸고 테스트 10개를 통과했다." },
        { "recordId": "record-02", "quote": "배포에 5분이 걸렸고 같은 테스트 10개를 통과했다." }
      ]
    }
  ]
}
```

- `growthAssessments`: 1~5개, 허용된 유형만 사용하고 같은 이벤트 안에서 유형 중복 금지.
- `reason`: 비어 있지 않은 판단 설명. `evidence`는 실제 저장 기록의 ID와 연속 원문 인용.
- `comparison`: 선택 필드. 비교 정보가 없으면 생략한다. AI 내부 모델의 null을 공개 응답에서 생략하는 정규화 규칙도 명시한다.
- 모든 판단에 근거가 있어야 한다. 인정할 유형이 없으면 이벤트를 생성하지 않는다.
- 전체 성장 근거가 부족하면 `events: []`를 반환하고 요약에 판단 한계를 설명한다.
- 기존 summary·badges와 그 근거는 유지한다. 첫 경험 배지는 제공된 기록 범위의 첫 경험으로 제한한다.
- AI 내부의 evidenceId 선택과 원문 복원 구조는 유지한다. 공개 응답에는 `{recordId, quote}`를 사용한다.

## 선택지와 검증

- Spring이 `typeOptions`에 전체와 고정 5종을 제공한다. 이벤트가 없거나 삭제 후에도 유지한다.
- AI 내부 출력에는 고정 typeOptions를 생성하도록 요구하지 않는 방향으로 정리한다. 기존 공급자 응답과의 정확한 경계는 전체 스키마에서 확정한다.
- axisOptions와 event.axis의 참조·중복 검증은 유지한다.
- Spring은 각 판단의 근거를 검증하고, 이벤트 내 전체 근거를 중복 없이 합쳐 활동 연결과 표시 월을 검증한다.
- 표시 월은 기존처럼 근거 기록의 저장 월을 사용한다. 실제 활동 발생 월로 단정하지 않는다.
- 경험 전이는 서로 다른 활동과 실제 활용을 뒷받침하는 근거가 필요하다. 이벤트의 대표 활동은 경험을 적용한 활동으로 하는 방향을 검토한다.
- 의미상 성장 인정 여부는 AI가 판단한다. 인용문 존재 확인만으로 의미적 타당성이 입증되지는 않는다.

## 변경 감지와 버전

- sourceFingerprint는 분석 대상 기록 묶음의 해시다. AI가 전달받은 값을 반환하고 Spring이 현재 기록의 해시와 비교한다.
- 분석 중 기록이 바뀌면 결과를 저장하지 않고 재분석을 안내한다. 중복 분석 요청 차단은 별도 처리다.
- 제안 버전: `promptVersion: journey-v6`, `criteriaVersion: growth-criteria-v1`. 아직 확정된 버전명은 아니다.
- JSON 구조 버전과 성장 기준 버전을 구분한다. 구조 버전의 필드·값·배치 위치는 확정이 필요하다.
- 기록 변경 상태와 기준 변경 상태를 구분해 재분석을 안내한다.

## DB·호환·삭제

- 새 분석은 기존 journey_analyses.result_json에 저장할 수 있다. 이번 화면을 위해 유형별 테이블을 신설할 필요는 없다.
- criteria_version 컬럼 추가를 제안한다. 적용 시 기존 DB 마이그레이션과 컬럼명을 명시한 INSERT가 필요하다.
- 기존 결과를 새 유형으로 임의 매핑하지 않는다. 이전 구조 조회와 재분석 안내의 구체적인 표시 정책을 확정한다.
- 새 분석 실패 시 마지막 결과를 유지한다. 삭제로 무효화된 결과를 복원해서는 안 된다.
- 자료·활동 삭제 시 관련 인용문이 남지 않도록 기존 전체 분석 무효화 동작을 유지한다.
- 기존 기록·Timeline의 JSON과 테이블은 성장 판단 배열로 변경하지 않는다.

## 구현 전 확정할 정책

- 하나의 기록에 명시된 Before/After도 인정할지: 현재는 서로 다른 기록 2개 이상을 요구한다. 변경 승인 전 기존 제한을 임의로 완화하지 않는다.
- 이전 구조 결과의 표시 방식과 새 고정 필터의 동작.
- 구조 버전 및 기준 버전의 최종 필드·값, 입력·출력 필드 배치.
- 근거 수·문자 길이 등 배열과 문자열의 상한.
- 유형별 comparison 필수 여부, 양쪽 상태와 근거를 연결하는 검증 방식.
- 경험 전이의 출발·적용 활동 및 이벤트 날짜를 검증하는 상세 규칙.
- 오류 코드·메시지와 전체 AI 요청·응답 예시.
