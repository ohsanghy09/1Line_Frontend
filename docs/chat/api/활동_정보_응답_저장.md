# 활동 정보 응답과 확인 저장

작성: 2026-11-04. 실제 AI 연결 전 사용할 임시 계약이다. 실제 공급자 명세가 정해지면 서비스 경계에서 변환한다.

## 요청 문맥과 응답

현재 `app.js`는 실제 입력·첨부와 `analysisContext(db)`의 기존 활동 ID·이름·메타정보를 목 공급자에 전달한다. 실제 AI 공급자도 이 문맥을 받아 기존 활동 ID를 선택하거나 새 활동 후보를 반환하도록 연결할 위치다. 파일 본문 추출·AI HTTP 요청·프롬프트는 아직 구현하지 않았다.

응답의 `analysis.activity`는 기존 name·confidence에 다음 선택 필드를 추가했다. 이전 저장 응답과 세션은 계속 읽을 수 있다.

```json
{
  "name": "컴퓨터비전 연구",
  "confidence": "medium",
  "id": null,
  "match": "new",
  "category": "프로젝트",
  "status": "진행 중",
  "role": null,
  "period": { "start": "2026-09", "end": null },
  "summary": null
}
```

- `match`: existing는 기존 활동 ID 필수, new/unresolved는 ID 없음(null/생략). unresolved는 사용자가 활동을 선택해야 한다. 새 후보의 ID는 저장 시 서버에서 생성한다.
- category·role·summary: 확인 가능한 문자열 또는 null. summary는 활동 전체 요약이며 기록의 `analysis.summary`와 별개다.
- status: 진행 중 / 완료 / null. 기간만으로 상태를 추측하지 않는다.
- period: null 또는 start/end가 각각 null이나 YYYY-MM / YYYY-MM-DD인 객체. 연도나 날짜 정밀도를 입력 없이 보충하지 않는다. 실제 달력 날짜와 시작/종료 순서를 검사한다.
- name·confidence만 있는 이전 응답도 허용한다. 새 공급자는 명시적인 match·id·nullable 메타정보를 반환하는 것을 기준으로 한다.

서버는 `replySchema`, 프론트는 `isActivityProposal`·`isReply`로 검증한다. 서버 목 응답도 초안 보관 전에 검증한다. 현재 목 공급자는 예시 1호선톤이 문맥에 있으면 해당 ID를 제안하고 역할·유형·상태·기간·활동 요약은 null로 둔다. 입력을 실제로 분석한 것이 아니다. 예시 활동이 없으면 unresolved를 반환한다.

## 사용자 확인 화면

**2026-11-06 현재:** 모든 카드의 기록·저장은 활동 정보 확인 모달 없이 기존 활동 ID와 자료 유형으로 요청한다. 수정 모달은 기존 활동 선택·자료 유형만 제공한다. 신규 활동·활동 메타정보 API 계약은 서버에 남아 있으나 현재 카드에서는 사용하지 않는다. 활동 ID가 미확정·삭제된 경우 저장을 막고 안내하며 새 활동 생성 진입은 미구현이다. [현재 카드 동작](../구현_기능/카드_기록_수정.md) 참고. 아래 확인 화면 설명은 이전 구현 이력이다.

변화 없음 단일 파일 카드는 아래 일반 흐름의 예외다. 아카이브 저장은 연결된 기존 활동으로 즉시 저장하며 확인 모달을 열지 않는다. 수정 모달은 기존 활동 선택과 자료 유형만 제공하고 활동 메타정보는 수정하지 않는다. 연결할 활동을 확인할 수 없으면 수정 버튼으로 활동 선택을 안내한다. [변화 없는 파일](../구현_기능/변화_없는_파일.md) 참고.

기존 카드 버튼은 유지하며 저장 버튼을 누르면 `ActivityReviewModal`에서 연결할 활동·자료 유형·활동명·유형·상태·역할·시작/종료일·전체 요약을 확인한다. 새 후보는 새 활동으로 저장을 선택하고 이름을 확인한다. 미확인 항목은 비워둘 수 있다.

기존 활동의 메타정보 적용 체크박스는 기본 해제다. 체크하지 않으면 제안이 있어도 DB 메타정보를 바꾸지 않는다. 체크하면 입력한 non-null 값만 적용한다. 빈 항목은 기존 값을 유지하며 기존 정보 삭제 기능은 아니다. 이 변경이 같은 활동의 다른 기록 화면에도 적용된다는 안내를 제공한다.

저장 전 수정은 응답/세션에 확인 내용을 적용할 뿐 DB를 변경하지 않는다. 최종 저장에서는 다시 확인한다. 저장 후 수정은 기존 활동 선택과 확인된 메타정보만 PATCH로 적용한다. 저장된 기록 수정에서 새 활동 생성은 제공하지 않는다.

취소·X·Escape는 저장하지 않는다. 요청 중에는 닫기·중복 제출을 막는다. native dialog로 초점 제한/복귀·배경 비활성화·배경 스크롤 제어를 적용했다. 실제 브라우저 검증은 사용자 담당이다.

## 저장 계약

기존 활동에 기록만 저장:

```json
{ "activityId": "computer-vision", "analysisId": "분석 초안 ID" }
```

새 활동 확인 후 기록 저장:

```json
{
  "analysisId": "분석 초안 ID",
  "newActivity": {
    "name": "컴퓨터비전 연구", "category": "프로젝트", "status": "진행 중",
    "role": null, "period": { "start": "2026-09", "end": null }, "summary": null
  },
  "classification": { "materialType": "연구 기록" }
}
```

`activityId`와 `newActivity`는 정확히 하나를 보낸다. `analysisId`와 직접 카드 `reply`도 정확히 하나다. `newActivity`는 name과 위 메타정보 필드 전체를 포함하며 모르는 값은 null이다. 직접 reply 저장은 서버의 개발 계약으로 남아 있지만 현재 홈은 analysisId를 사용한다.

기존 활동 정보를 명시적으로 적용할 때는 POST `/api/records` 또는 PATCH `/api/records/:id`에 `activityUpdates`로 category·status·role·period·summary 전체(nullable)를 보낸다. `activityUpdates`에는 이름/ID를 넣지 않는다. 응답의 활동 후보만으로는 메타정보를 적용하지 않는다.

활동 생성/수정·기록 저장/수정·변화 이벤트 저장은 같은 트랜잭션이다. 실패하면 모두 롤백한다. 같은 이름의 새 활동은 409로 거절해 기존 활동 선택을 유도하고 이름만으로 자동 합치지 않는다. 같은 초안의 중복 저장도 409다. 저장 응답의 activity는 확정된 ID와 실제 저장 메타정보, match=existing로 갱신된다.

## DB와 화면 반영

기존 activities에 nullable `start_date`, `end_date`를 없는 경우 추가한다. 이전 period 표시 문자열은 보존하며 확인된 날짜 수정 시에만 표시 문자열도 갱신한다. 일부 날짜만 확인한 경우 null인 반대쪽 날짜는 기존 값을 유지하고 병합된 기간을 다시 검사한다. 기존 기록·파일·초안은 변경하지 않는다.

나의 발자국은 재진입 시 확정된 유형·상태·역할·기간·활동 전체 요약을 조회한다. 저장 성공 후 활동 변경 이벤트를 보내 사이드바 개수를 갱신하고, 다른 카드의 확인 화면도 매번 활동을 재조회한다. 다른 탭 자동 갱신은 범위 밖이다.

## 검증

- 서버 검사: 기존/신규/미확인 계약, 이전 응답 호환, null, 잘못된 ID·상태·달력 날짜·역전 기간, 후보만으로 DB 미변경, 새 활동+기록 원자적 저장, 중복 이름/초안, 기존 메타정보 보호와 명시적 적용, 실패 롤백.
- 프론트 서비스→Vite→API→임시 SQLite: 확장 응답 검증, 새 활동 생성·기록 저장·활동 선택 재조회·메타정보 수정·아카이브 반영.
- 기존 채팅 API·세션 복원·아카이브 테스트를 함께 수행한다. 실제 사용자의 DB에 예시 기록을 주입하지 않는다.
- 실제 AI 정보 추출과 브라우저 모달 조작은 검증 완료가 아니다.
