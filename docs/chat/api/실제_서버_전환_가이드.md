# 실제 백엔드·AI 서버 전환 가이드

링크 기능 후속: 홈 링크 모달·`POST /api/chat/links`·목 진행·기록·수정·작업 복원을 구현했다. 실제 링크 분석은 `createMockLinkReply`와 링크 목 진행을 교체한다. 현재 외부 내용을 수집하지 않으며 상세는 [링크 입력·분석](../구현_기능/링크_입력_분석.md)을 참고한다.

작성: 2026-11-04. 현재 저장소의 구현을 기준으로 실제 서버 연결 시 바꿀 위치와 동작을 정리한다. 이 문서는 전환 계획이며 실제 AI 연결을 완료했다는 뜻은 아니다.

## 1. 현재 구조와 바꿀 구조

현재는 다음과 같이 동작한다.

```text
React → 프론트 서비스 → Vite /api 프록시 → api-server
                                           ├─ SQLite: 파일·대화·기록·작업 저장
                                           ├─ createMockReply: 임의 분석 결과
                                           └─ jobProgress: 시간 기반 목 진행
```

실제 연결 구조는 백엔드 구성에 따라 둘 중 하나로 정한다.

| 방식 | 바꿀 부분 |
| --- | --- |
| 현재 `api-server`를 유지하고 AI 서버를 연결 | 프론트 요청 구조를 유지하고 서버의 목 분석·목 진행을 실제 AI 요청과 작업 상태로 교체한다. 필요하면 DB도 교체한다. |
| 정식 백엔드가 업로드·AI 호출·저장을 모두 담당 | 프론트 API 주소와 서비스의 요청·응답 변환을 정식 계약에 맞춘다. `api-server`는 로컬 개발용으로 남기고 운영 요청을 보내지 않는다. |

아래 변경을 모두 양쪽 서버에 중복 구현할 필요는 없다. 파일·기록·작업의 최종 소유 서버를 먼저 정한다. AI 서버의 비밀키와 내부 통신은 백엔드에서 관리한다.

## 2. 프론트에서 수정할 파일

| 위치 | 변경할 내용 |
| --- | --- |
| `src/services/chat.ts` | API 기본 주소, 인증 전달, 업로드 요청, 작업 상태 조회, 응답 변환·검증, 조회 간격과 시간 제한 |
| `src/services/records.ts` | 활동 목록·기록 저장·기록 수정 경로와 요청·응답 변환 |
| `src/services/footprints.ts` | DB 아카이브 목록·활동 상세·자료 상세 조회와 응답 검증·날짜 변환 |
| `src/types/chat.ts` | 화면용 구조. 실제 응답을 이 구조로 변환할 수 있으면 그대로 유지 |
| `vite.config.ts` | 개발 중 `/api` 요청을 전달할 백엔드 주소 |
| `src/pages/Home.tsx` | 서비스 호출과 진행 콜백. 스트리밍·재접속·작업 복원이 필요한 경우 해당 상태 처리 추가 |
| `src/components/chat/ConnectedChatReplyCard.tsx` | 서버 기록 ID·저장 상태 복원, 재시도·중복 저장 정책에 맞춘 처리 |

카드 JSX에서 실제 분석을 다시 판단하지 않는다. 서비스가 백엔드 응답을 `ChatReply`와 `ChatProgress`로 변환하고 컴포넌트는 그 값을 표시한다.

### API 주소 설정

프론트의 기본 API 주소는 `/api`다. 로컬 개발에서는 Vite가 `http://127.0.0.1:3001`로 전달한다.

다른 주소로 직접 호출하려면 프로젝트 루트의 `.env.local` 등에 다음처럼 설정할 수 있다. 아래 주소는 예시다.

```dotenv
VITE_API_BASE_URL=https://backend.example.com/api
```

Vite를 다시 시작하거나 배포용 빌드를 다시 만든다. `VITE_` 값은 브라우저에 전달되므로 AI 비밀키를 넣지 않는다. `/api`까지 포함한 기본 주소를 지정하고 서비스가 `/chat` 등 하위 경로를 붙인다.

운영에서 `/api`를 그대로 사용한다면 호스팅/리버스 프록시가 정식 백엔드로 전달하도록 설정한다. Vite의 개발 프록시는 배포 결과물에 포함되지 않는다. `server.js`는 현재 로컬용 `127.0.0.1` 바인딩이므로 이 서버 자체를 배포할 경우 실행 환경에 맞게 조정한다.

다른 출처로 직접 호출할 때는 백엔드의 CORS 허용 출처·요청 헤더를 맞춘다. 현재 로컬 서버의 `FRONTEND_ORIGIN`은 기본 `http://localhost:5173`이며 서버 환경변수로 전달한다. 현재 Node 실행 명령이 서버 `.env`를 자동 로드하는 구조는 아니다.

인증 방식은 아직 없다. 정식 계약이 토큰이면 공통 `request()`에 인증 헤더를, 쿠키이면 fetch 옵션과 서버의 쿠키·CORS 설정을 계약에 맞춰 추가한다.

## 3. 서버의 목 분석을 실제 분석으로 교체

활동 정보 계약 후속: `analysisContext(db)`의 기존 활동 ID·메타정보를 공급자에 전달하고 `analysis.activity`의 기존/신규/미확인·nullable 정보 응답을 검증한다. 사용자 확인 후 새 활동 생성 또는 기존 활동 정보 적용을 기록 저장과 함께 처리한다. 실제 공급자 요청과 프롬프트는 아직 없으며 [활동 정보 응답·저장](활동_정보_응답_저장.md)을 교체 경계로 참고한다.

현재 `api-server/src/app.js`는 `createMockReply()`를 접수 시 호출해 목 최종 결과를 먼저 저장한다. 원본은 SQLite `files.content`에 BLOB으로 보관한다. 실제 PDF·문서 내용 추출이나 AI 호출은 하지 않는다.

실제 연결 시 다음을 변경한다.

1. 업로드 원본과 대화 입력을 보관하고 분석 작업을 생성한다.
2. 백엔드에서 AI 서버에 파일/저장 위치, 사용자 입력, 필요한 기존 활동·자료·대화 문맥을 전달한다. 현재 `conversationId`는 저장 묶음일 뿐 과거 대화를 AI에 전달하지 않는다.
3. 처리 중에는 작업 상태를 갱신하고, AI 응답을 받은 뒤 검증·변환한 최종 분석을 저장한다.
4. 최종 결과가 정상적으로 보관된 경우에만 작업을 `completed`로 전환한다. 실패는 작업 오류로 보관한다.

교체 지점은 `api-server/src/mock-reply.js`와 이를 호출하는 `app.js`다. 현재 `mode: change/no-change`, 예시 활동 `1호선톤`, 임의 분류·요약을 실제 판단으로 사용하지 않는다. 변화 여부·분류·관련 자료·이전 버전은 실제 분석 응답에서 가져온다.

실제 서버가 다른 이름의 필드를 제공하면 서버 또는 프론트 서비스에서 변환한다. 현재 카드가 읽는 핵심 값은 다음과 같다.

- `kind`, `content`
- `analysis.activity`, `materialType`, `stage`, `summary`
- `analysis.files`, `groups`, `changes`
- `analysis.suggestedSaveMode`, 선택 필드 `noChangeMessage`

중요 변화가 없으면 `changes: []`를 사용한다. 실제 입력의 파일명·개수·원본은 유지한다. 서버 검증은 `api-server/src/validation.js`, 프론트 검증은 `src/services/chat.ts`의 `isReply()`도 함께 맞춘다.

## 4. 진행 상태: 0.4초와 0.7초는 서로 다른 설정

| 설정 | 현재 위치 | 의미 | 실제 연결 시 |
| --- | --- | --- | --- |
| 400ms | 프론트 `waitForPoll()` | 다음 조회 요청 전 대기 시간 | 서버 부하·응답 속도에 맞춰 조정 가능 |
| 700ms | 서버 `progress.js`의 `MOCK_STAGE_MS` | 목 단계를 넘기는 시간 | 제거하고 실제 작업 상태로 교체 |
| 약 2.8초 | 목 단계 4개 × 700ms | 현재 목 완료 시점 | 실제 분석 완료 신호로 교체 |
| 30초 | 프론트 `request()` | 개별 HTTP 요청의 제한 시간 | 업로드·요청 소요 시간에 맞춰 조정 |
| 30초 | `getChatReply()` 폴링 블록 | 접수 응답 후 전체 조회 제한 | 예상 분석 시간과 복원 정책에 맞춰 조정 |

**400ms가 지나면 다음 분석 단계로 넘어가는 것이 아니다.** 프론트는 약 400ms 대기 후 상태를 다시 묻는다. 요청이 끝난 다음 대기하므로 실제 요청 사이 간격에는 네트워크 시간도 포함된다. 서버가 같은 상태를 반환하면 화면도 그 상태를 유지한다.

현재 서버의 `pollAfterMs: 400`은 안내값이며 프론트는 이를 읽어 간격을 바꾸지 않고 자체 400ms를 사용한다. 서버가 간격을 제어하게 하려면 프론트가 이 값을 검증하고 적용하도록 수정한다.

실제 연결 시 `jobProgress(startedAt)`을 경과 시간으로 계산하는 방식을 제거한다. `analysis_jobs`에 실제 상태·단계·완료 결과·오류를 보관하고 AI 작업자/콜백이 상태를 갱신하도록 구성한다. 현재 테이블은 시작 시각과 오류만 있으므로 실제 작업에 필요한 스키마와 마이그레이션도 작성해야 한다.

단계 완료 신호가 없으면 파일 확인·활동 비교를 완료했다고 임의로 표시하지 않는다. 실제 서버가 최종 결과만 제공한다면 일반 대기 또는 확인 가능한 작업 상태만 사용한다.

## 5. 현재 비동기 API 계약을 유지하는 경우

파일 전송은 다음 계약을 사용한다.

1. `POST /api/chat`: FormData `message`, 반복 `files`, `conversationId`, 헤더 `Prefer: respond-async`.
2. 접수: HTTP 202, `{ jobId, status: running, progress, analysisProvider }`.
3. 조회: `GET /api/chat/jobs/:jobId`.
4. 처리 중: `{ jobId, status: running, progress }`.
5. 완료: `{ jobId, status: completed, result: { analysisId, conversationId, reply, ... } }`.
6. 실패: `{ jobId, status: failed, error }`.

`progress`는 `{ title, steps: [{ label, status }] }`이며 단계 상태는 현재 `working` 또는 `completed`다. `queued`, `pending`, 퍼센트 등 새로운 상태를 사용하려면 프론트 검증·타입·진행 컴포넌트도 함께 확장한다.

텍스트 전용은 현재 동기 응답이다. 백엔드가 텍스트도 같은 비동기 계약으로 응답하면 서비스는 작업 ID 경로를 사용할 수 있지만, 실제 계약과 화면 표시를 함께 검증해야 한다.

정식 백엔드가 다른 경로·필드·상태를 쓰면 서비스에서 위 화면용 구조로 변환한다. SSE/WebSocket을 쓰기로 했다면 폴링 부분을 해당 구독 방식으로 교체하고 연결 해제·재접속도 처리한다.

### 오래 걸리는 작업과 취소

시간 제한을 단순히 늘릴 수도 있지만 작업 ID로 이어서 확인하는 흐름을 함께 정하는 것이 좋다. 현재 프론트는 접수된 작업 ID를 sessionStorage에 보관하고 새로고침·홈 재진입 시 조회를 재개한다. 실패하면 ID를 유지하고 재확인 버튼을 제공한다. 작업 ID를 받기 전 업로드 중단은 복원하지 않는다. 실제 서버 연결 시 작업 보존 기간·인증 만료·작업 소유권과 조회 계약을 이 흐름에 맞춘다.

현재 초기화·화면 이동은 브라우저 요청과 폴링만 취소한다. 이미 접수된 서버 작업이나 원본 파일을 삭제하지 않는다. 실제 AI 작업까지 취소하려면 작업 취소 API와 AI 처리 취소/결과 무시 정책을 별도로 구현한다.

## 6. 아카이브 저장·수정·DB 전환

후속 구현: 나의 발자국 목록·상세·자료 Drawer·Project Timeline은 개발용 SQLite의 확정 기록을 조회한다. `/api/archive/activities` 계열 API와 기존 DB 보존 마이그레이션은 [DB 연동 안내](../../footprints/DB_연동.md)를 참고한다. 실제 AI·Growth Journey 분석은 별도 작업이다.

분석 완료와 사용자 기록 확정은 구분한다. 작업 완료만으로 아카이브 기록을 자동 추가하지 않는다.

| 현재 API | 역할 |
| --- | --- |
| `GET /api/activities` | 실제 사용자 활동 목록으로 교체할 대상 |
| `POST /api/records` | 초안 ID 또는 카드 JSON을 활동 기록으로 확정 |
| `PATCH /api/records/:id` | 저장한 활동·분류 등 수정 |
| `GET /api/activities/:id/records` | 활동의 확정 기록 조회 |
| `GET /api/activities/:id/timeline` | 변화 이벤트 조회 |

홈 저장 요청의 `analysisId`는 서버 원본 파일과 연결된다. 저장 전 수정값은 `activityId`, `classification.materialType`으로 확정한다. 직접 `reply` 저장은 서버의 개발 계약으로 남아 있다. 운영에서 임의 JSON 저장을 허용할지는 백엔드 계약으로 정한다.

기록과 변화 이벤트는 한 트랜잭션으로 저장한다. 변화가 없으면 자료만 저장하고 Timeline 이벤트는 만들지 않는다. 현재 `isTurningPoint`는 항상 false인 목 정책이므로 실제 AI/사용자 판단에 따른 저장 구조를 추가해야 한다. Growth Journey 분석과 해당 화면의 DB 조회는 아직 연결하지 않았다.

홈 저장 상태·기록 ID는 sessionStorage에서 복원한다. 정식 연결 시 사용자별 기록 ID·중복 요청 키·저장 여부를 서버에서 조회/복원하도록 정한다. 같은 초안의 중복 저장은 현재 409로 막는다.

SQLite 교체가 필수는 아니다. 정식 DB를 쓰기로 했다면 `api-server/src/database.js`와 `app.js`의 SQL 접근을 새 DB 계층으로 바꾸고 기존 파일·초안·기록·작업의 이관 여부를 정한다. 활동 5개 자동 시드는 실제 사용자 활동 조회로 바꾼다.

파일 저장을 DB BLOB 대신 별도 저장소로 옮기면 업로드·파일 ID·다운로드 URL·접근 권한·분석 서버 전달 방식을 함께 변경한다. 파일 제한도 현재 프론트와 Multer 양쪽의 10개/각 10MiB 및 프록시 제한을 맞춘다.

## 7. 전환 작업 순서와 확인

1. 정식 백엔드·AI의 역할과 API 계약을 확정한다. URL, 인증, 파일 필드, 작업 ID, 진행·오류·최종 응답, 저장·수정 구조를 정한다.
2. 백엔드의 실제 분석 작업과 DB 상태 갱신을 구현하고 서버 단독으로 검증한다.
3. 프론트 기본 주소·서비스 변환·검증·시간 제한을 맞춘다.
4. 실제 입력 → 진행 → 분석 결과 → 사용자 수정 → 기록 확정 → 저장 후 수정을 검증한다.
5. 아카이브·Timeline 화면과 저장 상태 복원을 실제 조회에 연결한다.

현재 검증 명령:

```powershell
# 프로젝트 루트
npm.cmd run build
npm.cmd run lint
node scripts/check-chat-api.mjs

# api-server 폴더
npm.cmd test
```

현재 통합 스크립트는 로컬 목 서버와 임시 SQLite를 실행한다. 명령이 통과해도 정식 서버 연동을 검증한 것은 아니다. `progress.test.js`의 시간 경계와 통합 스크립트의 고정 카드·이벤트 개수 기대값은 실제 계약에 맞춰 바꾼다.

실제 연결에서는 오래 걸리는 분석, 작업 실패, 네트워크 단절 후 조회 재개, 중복 저장, 인증 만료, 다른 사용자 파일 접근 차단, 새로고침 후 상태 복원도 확인한다. 브라우저에서 진행 카드·수정 모달을 직접 확인한 결과는 자동 API 검사와 구분해서 기록한다.
