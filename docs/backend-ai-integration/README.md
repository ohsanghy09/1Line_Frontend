# 백엔드·AI 분리 서버 연동

작성일: 2026-11-13 · 상태: Spring 인증·홈 내부 API·활동 분석·파일 삭제 재분석 전달 구현, 로컬 테스트 47개·JAR 빌드 완료. AI 적용·실제 연동 미확인

## 목적과 범위

Spring 백엔드에 남아 있는 공유 DB 기반 AI 연동을 HTTP 데이터 전달 방식으로 변경한다. 백엔드와 AI가 별도 DB를 사용해도 홈 분석·확정 저장·활동 정보 갱신·자료 삭제가 동작하도록 한다.

이 폴더는 작업 계획과 진행 기록을 관리한다. API 규격은 [서버 간 데이터 전달 계약](../common/handoff/서버간_데이터_전달_계약.md)을 기준으로 하며, 계약 변경이 필요하면 원본 문서와 관련 OpenAPI도 함께 갱신한다. Journey는 [최신 공통 JSON 계약](../growth-journey-update/공통_JSON_계약.md)이 우선한다.

관련 이슈 제목: `feat: 백엔드·AI 분리 서버 연동 및 내부 인증 구현`

## 조사 시점의 차이와 진행

| 항목 | 현재 Spring 코드 | 변경 방향 |
| --- | --- | --- |
| 활동 정보 분석 | Spring의 활동·기존 정보·기록·파일 메타정보·기록 수·해시 JSON 전달 구현 완료 | AI 측 JSON 수신 구현과 실제 연동 확인 필요 |
| 파일 일부 삭제 후 재분석 | Spring의 삭제 대상 ID·삭제 전 기록 응답·활동 정보·남은 실제 원본 전달 구현 완료 | AI 측 JSON 수신·남은 원본 분석과 실제 연동 확인 필요 |
| 홈 분석 데이터 전달 | Spring의 문맥 조회·작업 게시/재조회 구현 완료 | AI 측 호출 구현과 실제 연동 확인 필요 |
| 서버 간 인증 | 조사 당시 Authorization 헤더 없음. 이후 Spring 송신·수신 구현 | AI 측 적용과 실제 HTTPS 연동 확인 필요 |

코드 조사 근거와 한계는 [작업 및 검증 기록](작업_및_검증_기록.md)에 남긴다. 실제 AI 서버의 현재 구현은 이 조사로 확인하지 않았다.

## 작업 목록과 담당

### 1. 서버 간 인증

- [ ] 백엔드·AI 담당자 중 한쪽이 암호학적으로 안전한 무작위 토큰을 생성해 안전하게 공유한다.
- [ ] 양쪽 서버 환경변수에 `INTERNAL_SERVICE_TOKEN`을 설정한다.
- [ ] 백엔드 → AI, AI → 백엔드 내부 요청에 `Authorization: Bearer <INTERNAL_SERVICE_TOKEN>`을 추가한다.
- [ ] 수신 서버에서 토큰을 검증하고 누락·오류는 401, 인가 범위 위반은 403으로 처리한다.
- [ ] 실제 서버 통신에 HTTPS를 적용한다. 토큰은 Git·문서·로그·프론트 환경변수에 기록하지 않는다.

Spring 적용: 환경변수 검증, 세 AI 호출의 Bearer 헤더, 내부 경로 인증 필터와 홈 내부 컨트롤러를 구현했다. 설정 누락은 서버 시작 오류이며, 공개 프론트 API에는 토큰을 요구하지 않는다. 위 인증 체크리스트는 양쪽 서버·배포 적용까지 완료한 경우에 체크한다.

현재 계약은 공유 Bearer 토큰 방식이다. 별도 JWT 발급이나 토큰을 해시해서 보내는 방식은 요구하지 않는다. 사용자 로그인·사용자별 접근 제어는 별도 계약이며 서버 간 토큰으로 대체하지 않는다.

### 2. 홈 분석 내부 API

백엔드 담당:

- [x] `GET /api/internal/home-context?conversationId=...`: 기존 활동·확정 기록·최근 대화·현재 활동 문맥 반환.
- [x] `PUT /api/internal/chat-jobs/:jobId`: 접수·진행·완료·실패 상태와 초안·원본을 영속 보관.
- [x] `GET /api/internal/chat-jobs/:jobId`: 정본 작업 스냅샷 반환.
- [x] requestId·입력 fingerprint 기반 중복 방지와 expectedRevision·revision 충돌 처리.
- [x] 사용자 확정 저장과 활동 직접 수정에서 동일 analysisId의 완료 초안·원본 조회.
- [x] 삭제·직접 수정 이후 정본 reply와 revision 갱신, 진행 중 삭제 충돌 및 재시작 복구 처리 (단일 백엔드 기준).
- [x] 원본의 base64 증가분을 수용하는 내부 PUT 본문 40MiB 한도 적용. 공개 JSON은 1MiB 유지.

Spring 로컬 검증 완료이며 실제 AI 연결 완료를 뜻하지 않는다. [접수·완료 교환 예시](examples/home-job-exchange.json)를 제공한다. 최초 expectedRevision=0으로 게시하고 반환 revision으로 후속 갱신한다. 409면 GET으로 정본을 확인하며, 완료 게시 저장 확인 후에만 공개 completed를 반환한다.

원본·초안·상태는 기존 analyses·files·ai_chat_jobs를 사용한다. 추가 테이블에는 버전·중복 검증값을 보관한다. 전체 삭제 후 원본·초안·작업은 지우고 재전송 방지용 ID 해시만 유지한다. 기동 시 미완료 작업은 failed로 복구하므로 여러 백엔드 인스턴스의 병행 기동에는 복구 소유권·리스가 추가로 필요하다. 사용자 인증·사용자별 데이터 범위는 기존처럼 별도 계약이다.

AI 담당:

- [ ] 분석 전에 백엔드의 홈 문맥 조회 API 호출.
- [ ] 접수·진행·완료·실패 데이터와 원본 게시.
- [ ] 백엔드의 완료 게시 영속 확정을 확인한 뒤 프론트에 completed/result 반환.
- [ ] 작업 재조회 시 백엔드 정본 또는 동일 revision이 확인된 캐시 사용.

초안·원본 보관은 활동의 정식 기록 저장과 구분한다. 활동 생성·확정 records 저장은 사용자가 카드에서 저장을 선택한 뒤 백엔드가 수행한다.

### 3. 활동 정보 분석 요청

- [x] 백엔드: `POST /api/analyze/activities/:activityId`에 activity·previous·records·files·recordCount·sourceFingerprint 전달.
- [ ] AI: 자체 DB 조회 대신 전달받은 문맥으로 활동 전체 요약·역할·상태·기간을 분석하고 근거와 요청 해시 반환.
- [x] 백엔드: 분석 전·저장 직전 스냅샷, AI 반환 해시·기록 수·원문 근거 검증 후 저장 (로컬 검사).
- [x] 실패 시 저장된 자료와 기존 활동 정보 보존 (로컬 검사).

이 요청의 files는 원본 bytes가 아닌 기록·파일 관계와 이름 메타정보다.

Spring은 기존 스냅샷 정렬·해시를 유지해 records의 id/message/summary/changes/savedAt/updatedAt을 전달한다. previous는 summary/status/role/start_date/end_date 키를 모두 포함하며 미설정 값은 null이다. 100개 초과 또는 직렬화 JSON 250000 코드 포인트 초과는 AI HTTP 호출 전에 실패 처리한다. 수동 요청의 기존 202 접수·상태 조회 흐름은 유지하며 자동 분석도 같은 본문을 사용한다. AI는 받은 해시를 재계산하지 않고 그대로 반환해야 한다. 실제 모델 품질·원격 호출 성공은 미검증이다.

### 4. 파일 일부 삭제 후 재분석

- [x] 백엔드: `POST /api/analyze/records/:recordId/exclude-file`에 fileId·recordReply·activity·남은 files 원본 전달.
- [ ] AI: 삭제 대상 원본을 제외하고 남은 파일만 분석. recordReply는 모델 입력에 사용하지 않고 그대로 반환.
- [x] 백엔드: 반환된 파일 ID·기록 응답·분석 결과·동시 변경 여부 검증 (로컬 검사).
- [x] 성공 시 원본 삭제와 기록 분석 결과 교체를 원자적으로 반영 (로컬 검사).
- [x] 재분석 실패·입력 불일치·동시 변경 시 기존 자료와 결과 보존 (로컬 검사).

예: 같은 기록에 A·B·C가 묶여 있을 때 A 삭제 요청은 A의 ID와 B·C 원본을 전달한다. AI는 B·C만 분석하고 실제 삭제는 백엔드가 한다. 다른 기록으로 각각 저장된 파일까지 함께 재분석하지 않는다. 남은 파일이 없는 경우에는 해당 재분석 호출 없이 삭제 정책을 적용한다.

files는 저장 순서대로 id/name/mimeType/실제 size/contentBase64를 담는다. 원본의 실제 bytes와 저장된 크기·개수·업로드 한도를 AI 호출 전에 확인하고 불일치 시 삭제하지 않는다. activity는 id/name/category만 전달한다. recordReply는 기록의 JSON 원문을 그대로 보내며 AI는 재직렬화하지 않고 응답에 그대로 돌려준다. AI 모델 입력에는 남은 원본과 현재 활동만 넣고 recordReply·이전 대화·삭제 대상 원본은 넣지 않는다. AI 수신 서버·프록시는 25MiB 원본의 base64 증가분과 recordReply·메타정보를 수용해야 한다.

Spring의 계획한 네 구현은 로컬 검증을 완료했다. AI 측 연결·인증/주소 설정·실제 원격 브라우저 검증과 배포는 아래 완료 조건에 따라 별도로 진행한다.

## 프론트와 Journey 범위

- 위 네 작업은 기존 프론트 공개 API 경로·본문·응답을 유지하는 방향으로 구현한다. 프론트가 남은 파일을 재업로드하거나 내부 API를 직접 호출하지 않는다.
- 프론트 수정은 실제 연동에서 발견한 계약 차이를 근거로 판단한다. 이번 조사에서는 위 네 작업 때문에 필수인 프론트 요청 변경을 확인하지 않았다.
- Journey는 Spring·프론트가 `journey-result-v2`·`growth-criteria-v1`·`journey-v6` 기준을 적용한 상태다. AI의 동일 계약 지원 여부와 실제 연동은 별도로 확인한다.
- 배포 프론트의 재배포는 기존 방침대로 사용자가 진행한다.

## 진행 순서와 완료 조건

1. 내부 계약·인증·원본 전달 방식과 서버 설정을 양쪽에서 확인한다.
2. 인증과 홈 내부 API를 구현하고 AI 게시·재조회를 연결한다.
3. 활동 분석·남은 파일 분석의 요청 본문과 AI 처리를 수정한다.
4. 서버 간 통합 검사를 수행한 뒤 프론트에서 전체 흐름을 검증한다.

- [ ] 공유 DB 없이 홈 분석 → 카드 표시 → 사용자 확정 저장 성공.
- [ ] 기존 활동 문맥 조회, 활동 직접 수정·작업 재조회 정본 일치 확인.
- [ ] 자료 저장 후 활동 정보 분석·갱신 성공.
- [ ] A·B·C 중 A 삭제 후 B·C 기준으로 결과 갱신.
- [ ] 인증 실패·게시 실패·재분석 실패·중복 요청·revision 충돌·동시 변경 시 잘못된 완료나 데이터 손실 없음.
- [ ] 삭제·재시작 후 오래된 초안과 결과가 부활하지 않음.
- [ ] 실제 HTTPS·CORS·원본 전송 한도·시간 제한 확인.
- [ ] 기존 공개 API를 사용하는 프론트의 저장·조회·삭제·복원·화면 갱신 확인.
- [ ] 검사 환경·실행 결과·미확인 항목을 작업 기록에 남김.
