# 프론트 기능 및 동작 명세서

작성일: 2026-11-09 · 이슈: #17 · 대상: 현재 `src/` 구현

## 1. 문서의 기준과 확인 범위

이 문서는 현재 프론트의 사용자 기능과 실제 코드 흐름을 보존하기 위한 명세서다. 신규 기능 제안이나 handoff에 맞춘 기능 변경 지시가 아니다. 현재 기능을 완성된 범위로 취급하며 리팩토링에서도 동작을 보존한다. handoff와 충돌하거나 원격 연동 시 기능 손상이 예상되면 [작업 기준](README.md)에 따라 사용자에게 보고하고 해당 기능을 임의로 변경·제거하지 않는다.

조사 범위는 등록된 전체 화면 5개, 공통 화면·설정, `src/components/` 전체, 서비스 7개, hook 1개, 유틸리티·타입 및 관련 기존 검사다. 실행 코드의 조건·호출·상태 갱신을 근거로 작성했다. 오래된 주석이나 타입 선언만으로 실제 화면 동작을 확정하지 않았다. 화면의 삭제 안내는 서버에 요구하는 동작이며 서버의 실제 원자성까지 프론트 코드로 입증한 것은 아니다.

| 구분 | 이번 확인 수준 |
| --- | --- |
| 경로·버튼·조건부 화면·API 호출·상태·저장소 | 현재 코드에서 확인 |
| 세션 직렬화·손상 처리·중복 카드 방지 | 기존 독립 검사 실행 통과 |
| 확정된 작업 실패와 통신 실패 구분 | 기존 합성 fetch 검사 실행 통과 |
| 최근 시각 표시 | 기존 검사 3개 실패. 실행 환경의 AM/PM 표기 차이, 15절 참조 |
| 브라우저 클릭·레이아웃·초점·화면 전체 시나리오 | 이번 실행 검증 안 함. 아래 동작은 코드 기준 |
| 서버의 실제 DB·파일 저장·삭제·AI 분석 품질·내부 전달 | 이번 검증 안 함 |
| 실제 원격 HTTPS·CORS·인증 | 이번 범위 밖 |

완전성을 확인할 수 있도록 기능 식별자, 코드 근거, API 목록, 미검증 범위를 함께 기록한다. 실행하지 않은 동작을 검증 완료로 표시하지 않는다.

사이드바의 사용자명 `김성장`은 정적 표시다. 로그인·프로필 수정 기능으로 해석하지 않는다. 활동 수는 백엔드 활동 목록 길이이며 최초 조회 전/최초 실패 시 예시 숫자를 만들지 않는다. 재조회 실패 시 이전 수가 남을 수 있다.

## 4. 홈 입력·분석·복원

근거: [Home.tsx](../../src/pages/Home.tsx), [chat.ts](../../src/services/chat.ts), [LinkInputModal.tsx](../../src/components/chat/modals/LinkInputModal.tsx).

### HOME-01 — 텍스트 전송

- 단일 행 입력창에서 보내기 또는 Enter로 제출하며 앞뒤 공백을 제거한다. 한글 조합 확정 중 Enter는 제출하지 않는다.
- 텍스트도 파일도 없으면 전송하지 않는다. 요청 중 또는 미해결 pendingJob이 있으면 중복 전송을 차단한다.
- 사용자 말풍선과 전송 시각을 먼저 추가한 뒤 입력·전송 파일을 비운다. 응답 대기 중에도 다음 글 작성·파일 첨부는 가능하지만 전송은 차단한다.
- AI `POST /chat` multipart에 message, requestId, conversationId를 넣는다. 파일 없는 요청은 `Prefer: respond-sync`, HTTP 제한 150초다.
- 파일 없는 응답이 jobId를 포함하면서 completed/failed가 아니면 미완료 오류로 처리한다. 파일/링크용 진행 콜백은 텍스트에서 숨긴다.
- AI 완료가 오면 검증된 reply를 도착 시각과 함께 추가한다. 일반 대화인지 분석 카드를 표시할지는 응답 데이터로 결정한다.

### HOME-02 — 파일 첨부·전송

- 클립 선택창은 다중 선택 가능하며 여러 번 추가할 수 있다. 같은 이름도 첨부 ID로 구분한다. 선택한 파일은 바로 전송하지 않는다.
- 드롭은 채팅 하단 입력 영역에서 Files 드래그만 처리한다. 드롭 위치를 강조하고 브라우저의 파일 열기를 막는다. 일반 텍스트 드래그는 그대로 둔다.
- 전송 전 목록에서 파일별 삭제가 가능하다. 같은 파일 재선택을 위해 파일 input 값을 선택 후 비운다.
- 텍스트 없이 파일만 전송하거나 텍스트와 파일을 함께 전송할 수 있다. 전송한 실제 파일명은 사용자 말풍선에 표시하며 여러 파일은 개수와 이름 목록을 표시한다.
- 서비스에서 텍스트 20000자, 파일 최대 10개, 개별 10MiB 초과를 거절한다. 현재 프론트는 합계 크기·0바이트·확장자·MIME 제한을 사전 검사하지 않고 서버 오류를 받는다. 선택 input에 accept 제한도 없다.
- 파일을 반복 `files` 필드로 전송하며 `Prefer: respond-async`, 접수 HTTP 제한 30초다. multipart Content-Type/boundary는 브라우저가 생성한다.
- UI는 서비스 검증 전에 말풍선을 추가한다. 사전 검증 실패라도 전송 내역이 보이고 오류 후 입력·파일을 복원할 수 있다. 실제 서버가 접수했다는 의미는 아니다.

### HOME-03 — 링크 입력

- 링크 모달은 HTTP/HTTPS, 길이 4096자 이하, 사용자명·암호가 없는 URL을 허용한다. 안내 문구는 GitHub/ChatGPT 예시지만 프론트의 도메인 허용 목록은 없다.
- 분석 시 URL을 trim하고 모달을 닫아 사용자 말풍선을 추가한다. AI `POST /chat/links` JSON에 url, conversationId, 매번 생성한 requestId를 보낸다.
- 기존 채팅 입력 글과 전송 전 첨부는 유지한다. 마지막 제출 링크는 linkDraft로 남지만 제출하지 않고 닫은 편집 내용은 모달 해제 시 유지되지 않는다.
- 대기 중·미해결 작업이 있으면 링크 열기 버튼을 비활성화한다. 결과 진행·재조회는 파일과 같은 처리다.
- 링크 검증 오류는 모달 안에 표시하고 입력 수정 시 지운다. 취소·닫기·Escape를 지원한다.

### HOME-04 — 대기·진행·완료

- 진행 정보 전에는 Bot 아이콘과 점 3개를 표시한다. 파일·링크에서 서버 progress가 오면 제목과 completed/working 단계로 바꾼다.
- jobId가 오면 pendingJob에 작업 ID, 연결 사용자 메시지 ID, 진행 표시 여부를 보관한다.
- 동일 jobId인지 매 응답을 확인한다. running은 올바른 progress를 요구하며 400ms를 기다린 뒤 순차 재조회한다. 서버 pollAfterMs 값을 대기 시간으로 사용하지는 않는다.
- 폴링 전체 제한은 120초이며 개별 GET 제한은 기본 30초다. 사용자 취소 신호와 timeout을 결합한다.
- completed는 result를 최종 검증한다. 같은 reply.id 또는 같은 analysisId의 카드는 다시 추가하지 않는다.
- ready/unavailable 상태 배지는 홈 진입 시 AI `GET /chat/health`로 따로 조회한다. 조회 전은 상태 확인 중, 실패는 상태 확인 실패다. 이 배지 상태만으로 전송 버튼을 차단하지 않는다.

### HOME-05 — 실패·시간 초과·재조회

- failed 작업은 error·code와 terminalChatJob 표시를 가진 오류로 변환한다. 확정 실패는 pendingJob을 해제해 다음 입력을 허용한다.
- 작업 접수 전 실패 또는 확정 실패한 일반 입력은 입력 글·파일을 복원한다. 사용자가 새로 작성한 글은 덮어쓰지 않고 파일은 기존 대기 파일 앞에 복원한다. 전송 말풍선은 남는다.
- 작업 ID를 받은 뒤 통신 실패·폴링 제한 등 불확실한 실패는 pendingJob을 유지하고 새 전송을 막는다. 사용자는 ‘진행 상태 다시 확인’으로 기존 작업을 조회한다. 파일을 자동 재전송하지 않는다.
- 링크는 일반 입력 복원 대상이 아니며 제출한 linkDraft를 다시 열어 활용할 수 있다.
- 활동 직접 수정 적용의 400/404/409/422는 확정 거절로 분류한다. 통신 실패는 재조회로 확인한다.
- 재조회 실패·중단과 서버 작업 취소는 다르다. Abort는 프론트 대기/반영을 중단하며 서버의 분석·저장 취소 API를 호출하지 않는다.

### HOME-06 — 탭 대화 복원

근거: [chatSession.ts](../../src/utils/chatSession.ts).

- 홈 최초 마운트에 sessionStorage `1line.home-chat.v1`을 읽는다. version=1, conversationId, 인사 시각, messages, pending, pendingJob을 저장한다.
- 메시지 ID 중복·역할·본문·시각·첨부 표시 정보·reply·선택 ID를 검증한다. 잘못된 JSON·버전·카드·작업 연결은 세션 전체를 무효로 보고 새 대화로 시작한다.
- 일반/분석 카드, 저장 ID, 연결 활동, 분류 수정값, 시각·첨부 이름을 복원한다. File 원본, 전송 전 첨부, 입력 중 글, 링크 초안, 오류 문구, AbortController는 보관하지 않는다.
- pendingJob이 있으면 홈 재진입 시 기존 작업을 자동 조회한다. pending만 있고 작업 ID가 없으면 자동 재전송하지 않고 중단 안내를 표시한다.
- ai- 접두사 작업은 AI에, 그 외 과거 작업은 백엔드 `/chat/jobs/:id`에 조회한다. 이전 세션 호환 분기이므로 계약에 없다는 이유로 제거하지 않는다.
- 저장소 접근 차단·용량 초과 시 대화는 계속 사용하고 보관 실패 경고를 표시한다. 서버 영속 기록과 탭 화면 복원은 별개다.

### HOME-07 — 대화 초기화와 화면 이탈

- 초기화는 링크 모달·대기 작업·메시지·입력·첨부·진행·오류·드래그 상태를 비우고 새 conversationId와 인사 시각을 만든다. 빈 대화가 같은 세션 키에 다시 기록된다.
- 요청을 abort하고 요청 순번을 증가시켜 초기화 전 늦은 응답을 화면에 추가하지 않는다. 서버 기록·원본·작업 삭제를 요청하지 않는다.
- 홈 이탈·StrictMode 재실행에서도 이전 요청 반영을 차단한다. 이탈 후 서버 작업은 계속될 수 있다.

### HOME-08 — 메시지 표시·시각

- 사용자와 AI 메시지는 같은 배열의 순서를 유지한다. 응답은 서버 createdAt 대신 화면 도착 시각을 저장하며 카드 수정 시 기존 메시지 ID·표시 시각을 유지한다.
- 메시지·대기·오류·진행 변경 시 채팅 영역 하단으로 스크롤한다. 현재 시각은 30초마다 갱신한다.
- 메시지는 1분 미만 ‘방금 전’, 60분 미만 ‘N분 전’, 이후 당일 오전/오후 시각, 다른 날 월일과 시각(연도가 다르면 연도 포함)을 표시한다. hover title에 정확한 현지 시각, time에 ISO 시각을 둔다.
- 사용자 말풍선은 최대 80%, 결과 카드는 기본 85%·sm 이상 80%다. API 문자열은 React 텍스트로 표시한다.

## 6. 기록 저장·분류 수정·활동 직접 수정

근거: [ConnectedChatReplyCard.tsx](../../src/components/chat/ConnectedChatReplyCard.tsx), [records.ts](../../src/services/records.ts), [ActivityReviewModal.tsx](../../src/components/chat/modals/ActivityReviewModal.tsx).

### RECORD-01 — 저장 상태와 중복 방지

카드별 reply, recordId, activityId, 처리 중 상태·오류·안내를 관리한다. ref 잠금으로 저장/수정의 중복 실행을 막고, 저장 완료 버튼은 비활성화한다. 저장 성공 전에는 저장 완료라고 표시하지 않는다. 실패는 카드 또는 열린 수정 모달에 표시하며 성공 안내와 구분한다.

`saveRecord`는 선택 대상, analysisId(없으면 직접 reply 분기), classification.materialType을 보낸다. 응답의 id·activityId·reply를 검증한 뒤 두 변경 이벤트를 발생시키고 카드에 기록 ID를 반영한다. 서비스에 직접 reply 저장 분기가 있다는 사실과 실제 일반 화면에서 도달 가능한지는 별개이며 추가 추적 없이 불필요하다고 판정하지 않는다.

### RECORD-02 — 새 활동 또는 기존 활동 저장

- match=new는 명시적 클릭으로 newActivity{name,category,status:null,role:null,period:null,summary:null}와 함께 저장한다. 활동명·분류 제안과 사용자 확정 저장을 구분한다.
- 기존 활동 저장은 최신 활동 목록을 가져와 카드에서 선택한 ID 또는 분석의 실제 기존 ID를 확인한다. 이름으로 ID를 추측하지 않는다.
- 저장 대상 ID가 없거나 목록에서 사라졌으면 선택 영역을 열고 사용자가 기존 활동을 지정하게 한다. 선택 후 저장 직전에도 목록을 다시 확인한다.
- 기존 대상 category가 비어 있고 분석 제안 category가 있으면 저장 요청에 해당 category와 나머지 null의 activityUpdates를 추가한다.
- 기존 연결 선택은 취소 가능하다. 기존 활동이 없으면 안내를 표시하며 unresolved를 임의 활동에 저장하지 않는다.
- 성공하면 recordId/activityId와 서버 reply를 카드·부모 메시지에 반영하고 선택/수정 화면을 닫으며 ‘아카이브에 저장했어요.’를 표시한다.

### RECORD-03 — 저장 전 분류 수정

- 수정 또는 ‘다른 활동 선택’은 최신 활동 목록을 로드한 뒤 ActivityReviewModal을 classificationOnly=true로 연다.
- 실제 활성 모달은 기존 활동 선택과 자료 유형 입력만 제공한다. 신규 생성·활동명/상태/역할/기간/전체 요약 편집 UI는 이 호출에서 노출하지 않는다.
- 두 값이 있어야 적용할 수 있고 자료 유형을 trim한다. 변경된 활동으로 본문 활동명을 치환하고 파일 materialType·그룹도 맞춘다.
- 미저장 카드에서는 서버 PATCH 없이 로컬 카드·세션의 선택과 분류만 바꾼다. 별도 저장 버튼을 눌러야 기록이 생성된다.

### RECORD-04 — 저장 후 수정·복구

- 저장된 카드는 기존 활동과 자료 유형을 `PATCH /records/:id`로 수정한다. 현재 실제 카드 호출은 선택 activityUpdates를 전달하지 않는다.
- PATCH 성공 응답을 반영하고 최근 목록·활동 수 등 갱신 이벤트를 발생시킨다. 저장 완료 이후에도 수정 버튼은 사용할 수 있다.
- recordId가 있는 카드의 마운트 및 `1line:records-changed`에서 `GET /records/:id`를 호출해 서버의 reply와 연결 활동을 확인한다.
- 404는 기존 본문에 ‘이 기록은 삭제했어요.’를 붙인 general 카드로 바꾸고 로컬 recordId/activityId를 비운다. 다른 조회 오류는 현재 카드를 유지하며 별도 오류를 띄우지 않는다.
- 이 재조회는 카드 내부 상태를 갱신하며 부모 onChange를 호출하는 경로와 다르다. 부모 세션 값이 항상 즉시 동기화된다고 보장하지 않는다.

### RECORD-05 — 대화로 활동 정보 직접 수정

AI 완료 result.reply.kind=activity-update이면 프론트는 값이나 SQL을 실행하지 않는다. 백엔드 `POST /activities/apply-chat-update`에 analysisId만 전송하고 응답을 최종 검증한다. general 완료 reply와 updatedActivityId가 있으면 활동 변경 이벤트를 발생시킨다. 이 일반 응답에는 새 기록 저장 버튼을 표시하지 않는다.

## 7. 홈 최근 목록과 활동 정보 분석

근거: [useHomeRecent.ts](../../src/hooks/useHomeRecent.ts), [home.ts](../../src/services/home.ts), [ActivityAnalysisStatus.tsx](../../src/components/ActivityAnalysisStatus.tsx).

### RECENT-01~02 — 최근 활동·최근 자료

홈 진입·활동 변경 이벤트·재시도에서 `GET /home/recent`를 호출한다. 새 요청 시 이전 요청을 취소하고 데이터를 비워 로딩 상태로 전환하며 최신 응답만 반영한다. 로딩·오류·빈 목록·정상 목록을 구분하고 재시도 버튼을 제공한다.

최근 활동은 활동 상세로, 최근 기록은 해당 활동의 `?file=자료ID`로 이동한다. 기록의 id는 자료 이동용이며 recordId와 구분한다. 서버가 순서·최대 개수를 결정하고 프론트는 받은 배열을 다시 정렬하거나 3개로 자르지 않는다. file/text/link 아이콘을 지원한다.

최근 목록 시각은 오늘 시각, 어제+시각, 그 이전 YYYY.MM.DD로 표시하며 브라우저 현지 날짜 기준이다. 메시지 상대 시각 함수와 다르고 Intl 표기 환경의 영향을 받는다.

### META-01 — 활동 종합 상태·재분석

- 저장된 카드 및 기록이 있는 활동 상세에서 상태 컴포넌트를 제공한다. GET은 상태를 조회하고 POST /analyze는 사용자 재분석 요청이다.
- 상태는 idle/queued/running/ready/failed, error·updatedAt은 null 허용, stale은 boolean이다.
- 조회 중·재분석 중·queued/running은 정리 중 안내. queued/running만 1500ms 후 순차 재조회한다.
- 실패 또는 stale이면 오류/갱신 안내와 ‘활동 정보 다시 분석’을 표시한다. ready이고 stale이 아니면 종합 완료 안내, idle이고 stale이 아니면 별도 문구를 표시하지 않는다.
- 상태 조회 오류는 ‘상태 다시 확인’, 재분석 실패는 오류로 표시한다. 기록 저장 성공과 활동 분석 실패를 혼동하지 않는다.
- 진행을 본 뒤 종료하거나 ready를 받으면 activities-changed를 알린다. records-changed를 받으면 상태 조회를 다시 시작한다. 해제 시 타이머와 GET을 취소한다.

## 8. 발자국 검색·상세·자료

근거: [Footprints.tsx](../../src/pages/Footprints.tsx), [ActivityArchive.tsx](../../src/pages/ActivityArchive.tsx), [footprints.ts](../../src/services/footprints.ts).

### ARCHIVE-01 — 검색·필터·정렬

- 초기 조건은 search='', category=all, status=all, sort=recent다. q/category/status/sort를 URLSearchParams로 인코딩해 서버 검색 API에 보낸다.
- 검색은 최대 500자, 입력 변경 즉시 요청한다. debounce나 조합 종료 대기는 없다. 검색·유형·상태·정렬은 함께 전달하며 프론트가 자료 내용을 재검색하지 않는다.
- 유형은 서버 categories에 ‘전체’를 추가한다. 선택한 유형이 새 응답에서 사라지면 all로 복귀해 다시 조회한다.
- 상태 선택은 전체/진행 중/완료, 정렬은 최근 업데이트/자료 많은 순/오래된 업데이트 순이다. 실제 정렬은 서버 책임이다.
- 이전 요청을 abort하고 최신 조건 응답만 사용한다. 최초 로딩과 재조회 중 로딩을 구분한다. 재조회 중 기존 목록은 흐리게 표시하고 inert로 클릭·키보드 접근을 막는다.
- total=0이면 기록 없음, total>0이고 items=[]이면 조건 결과 없음으로 구분한다. total은 서버 계약상 필터 전 전체 수이며 프론트는 total>=items.length를 검사한다.
- 오류는 다시 불러오기 버튼을 제공한다. 활동 변경 이벤트 또는 표시 목록에 queued/running이 있을 때 1500ms 후 재조회한다.

### ARCHIVE-02~03 — 활동 상세·폴더

활동 ID 변경 시 하위 컴포넌트를 새로 만들며 조회·펼침 상태를 초기화한다. GET 응답 ID와 요청 ID를 대조하고 404만 없음으로 변환한다. 로딩·일반 오류·활동 없음·정상을 구분한다. 활동 변경 이벤트로 재조회하고 요청 순번으로 이전 응답을 무시한다.

상세는 활동명·분류·상태·역할·기간·AI 전체 요약, 자료 폴더, Timeline 이동, 활동 더보기/삭제를 표시한다. recordsCount가 없으면 materialsCount로 기록 유무를 판단한다.

폴더는 서버가 준 유형 그룹이며 처음 모두 펼쳐져 있다. ID별로 독립 접기/펼치기를 제공하고 표시 수는 서버 materialsCount를 사용한다. 자료 버튼은 이름·유형·업로드 시각·선택 version을 표시하고 Drawer를 연다. 빈 폴더와 폴더 없음 안내를 구분한다.

### MATERIAL-01~02 — 자료 Drawer·근거 이동

근거: [FileDetailDrawer.tsx](../../src/components/footprints/FileDetailDrawer.tsx), [ActivityFolders.tsx](../../src/components/footprints/ActivityFolders.tsx).

- activityId와 자료 id로 상세를 조회한다. 응답 activityId·file.id를 요청과 대조한다. 404는 자료 없음, 나머지 오류는 다시 열기 안내다.
- 자료명·유형·업로드일·선택 버전·버전 이력(2개 이상일 때), AI 요약을 표시한다. summaryScope=record이면 ‘AI 기록 요약’이다.
- 해당 자료에 연결되어 응답으로 온 이벤트만 표시한다. 변화가 없으면 비교를 생성하지 않는다.
- 관련 이벤트와 하단 버튼으로 Timeline에 이동한다. 첫 이벤트가 있으면 그 hash를 사용한다.
- 자료 원본 다운로드·파일 본문 미리보기·자료 sourceUrl 열기 버튼은 현재 Drawer에 없다. 응답/개발 서버에 필드나 다운로드 API가 있다는 이유로 활성 기능으로 분류하지 않는다.
- 닫기 버튼·Escape·Drawer 바깥 좌표 클릭으로 닫는다. 닫기 시 file query를 제거하고 다른 query를 보존한다.

## 9. 자료·활동·전체 데이터 삭제

근거: [DeleteConfirmation.tsx](../../src/components/footprints/DeleteConfirmation.tsx), [SettingsModal.tsx](../../src/components/SettingsModal.tsx), [settings.ts](../../src/services/settings.ts).

| ID | 확인과 요청 | 성공 후 | 실패·진행 중 |
| --- | --- | --- | --- |
| DELETE-01 자료 | Drawer 삭제 → 확인 모달. 문구 입력 없이 DELETE /archive/activities/:id/materials/:fileId에 JSON {} | deleted=true 검증, 두 변경 이벤트 발생, Drawer 닫기 | 확인 모달 오류, busy 동안 취소·제출·Escape 닫기 차단 |
| DELETE-02 활동 | 상세 더보기 → 삭제. 화면 활동명과 입력 문자열이 정확히 같아야 요청, trim하지 않음. JSON {confirmation:활동명} | deleted=true 검증·이벤트 후 /archive로 replace 이동 | 미입력/불일치는 입력 오류·초점 이동, 서버 실패는 모달 유지 |
| SETTINGS-01 전체 | 공통 설정. 정확히 ‘전체 삭제’ 입력, 앞뒤 공백도 불허. POST /settings/reset-data | deleted=true 뒤 현재 탭 CHAT_SESSION_KEY만 제거. 완료 화면의 ‘홈으로 이동’은 location.assign('/') | 오류 시 세션을 지우지 않음. 삭제 중 닫기/취소/Escape 차단, 완료 후에도 일반 닫기 차단 |

자료/활동 DELETE HTTP 제한은 165초, 전체 삭제는 기본 30초다. 삭제 요청 성공 여부가 불확실하거나 deleted=true가 아니면 성공으로 간주하지 않는다. 확인 모달은 ref 잠금으로 중복 제출을 막는다.

자료 삭제 안내에는 마지막 자료면 연결 기록·Timeline 삭제, 파일이 남으면 재분석 후 삭제, 실패하면 기존 자료 유지가 명시된다. 활동 삭제 안내에는 자료·기록·Timeline·활동 분석 삭제와 Journey 재갱신 필요가 표시된다. 이 서버 처리 결과는 이번 프론트 조사에서 실제 저장소로 검증하지 않았다.

대화 초기화는 서버 삭제가 아니며 전체 삭제와 구분한다. 전체 삭제 성공은 이미 실행 중인 홈 요청을 명시적으로 abort하는 코드를 포함하지 않고, 홈으로 전체 이동하면서 화면을 재초기화한다.

## 11. Growth Journey

근거: [GrowthJourney.tsx](../../src/pages/GrowthJourney.tsx), [journey.ts 서비스](../../src/services/journey.ts), [JourneyEventCard.tsx](../../src/components/journey/JourneyEventCard.tsx).

### JOURNEY-01 — 저장 결과 조회

진입 시 백엔드 GET /journey로 저장 결과를 읽고 월(YYYY-MM) 오름차순으로 사본 정렬한다. 프론트가 분석을 자동 요청하지 않는다. 로딩·조회 오류(다시 불러오기)·정상과 이벤트 없음 상태를 구분한다.

전체 요약·배지, 분석에 사용한 기록 수·마지막 분석 시각·stale 안내·현재 기록 없음 안내를 표시한다. 서버 analysis가 선택 필드이므로 없을 때 임의 메타정보를 채우지 않는다.

### JOURNEY-02 — 사용자 수동 분석·갱신

- 기록 수가 명시적으로 0이면 분석 버튼을 막고, 기존 analysis.id 유무에 따라 ‘성장 분석하기’ 또는 ‘분석 갱신’을 표시한다.
- POST /journey/analyze, 본문 없음, HTTP 제한 145초. controller ref로 중복 실행을 차단한다.
- 성공하면 결과를 교체하고 이벤트 펼침·유형·축을 초기화한다. 분석 중에도 마지막 결과는 남는다.
- 실패하면 오류와 마지막 저장 결과라는 안내를 표시하고 GET /journey를 한 번 재조회한다. 새 GET도 실패하면 기존 결과를 유지한다. 모델 POST를 자동 재전송하지 않는다.
- 화면 이탈은 요청 대기를 취소하지만 서버에서 접수된 분석·저장은 완료될 수 있다. 활동/기록 변경 이벤트를 구독해 Journey를 자동 갱신하는 기능은 없다.

### JOURNEY-03 — 필터·상세

서버 typeOptions·axisOptions로 선택지를 만들고 두 조건을 이벤트 목록에만 AND로 적용한다. 전체 성장 요약과 배지는 필터링하지 않는다. 필터로 숨겨져도 같은 이벤트 ID의 펼침 상태는 유지한다.

이벤트는 월·활동명·유형·축·제목·설명을 표시한다. 유효 Before/After 또는 event.evidence가 있으면 펼침 버튼으로 비교와 인용문을 표시한다. 상세 없는 이벤트는 버튼이 아니다. event.evidence가 우선이며 없을 때 comparison.evidence 문구를 표시할 수 있다. 인용문은 현재 UI에서 기록/자료로 이동하는 링크가 아니다.

전체 이벤트 없음과 필터 결과 없음을 구분한다. 근거 저장 월을 표시하며 임의 일자를 보충하지 않는다. Project Timeline과 별도 결과이며 홈 저장만으로 성장 이벤트를 생성하지 않는다.

아래 경로는 각 Base 뒤에 붙인다. 이 표는 현재 프론트 호출 사실이며 handoff를 수정하거나 서버 구현 완료를 선언하는 표가 아니다.

이 외 과거 비 ai- 작업에 백엔드 GET /chat/jobs/:id를 사용하는 복원 호환 분기가 있다. 공개 20개와 별개로 보존 여부를 조사할 대상이다.

공통 request는 fetch 후 JSON 파싱을 시도하며 실패 시 null로 취급한다. 2xx는 별도 상태 코드 강제 일치 없이 응답 검증기로 넘기고, 비 2xx는 서버 error 문자열 또는 기본 문구를 status와 함께 throw한다. 잘못된 성공 응답은 서비스에서 거절하며 가짜 성공·목 데이터로 대체하지 않는다.

기본 HTTP 제한은 30초이며 호출별 예외는 4·9·11절에 기록했다. timeout은 서버 처리 여부를 확인하라는 안내, 네트워크 TypeError는 연결 실패 안내다. 외부 abort는 그대로 전달한다. 자동 HTTP 재시도는 없으며 작업 GET 폴링과 명시적 재조회만 있다.

백엔드 Base는 VITE_API_BASE_URL 또는 /api, AI Base는 VITE_AI_API_BASE_URL 또는 /ai-api이고 끝 슬래시 하나를 제거한다. 개발 프록시는 /api→127.0.0.1:3001, /ai-api→127.0.0.1:8000/api로 바꾼다. 정적 배포에는 이 개발 프록시가 적용되지 않는다.

현재 요청에 Authorization 또는 credentials:include를 설정하지 않는다. 파일을 제외한 JSON 요청은 Content-Type을 명시한다. 경로의 활동·기록·자료·작업 ID는 encodeURIComponent로 처리한다. 서버 간 내부 API를 브라우저에서 호출하는 코드는 없다.

## 13. 데이터 검증·ID·갱신 이벤트

### 응답 검증의 실제 범위

- ChatReply: assistant/id/content, general의 analysis=null, 지원 분석 kind·활동 제안·분류·stage·summary·changes·files·groups·saveMode를 확인한다. new/unresolved는 실제 ID를 가지면 거절하고 existing은 실제 ID가 필요하다. 파일 previousVersion과 stage는 null을 허용하되 생략과 구분한다. 날짜는 월/일 형식·실제 유효일·전후 순서를 검사한다.
- 채팅 완료 envelope: analysisId·conversationId 문자열과 isReply를 확인하고 ID를 카드에 결합한다. attachments·createdAt 등 envelope의 모든 필드를 검증하는 것은 아니다. activity-update는 최종 isReply 전에 백엔드 적용으로 처리한다.
- 기록 응답: id·activityId·reply만 검증해 보관한다. 서버 전체 필드의 완전 검증으로 해석하지 않는다.
- 발자국: 활동 상태·문자열·개수·시각, 폴더/자료/이벤트 구조 및 상세 대상 ID를 검사한다. 검색 categories는 중복·빈 값·예약 all을 거절한다. materialsCount와 배열 길이의 완전 동등성까지 요구하지는 않는다.
- Journey: source=api, 비빈 summary·배지·옵션·이벤트, ID/옵션 중복, all 옵션, 월 형식, 옵션 참조, 선택 analysis를 검사한다. evidence는 없을 수 있지만 있으면 비빈 배열이어야 하며 null은 거절한다. comparison도 생략과 null을 구분한다. 월은 YYYY-MM이며 실제 기록 원문의 근거 진실성은 서버 책임이다.
- 활동 분석: 상태 enum, nullable error·updatedAt, stale boolean을 검사한다. 재분석 POST는 성공 상태만 확인하고 응답 본문 스키마를 별도 검사하지 않는다.

## 14. UI 보존·비활성 코드·문서 기능

- MainPage는 모바일 세로/데스크톱 사이드바 배치, 최소 화면 높이, 최대 본문 폭 1400px을 사용한다. 브랜드·버튼 문구·카드 분기·빈 화면·오류 표시를 리팩토링 때문에 임의로 바꾸지 않는다.
- 기본 dialog는 showModal로 배경 조작과 초점을 제한하고 닫기 시 이전 초점으로 복귀하도록 작성되어 있다. 링크·분류·삭제·설정은 바깥 클릭 닫기를 별도 구현하지 않으며 Drawer만 좌표 기반 바깥 클릭을 지원한다. busy/삭제 완료의 닫기 제한은 각 기능 절을 따른다.
- Drawer는 body 스크롤을 잠그며 오른쪽 등장 모션은 reduced-motion에서 제거한다. 전체 화면의 모든 애니메이션이 reduced-motion을 완전히 따르는 것으로 일반화하지 않는다.
- 모달·Drawer의 스크롤, labels, aria-expanded/pressed, role=log/status/alert 등은 코드에 있으나 실제 키보드·스크린리더·모바일 화면은 이번에 검증하지 않았다.
- `src/mocks/Home/*`, `src/mocks/footprints/*`는 활성 src 화면의 import 검색에서 참조를 찾지 못했다. EditCategoryModal도 현재 import 호출을 찾지 못했고 실제 수정 UI는 ActivityReviewModal이다. 제거는 이번에 수행하지 않았으며 검사·외부 참조까지 확인 후 별도 판단한다.
- ActivityReviewModal에는 일반 메타정보 편집 분기도 있으나 현재 유일한 호출은 classificationOnly=true다. 숨겨진 코드 가능성을 사용자 기능으로 기록하지 않는다. `getFootprintActivities`도 직접 사용 호출을 검색에서 찾지 못했으며 활성 목록은 searchFootprintActivities다.
- API 없는 상황을 예시 데이터로 대체하는 활성 화면 fallback은 확인하지 못했다. 서버 오류는 오류/없음 상태로 표시한다.
- `/swagger`는 Vite에서 `/swagger/`로 307 이동하고 `/swagger/index.html`을 제공한다. npm predev/prebuild가 문서를 생성한다. 현재 Swagger는 읽기 전용(supportedSubmitMethods=[])이고 백엔드·AI 선택을 제공하지만 서버 폴더의 기존 명세에 의존한다. 이 정비 작업의 교체 대상이며 현재 사용자 데이터 API 기능과 구분한다.

| 등록 화면·컴포넌트·서비스·hook·타입·utils 소스 읽기, 호출/저장소/import 검색 | 문서의 코드 근거. 브라우저 E2E가 아님 |
| node scripts/check-chat-session.mjs | 통과. 합성 sessionStorage·fixture만 사용. 복원·수정값·첨부·시각·초기화·손상/접근제한·분석 중복 방지 확인 |
| node --test tests/chat-terminal-error.test.mjs tests/recent-activity-time.test.mjs | 최초 sandbox spawn EPERM으로 실행 차단. 승인 후 재실행: 4개 중 1개 통과, 최근 시각 3개 실패 |
| chat-terminal-error의 합성 fetch | failed 작업은 확정 실패, offline/abort는 불확실한 실패로 구분하는 검사 통과 |

기능 보존 원칙에 따라 시각 함수나 테스트는 변경하지 않았다. 실패 원인에 대한 런타임/ICU 상세 조사는 아직 수행하지 않았다. 이번 작업은 문서 작성이며 lint·build·실제 모델 호출·서버 실행·개인 DB 쓰기·원격 연결·브라우저 E2E는 수행하지 않았다.

handoff 대조 시 보고할 초기 차이 후보는 [API 대조표](API_계약_대조표.md)의 C-01~03이다. 이번 조사에서 C-02의 실제 카드 PATCH 호출은 activityUpdates를 보내지 않는 것으로 확인했다. GET /records/:id는 서비스 파일 밖 ConnectedChatReplyCard의 직접 호출로 확인했다. 현재 기능 명세 작성만으로 모든 handoff 충돌 검사가 끝난 것은 아니다.

## 16. 후속 대조·리팩토링 보존 체크리스트

2026-11-09 실제 브라우저 대조를 시도했으나 내장 Browser는 연결 목록이 비어 있고, Browser Use는 호출 시 플러그인 서버의 `Unknown tool` 오류로 실행되지 않았다. Vite 개발 서버 시작만 확인했으며 브라우저에서 이 문서와 실제 화면의 일치 여부는 아직 검증하지 못했다. 상세 시도와 한계는 [검증 기록](변경_협의_및_검증_기록.md)에 남겼다. 아래 체크 항목을 통과 처리하지 않는다.

아래는 향후 변경 시 재검증 항목이며 이번에 모두 실행했다는 뜻은 아니다.

- [ ] 화면 5개·설정·직접 URL/query/hash 이동 및 미존재 ID 상태 유지.

- [ ] 저장 전 로컬 분류 변경과 저장 후 PATCH, 신규/기존 연결, 중복 저장 차단 유지.

- [ ] 검색 조합·최신 결과·total 의미·폴더·자료 Drawer·근거 이동 유지.
