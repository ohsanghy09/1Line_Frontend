# 개발 기록 · 홈 AI 채팅

최종 정리: 2026-11-01

## 다음 작업을 시작할 때 먼저 읽을 내용

홈 채팅을 실제 AI API와 연결하기 전에 **목 응답으로 입력 → 응답 대기 → 분석 카드 표시**를 구현한 상태다. 사용자는 기능을 하나씩 확인하면서 진행하기를 원한다. 다음 기능을 한꺼번에 추가하기보다 최신 요청에 해당하는 범위부터 진행한다.

### 최신 사용자 지시: 다음 작업의 우선순위

사용자는 저장 기능을 먼저 추가하는 것보다 **실제 AI API를 연결했을 때 시연 시나리오가 원본처럼 동작할 수 있도록 채팅 흐름을 완성하는 것**을 우선한다. API 결과를 받는 부분은 당분간 목데이터로 유지한다.

| 우선 점검할 시나리오 | 목표 | 현재 부족한 부분 |
| --- | --- | --- |
| 텍스트 경험 입력 | 활동 분류, 주요 변화, 근거, 결과 카드 | 모든 텍스트가 같은 기능 축소 응답으로 나옴 |
| 파일 업로드 | 파일 입력, 응답 대기, 단일 파일 결과 카드 | 원본의 단계별 파일 분석 진행 화면은 미구현 |
| 변화 없는 파일 | 주요 변화 없이 자료 버전 업데이트를 제안 | 특정 예시 파일명만 목 분기로 연결됨 |
| 변화 없는 텍스트 | 주요 변화를 억지로 생성하지 않고 자연스러운 답변·분석 결과 표시 | 이 경우를 선택하는 목 분기와 시연 경로 미구현 |
| 다중 파일 일괄 업로드 | 자료 분류·합계·버전 관계를 원본 형식으로 표시 | 목 분류 구현됨. 실제 응답과 시나리오별 화면 검증 필요 |

**원본 `references/1Line_reference.html`은 수정하지 않는다.** 원본의 대화 흐름이 부자연스럽다면 현재 구현 중인 `src/pages/Home.tsx`에 반영하고, 필요한 화면·데이터 처리는 연결된 컴포넌트와 서비스에서 보완한다. 원본과 같은 결과 구성을 목표로 하되 부자연스러운 대화까지 그대로 복제하지 않는다.

최신 지시는 목표와 작업 기준을 정한 것이며, 이 문서에 기록했다고 아직 없는 목 분기나 시연 기능까지 구현된 것은 아니다.

다음 작업자는 이 문서와 [개발 규칙](development-rules.md)을 읽고, 실제 파일의 현재 상태를 확인한다. 문서 작성 이후 사용자 수정이 있을 수 있으므로 기존 변경을 덮어쓰지 않는다.

| 기준 | 위치 |
| --- | --- |
| 원본 화면과 시나리오 | [1Line_reference.html](../references/1Line_reference.html) |
| 기존 구현 가이드 | [구현_가이드라인.md](../references/구현_가이드라인.md) |

이 기록은 이번 대화에서 진행한 **홈 채팅 작업**에 대한 것이다. 다른 페이지의 개발 완료 상태를 뜻하지 않는다.

## 1. 현재 구현한 기능

| 기능 | 현재 동작 |
| --- | --- |
| 텍스트 전송 | 보내기 버튼 또는 Enter로 사용자 말풍선 추가 |
| 빈 입력 방지 | 글과 파일이 모두 없으면 전송하지 않음 |
| 입력 초기화 | 전송한 내용은 메시지 목록에 남기고 입력창만 비움 |
| 한글 조합 처리 | 조합 중 Enter는 폼 제출로 이어지지 않도록 처리 |
| 응답 대기 | 원본과 같은 Bot 아이콘·회색 말풍선·움직이는 점 3개 |
| 텍스트 분석 카드 | 현재는 모든 텍스트에 기능 6개 → 핵심 기능 3개 목 응답 |
| 파일 선택 | 클립 버튼으로 여러 파일 선택, 추가 선택 가능 |
| 전송 전 첨부 목록 | 입력창 위에 파일명 표시, 개별 삭제 가능 |
| 파일 전송 | 파일만 또는 텍스트와 함께 전송 가능, 실제 파일명은 사용자 말풍선에 표시 |
| 드래그 앤 드롭 | 입력창·첨부 영역에 놓으면 전송 전 목록에 추가, 자동 전송하지 않음 |
| 드롭 안내 | 파일 드래그 중 강조, 자식 요소 이동 시 깜빡임 방지 |
| 자동 스크롤 | 메시지·응답 대기·오류 상태가 바뀌면 채팅 맨 아래로 이동 |
| 대화 초기화 | 메시지·입력·첨부·대기·오류·드래그 상태 초기화 |
| 비동기 보호 | 중복 전송 방지, 초기화·화면 해제 전 요청의 늦은 응답 무시 |
| 오류 표시 | 응답 실패 안내 표시. 전용 재시도 버튼이나 파일 복원은 아직 없음 |

## 2. 응답 흐름과 파일 구조

```text
Home.tsx
  → getChatReply(message, files)        services/chat.ts
  → getMockChatReply(message, files)    mocks/Home/chatResponse.ts
  → ChatReply 반환
  → 사용자·AI 메시지를 같은 배열에 순서대로 추가
  → ChatReplyCard.tsx
      → 다중 파일이면 BatchAnalysisContent.tsx
```

| 파일 | 역할 |
| --- | --- |
| [Home.tsx](../src/pages/Home.tsx) | 입력, 첨부, 전송, 대기, 초기화, 메시지 렌더링 |
| [types/chat.ts](../src/types/chat.ts) | `UserMessage`, `ChatAttachment`, `ChatReply`, `ChatMessage` 등 공통 타입 |
| [services/chat.ts](../src/services/chat.ts) | 화면이 호출하는 응답 함수. 실제 API로 교체할 경계 |
| [mocks/Home/chat.ts](../src/mocks/Home/chat.ts) | 초기 인사·일반 답변·5가지 시나리오의 고정 목데이터 |
| [mocks/Home/chatResponse.ts](../src/mocks/Home/chatResponse.ts) | 약 1.3초 대기 후 입력 종류에 맞는 목 응답 반환 |
| [mocks/Home/batchAnalysis.ts](../src/mocks/Home/batchAnalysis.ts) | 파일명 기반 자료 분류·개수·버전 관계 생성 |
| [ChatReplyCard.tsx](../src/components/ChatReplyCard.tsx) | 일반 분석 카드와 다중 파일 본문 분기 |
| [BatchAnalysisContent.tsx](../src/components/BatchAnalysisContent.tsx) | 원본에 맞춘 다중 파일 결과 본문 |
| [index.css](../src/index.css) | 원본의 점 3개 애니메이션: 1.4초 주기, 0·0.2·0.4초 지연 |

초기 AI 인사는 `Home.tsx`에서 `mockGreetingReply.content`를 직접 표시한다. 일반 질문·링크 목데이터는 존재하지만 현재 전송 흐름에서 사용하지 않는다.

## 3. 목 분석의 현재 분기

| 입력 | 응답 |
| --- | --- |
| 파일 2개 이상 | 실제 파일명으로 다중 파일 결과 생성 |
| `wireframe_v2.pdf` 1개 | 원본의 단일 파일 변화 발견 시나리오 |
| `presentation_typo_fix.pdf` 1개 | 오탈자 수정, 주요 변화 없음 시나리오 |
| 그 외 파일 1개 | 실제 파일명을 넣은 일반 첨부 자료 목 응답 |
| 텍스트만 입력 | 기능 축소 시나리오의 고정 목 응답 |

파일과 텍스트를 함께 보내면 현재 목 분기는 파일을 우선한다. 파일 내용은 읽지 않고 서버 업로드도 하지 않는다. **1호선톤은 예시 활동명**이며 실제 사용자 활동 매칭 결과가 아니다.

### 다중 파일 분류 규칙

| 파일명 키워드 | 자료 유형 |
| --- | --- |
| `wireframe`, `와이어프레임` | 와이어프레임 |
| `meeting`, `회의록`, `회의` | 회의록 |
| `idea`, `proposal`, `기획`, `제안` | 기획안 |
| `presentation`, `발표` | 발표자료 |
| 해당 없음 | 기타 자료 |

위 순서대로 먼저 일치하는 유형을 사용한다. 영문 대소문자는 구분하지 않는다.

버전은 같은 기본 이름·확장자 안에서 `_v1`, `_v2`, `_final` 등을 비교한다. 구분자는 밑줄·하이픈·공백을 지원한다. 입력 순서와 관계없이 낮은 버전 중 가장 가까운 것을 이전 버전으로 연결하며, `final`은 숫자 버전 뒤로 취급한다. 파일명이 다른 자료나 확장자가 다른 자료는 연결하지 않는다.

원본의 `idea_v1.pdf`, `idea_final.pdf`, `wireframe_v1.pdf`, `wireframe_v2.pdf`, `meeting.docx`를 보내면 기획안 2개·와이어프레임 2개·회의록 1개가 된다. 원본의 두 버전 연결이 모두 있으면 안내 문구도 원본과 같게 반환한다.

## 4. 다중 파일 카드의 최종 화면 상태

표시 순서는 **완료 문구 → 활동명·자동 매칭 개수 → 분류별 개수 → 💡 버전 안내 → 버튼 → 분석 완료 시각 문구**다.

- 일반 카드의 추가 활동 제목·확신도 영역과 개별 파일 상세 목록은 다중 파일 카드에 표시하지 않는다.
- 바깥 카드는 내용에 맞춰 늘어나되 최대 `28rem`과 채팅 영역 너비 안으로 제한한다.
- 분류 박스는 `flex-wrap`과 `flex-auto`로 남는 공간을 채운다. 고정 3열이 아니다.
- 유형명과 개수는 한 줄을 유지한다. 공간이 부족하면 박스 전체를 다음 행에 배치한다.
- 박스 하나의 문구가 카드보다 길면 박스 내부 가로 스크롤로 전체 내용을 볼 수 있다.
- 분류가 1개일 때도 별도 좌우 마진을 추가하지 않는다.
- 제목·활동명·하단 안내 문구에는 말줄임 처리를 하지 않는다. 제목과 안내는 필요한 경우 줄바꿈한다.

최근 캡처에서 4개 분류 중 ‘와이어프레임 2개’의 ‘개’가 다음 줄로 떨어졌다. 기존 자동 그리드 대신 위 방식으로 수정했다. 이 수정 이후 브라우저에서 새 캡처로 시각 검증을 완료했다는 기록은 없다.

## 5. 아직 구현하지 않은 부분

| 항목 | 현재 상태 |
| --- | --- |
| 실제 AI API | 미연결. 모든 답변은 목데이터 |
| 실제 파일 업로드·내용 분석 | 미구현 |
| 기록 저장 | 일반 기록 버튼과 다중 파일 ‘전체 저장’은 비활성 |
| 분류 수정·다른 활동 선택 | 일반 카드에 버튼만 있고 비활성 |
| 다중 파일 ‘자료 확인’ | `/archive` 이동만 구현. 이번 첨부 자료가 실제 저장된 것은 아님 |
| 링크 추가 | 입력창 버튼 미연결, 링크 응답 목데이터만 존재 |
| 시연 버튼 | 화면에 있으나 클릭 동작 미연결 |
| 대화 영속 저장 | 미구현. 새로고침·홈 재진입 시 대화 보존 없음 |
| 단일 파일 단계별 진행 표시 | 원본의 파일 비교 단계 화면은 미구현. 공통 점 3개 대기 사용 |

## 6. 다음 진행 방향

다음 항목은 **진행 제안**이며, 사용자가 새로 요청하기 전에 전부 구현하라는 지시는 아니다.

1. 최신 캡처와 실제 화면에서 분류 1·2·3·4개, 긴 유형명, 좁은 화면의 레이아웃을 확인한다.
2. 텍스트 경험, 단일 파일, 변화 없는 파일·텍스트, 다중 파일의 목 응답과 화면 흐름을 하나씩 완성한다. 저장 버튼 연결을 이 목표보다 앞선 기본 우선순위로 삼지 않는다.
3. 백엔드와 API 계약을 정한다: URL·인증·파일 요청 필드·응답 구조·대화 문맥·오류 형식·저장 방식.
4. `services/chat.ts`에서 목 호출을 실제 요청으로 교체한다. 응답 구조가 같으면 화면 컴포넌트를 유지할 수 있다.
5. 실제 응답의 필수 필드와 타입을 확인한다. TypeScript 타입 선언만으로 외부 JSON이 검증되지는 않는다.
6. 실제 API 전환 시 초기 인사 처리와 텍스트·파일·일반 질문·링크의 응답 흐름도 함께 점검한다.

화면은 응답의 `kind`, `analysis`, `changes` 등을 기준으로 표시하고, 실제 API 연결 후에도 프론트엔드가 파일명이나 텍스트 키워드로 주요 변화 여부를 다시 판정하지 않도록 한다. 목 시연용 분기와 실제 분석 책임을 구분한다. `changes: []`인 텍스트 결과도 처리할 수 있도록 준비한다.

파일 전송은 `FormData`를 사용할 수 있으나 아직 확정된 서버 계약은 없다. API 주소나 요청 필드명을 임의로 확정하지 않는다.

## 7. 검증 기록

- 구현 과정에서 `npm run build`, `npm run lint` 통과를 반복 확인했다.
- 다중 파일 목 분석의 원본 분류 합계, 버전 연결, 역순 선택, 알 수 없는 파일, 확장자 분리, 주요 변화 미생성을 Node로 확인했다. 일회성 검증이며 저장된 테스트 파일은 없다.
- 마지막 자료 유형 가로 스크롤 수정 후에는 린트 통과를 확인했다. 이 문서를 작성하면서 브라우저 시각 검증이나 전체 테스트를 새로 수행한 것은 아니다.

다음 작업에서는 변경 범위에 맞게 검사한다. 화면을 확인하지 않았으면 시각 검증까지 완료했다고 적지 않는다.
