# 백엔드·AI 파트별 인수인계 문서 작성 계획

기록일: 2026-11-06.

최신 전달 조건(2026-11-06): 사용자는 개발 코드를 제공하지 않고 문서만으로 다른 환경의 백엔드·AI 구현이 가능하길 요청했다. 이 조건이 아래 초기 코드 안내 계획보다 우선한다. 최종 전달은 docs/handoff/만으로 독립되게 구성하며 관련_코드_안내.md 두 개는 제거했다. 개발환경 재현 요구 대신 공개 계약·논리 DB·전문 프롬프트·독립 서버 간 전달·검증 기준을 문서 안에 명시한다. 공유 로컬 DB/스크립트 실행·폴더 밖 참조를 수신자의 필수 조건으로 쓰지 않는다.

작성 후속(2026-11-06): [현재 구현 인수인계](../handoff/README.md) 문서 묶음을 작성했다. 사용자 후속 결정으로 review/확인과_합의가_필요한_사항.md는 만들지 않고 운영 전환 결정은 integration/배포와_서버_연결.md에 통합했다. 개발용 독립 카드 페이지는 명세에서 제외하고 라우트도 제거했다. Home과 공통 컴포넌트는 변경하지 않았다. 아래 ‘아직 작성하지 않았다’와 폴더 구조는 계획 수립 당시 기록이며 현재 완료 범위·검증은 새 문서 묶음을 따른다.

## 현재 요청과 다음 작업

사용자는 프론트를 `https://1-line-frontend.vercel.app/`에 배포했다고 알렸다. 현재 동작하는 프론트·백엔드 개발 서버·AI 개발 서버와 기존 기능 문서를 기준으로, 백엔드/AI 담당자와 각 파트 에이전트가 실제 서버 연동을 구현할 수 있는 문서 묶음을 만들고자 한다.

이번 요청에서는 **이 계획과 읽기 순서만 기록**한다. `docs/handoff/`의 최종 문서 묶음은 아직 생성·작성하지 않았다. 후속 사용자 요청에 따라 아래 구조로 내용을 채운다. 이 계획만으로 코드 변경, 배포, DB 수정, 실제 모델 호출, GitHub 이슈 생성까지 수행하지 않는다.

## 다음 채팅에서 읽을 순서

1. [프로젝트 문서 입구](../README.md): 최신 작업과 문서 경로.
2. **이 파일**: 사용자와 논의한 문서 목적·구조·작성 범위·완료 기준.
3. [현재 작업 인수인계](현재_작업_인수인계.md): 실제 구현과 검증 범위. 과거 이력과 최신 상태를 구분한다.
4. [개발 규칙](../개발_규칙.md)과 각 기능의 최신 문서: 홈 채팅, 나의 발자국, Growth Journey.
5. 아래 관련 소스: 문서 내용은 이전 계획을 복사하는 대신 현재 코드와 대조한다.

사용자가 문서 작성을 요청하면 구조 설명을 반복하거나 같은 승인을 다시 요청하지 말고, 위 자료를 확인한 뒤 문서를 작성한다. 운영 환경에서 확인하지 못한 사실은 추정해 확정하지 않는다.

## 목표와 독자

- 사용자: 화면에서 어떤 정보가 보이고 어떤 행동을 할 수 있는지 읽고 의도한 기능인지 검토한다.
- 공통 독자: 프론트·백엔드·AI의 책임과 사용자 행동에 따른 요청/응답·저장 시점을 이해한다.
- 백엔드 담당자/에이전트: API·DB·ERD·트랜잭션·관련 코드를 읽고 정식 백엔드를 연결한다.
- AI 담당자/에이전트: API·입력 문맥·출력 스키마·프롬프트·후처리·검증 규칙을 읽고 AI 서버를 연결한다.

단순한 개발 일지가 아니라 **사용자 행동 → 프론트 요청 → 백엔드/AI 처리 → 응답 → 저장과 화면 반영**을 재현할 수 있는 현재 구현 기준 문서를 작성한다.

## 문서에 포함할 내용

### 사용자 화면과 공통 흐름

| 화면 | 기능 범위 |
| --- | --- |
| 홈 채팅 | 일반 대화, 텍스트 경험, 단일/다중 파일·링크 분석, 진행 표시, 신규 활동 제안, 기존 활동 연결, 확정 저장, 분류 수정, 대화로 역할·상태·기간·전체 요약 변경, 최근 활동·자료 |
| Growth Journey | 저장 결과 조회, 분석 실행·갱신, 동적 유형/분야, 배지·이벤트·비교/근거, 필터, 빈 결과·실패·갱신 필요 상태 |
| 나의 발자국 | 활동 목록·검색·유형/상태 필터·정렬, 활동 요약/기간/역할/상태, 자료 폴더·상세, 타임라인, 자료 개별 삭제·활동 전체 삭제 |
| 사용자 설정 | 확인 문구 검증, 전체 데이터 삭제, 진행 충돌과 실패·완료 처리 |

각 기능에 `HOME-01`, `JOURNEY-01` 등의 식별자를 부여하고 화면 정의·API 흐름·검증 시나리오에서 동일하게 참조한다. 기능별로 표시 항목, 사용자 행동, 담당 서버, 요청 순서, 응답 예시, 저장 시점, 연쇄 갱신, 예외/빈 상태를 작성한다. 분석 초안 보관과 사용자 확정 기록 저장을 구분한다.

### 백엔드 API·DB·ERD

- API 메서드·경로·담당 서버·헤더·파라미터·요청/응답 JSON·필드 필수/선택/null·상태 코드·검증 규칙.
- 테이블/컬럼 자료형·NULL·기본값·PK/FK/UNIQUE·인덱스와 용도. 실제 스키마를 기준으로 작성한다.
- ERD의 실제 외래 키 관계와 JSON 내부 논리 참조를 구분한다. 테이블뿐 아니라 `records.reply` 등 JSON 구조도 설명한다.
- 원본 파일 BLOB·분석 초안·확정 기록·타임라인·성장 결과 관계, 중복 방지·원자적 저장/삭제·진행 작업 충돌을 설명한다.
- 활동/자료/전체 삭제 범위와 대화 보존, 다중 파일 일부 삭제 시 재분석, 성장 결과 무효화 규칙을 포함한다.
- SQLite 공유 DB는 현재 개발 구조임을 명시한다. 정식 서버의 DB 선택과 API 호환 계약을 혼동하지 않는다.

### AI API·프롬프트

- 공개 홈 접수/진행 API, 문맥 조회, 내부 활동 정보/성장/남은 파일 분석 API를 실제 라우트 기준으로 구분한다.
- 입력 문맥의 출처·범위·기록/파일 한도, 일반 대화/활동 수정/분석 구분, 활동 매칭과 생성 책임을 설명한다.
- 현재 프롬프트 원문, 적용 파일/함수, 입력 변수, 출력 스키마와 금지 사항을 포함한다. Markdown 파일뿐 아니라 Python 코드 내 지시문도 조사한다.
- 모델 생성 값과 서버가 부여/정리하는 ID·날짜·분류·아이콘·근거를 구분한다.
- 모델 설정, 시간 제한, 실제 호출 횟수/재시도 정책, 근거/해시 검증, 오류 처리를 작성한다. 비밀키와 `.env` 실제 값은 싣지 않는다.
- 최신 Journey는 `journey-v4`: 미사용 분류 제거, 정규화 후 정확히 같은 라벨 통합 및 참조 치환, 미등록/모호한 참조 거절, 근거 검증 유지. 자동 모델 재호출은 없다.

### 운영 연동과 검증

- 프론트 배포 주소, 백엔드/AI Base URL 설정, 로컬 Vite 프록시와 Vercel 라우팅 차이, HTTPS·CORS·인증·사용자 식별을 확인한다.
- 프론트 배포 사실만으로 운영 백엔드/AI 연결이 검증됐다고 적지 않는다. 공유 SQLite를 별도 서버 배포에서 대체할 방식도 합의 항목으로 둔다.
- 화면별 정상·실패·빈 상태·중복 저장·삭제·재추가·변경 중 분석 시나리오를 정리하고 기대 API/DB/화면 결과를 연결한다.
- 자동 테스트, 실제 모델/API 확인, 브라우저 확인, 미확인을 구분한다. 문서 작성을 위해 사용자 DB를 초기화하거나 유료 분석을 자동 반복하지 않는다.

## 작성 기준과 완료 조건

- 현재 코드 → 기존 문서 → 필요 시 실제 배포 상태 순서로 대조하고 문서마다 기준일과 검증 범위를 표시한다.
- 현재 구현, 검증 완료, 합의 필요를 분리한다. 계획상의 기능을 완료로 쓰지 않는다.
- 공통 데이터 구조는 원본 정의 한 곳에 두고 API별 문서에서 연결한다. 프롬프트 복사본에는 원본 코드 경로를 명시한다.
- 백엔드/AI 담당자가 문서의 요청/응답 예시로 프론트 연결을 재현할 수 있어야 한다.
- 모든 새 문서는 상대 링크로 연결하고 코드 경로·라우트·예시·읽기 순서를 점검한다. Markdown ERD를 작성할 때는 실제 스키마와 대조한다.
- 기존 개발 이력은 보존한다. 사용자 지시로 **Swagger 최신화/정적 OpenAPI 생성은 하지 않는다.** 문서 작성 중 불필요한 전체 빌드나 `npm run build`의 Swagger 생성도 피한다.

## 사용자가 강조한 문서 품질 요구 — 반드시 적용

사용자는 단순히 문서를 만들 수 있는지 묻는 것이 아니라 **백엔드·AI 담당자가 문서만 보고 현재 프론트에 맞춰 구현할 수 있을 만큼 꼼꼼하게 작성할 것**을 강조했다. 에이전트는 일반적인 연동 가능성 설명이나 추상적인 주의사항으로 답변을 대신하지 말고, 작성 시 실제 코드의 동작과 계약을 하나씩 대조하고 빠진 내용을 찾아 채워야 한다.

아래 약속을 후속 작업의 품질 기준으로 적용한다.

1. 화면별 사용자 행동, 표시 항목과 상태를 실제 컴포넌트에서 확인한다. 버튼 이름만 나열하지 말고 클릭 전후의 변화와 후속 동작까지 설명한다.
2. 프론트 서비스 호출 → 백엔드/AI 라우트 → 입력 검증 → 처리/저장 → 응답 검증 → 화면 반영을 끝까지 연결한다. 서버 사이의 내부 호출과 비동기 후속 분석도 포함한다.
3. API 경로·메서드·Base URL·헤더·전송 형식·상태 코드와 필드의 이름/자료형/필수 여부/null/제약을 실제 코드와 대조한다. 예시 JSON은 정의된 계약을 만족해야 한다.
4. DB·ERD·JSON 내부 구조와 API 필드의 대응을 확인한다. 실제 FK와 논리 참조, 원본/초안/확정 기록/캐시의 차이, 중복 방지와 트랜잭션 경계를 설명한다.
5. 프롬프트와 입력 문맥·출력 스키마·모델 후처리·서버 검증을 함께 설명한다. 프롬프트만 복사하거나 모델의 출력이 그대로 DB에 저장된다고 단순화하지 않는다.
6. 정상 동작뿐 아니라 빈 값·분석 실패·시간 초과·진행 상태·재요청·중복 저장·삭제된 ID·삭제/재추가·동시 변경과 복구/재시도 흐름도 실제 구현에 맞춰 적는다.
7. 모든 관련 문서의 용어·필드·흐름을 교차 확인한다. 같은 계약을 서로 다르게 설명하거나, 현재 구현과 과거 계획을 섞지 않는다.
8. 각 파트가 추측하며 구현하지 않도록 미정인 사항과 서로 합의해야 할 사항을 명확히 표시한다. 실제로 확인되지 않은 동작을 임의로 완성된 계약으로 만들지 않는다.

| DB/ERD | 실제 테이블·컬럼·제약과 일치하는가? JSON 내부 참조와 저장/수정/삭제 순서를 누락하지 않았는가? |

### 작성 작업의 마무리 방식

- 현재 프론트가 사용하는 API를 먼저 목록화하고, 각 항목이 문서에 반영됐는지 대조한다. 실제 코드에 없는 기능은 현재 구현으로 추가하지 않는다.
- 각 핵심 흐름에 실제 코드 경로를 근거로 연결하고, 스키마/예시/DB 정의 사이의 불일치를 점검한다. 확인이 필요한 차이는 숨기지 말고 합의 문서에 기록한다.
- 문서를 모두 작성한 뒤 위 점검표로 검토하고 누락/불일치를 보완한다. 빈 템플릿이나 제목만 만든 상태를 완료로 보고하지 않는다.
- 사용자에게는 읽기 시작 파일, 작성한 문서 범위, 코드와 대조한 항목, 남은 합의 사항과 실제 검증 범위를 전달한다.
- 문서의 완성도와 실제 운영 서버 연동 검증은 구분하되, 이 구분을 문서를 대충 작성하거나 검토를 생략하는 이유로 사용하지 않는다. 목표는 **현재 구현 기준으로 추측을 최소화한 재현 가능한 인수인계 문서**다.
