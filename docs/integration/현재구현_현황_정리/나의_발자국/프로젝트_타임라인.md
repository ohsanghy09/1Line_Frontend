# 프로젝트 타임라인 구현 현황

정리일: 2026-11-05. 경로: `/archive/:activityId/timeline`. 공통 전제는 [문서 안내](../문서_안내.md)를 따른다.

## 구현된 동작

- 한 활동의 확정 기록에 연결된 변화 이벤트를 날짜순으로 표시한다. 여러 활동의 성장을 분석하는 Journey와 별도다.
- 활동 정보·주요 변화 수·Turning Point 수를 표시한다. 주요 변화 수는 현재 이벤트 수다.
- 일반 변화는 설명·Before/After를 표시한다. Turning Point는 별도 강조와 Reason을 표시한다.
- 연결된 근거 자료를 누르면 같은 활동의 자료 Drawer로 이동한다. ID를 해결하지 못한 근거는 문자열로 남긴다.
- 활동 상세 복귀·관련 자료 보기, 해시로 지정한 이벤트 스크롤·초점 이동을 지원한다.
- 로딩·서버 실패·활동 없음·이벤트 없음을 구분한다. 오류 시 재방문 안내이며 별도 재시도 버튼은 없다.

## 실제 호출과 저장 관계

현재 화면은 GET `/api/archive/activities/:id`의 `timeline`과 `folders`를 사용한다. 서버의 GET `/api/activities/:id/timeline`도 존재하지만 이 화면이 직접 호출하는 API는 아니다.

- 이벤트는 SQLite의 `timeline_events`와 확정 기록에서 조회한다. 같은 시각은 DB 삽입 순서다.
- 저장 시 changes가 있으면 기록과 이벤트를 함께 저장하고 없으면 이벤트를 생성하지 않는다.
- 기록을 다른 활동으로 이동하면 자료·이벤트도 새 활동에서 조회한다. changes를 빈 배열로 수정하면 이벤트를 제거한다.
- 현재 저장 API는 이벤트를 만들 때 Turning Point를 false로 저장한다. 실제 AI 전환점 판단은 없다.
- 이벤트가 실제 DB에 있다는 것과 Before/After가 실제 AI로 분석됐다는 것은 다르다. 현재 저장된 변화는 목 분석일 수 있다.

## 실제 연동 시 남은 작업

- 실제 비교·변화·Turning Point·Reason 판단 기준과 근거 ID 계약
- 분석 결과 수정·재분석 시 이벤트 ID 보존·갱신 정책. 현재 changes 수정은 이벤트 삭제 후 재생성한다.
- 활동 상세와 Timeline의 응답을 함께 받을지 별도 조회할지 최종 계약 협의
- 기록 수정·삭제·이동 후 관계 유지와 사용자별 접근 제어
