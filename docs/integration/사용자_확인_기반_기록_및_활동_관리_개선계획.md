# 사용자 확인 기반 기록 및 활동 관리 개선계획

작성일: 2026-11-06

최신 추가 요청: [대화로 활동 정보 직접 수정](../chat/구현_기능/대화로_활동_정보_수정.md)을 구현했다. 명시적 역할·상태·기간·전체 요약 수정은 새 정정 기록이나 확인 모달 없이 DB의 해당 값만 바꾼다. 이전 값의 별도 이력과 영구 수동 잠금은 두지 않는다. 아래 사용자 입력 보호에 관한 초기 제안보다 이 최신 동작을 우선하며 이후 자료 저장의 AI 갱신은 허용한다.

후속 구현: 사용자 요청으로 [활동 전체 정보 AI 자동 갱신](../footprints/활동_정보_AI_갱신.md)을 구현했다. 저장·수정·이동 후 AI 종합과 실패 보존·재시도까지 연결했다. 아래 활동 정보 부분의 ‘현재 동작/제안’은 계획 작성 당시이며 최신 기능 문서를 우선한다. 개별 삭제·Journey 분야 등 나머지는 아직 후속 범위다. Swagger 갱신은 최신 사용자 요청으로 제외한다.

**상태: 1단계 구현·자동 검사 완료, 후속 항목 검토 중.** 후속 요청 ‘하나씩 구현’에 따라 홈 응답 구분·신규 활동 확인 저장을 구현했다. 실제 모델·브라우저 확인은 대기다. [1단계 구현 기록](../chat/구현_기능/홈_응답_구분_및_활동_확인_저장.md)을 우선한다. 아래 ‘현재 동작’ 설명은 계획 작성 당시 기준이며 변경 완료 사항은 해당 구현 기록을 따른다. 남은 항목을 전체 일괄 구현 지시로 해석하지 않는다.

현재 구현 상태는 [현재 작업 인수인계](현재_작업_인수인계.md)를 따른다. 이 문서는 변경할 방향과 미결정 사항을 기록하며 기존 구현 문서를 대체하지 않는다. 사용자 요청과 아래 설계 제안을 구분한다.

## 1. 요청과 검토 범위

| 영역 | 사용자가 요청하거나 검토한 내용 | 상태 |
| --- | --- | --- |
| 공통 말투 | 딱딱한 다나까체 대신 부드러운 말투 | 홈 프롬프트에 해요체 적용, Journey·전체 안내 정리는 후속 |
| 홈 신규 자료 | 기존에 없던 활동이면 변화 없음 대신 새 활동 카드 표시 | 1단계 구현, 실제 모델·브라우저 확인 대기 |
| 홈 카드 제목 | AI 요약 반복 대신 어떤 활동의 자료인지 표시 | 신규 제안 카드·content 분리 적용, 기존 모든 카드 정리는 후속 |
| 홈 일반 대화 | 활동과 관련 없는 말에는 일반 말풍선으로 응답 | 1단계 구현, 실제 모델·브라우저 확인 대기 |
| 신규 활동 저장 | AI 판단만으로 활동을 저장하지 않고 사용자가 판단 | 최신 요청으로 확인 모달 제거. 카드에서 새 활동 저장 또는 기존 활동 목록 선택 후 저장, 보관 기간은 미결정 |
| Journey 분야 | 고정 분야 분류 여부 확인과 개선 | journey-v3에서 실제 이벤트 기반 동적 분야 생성·검증·기존 결과 호환 구현, 실제 모델·브라우저 확인 대기 |
| 활동 정보 | 전체 요약·상태·기간·역할의 AI 판단 | 저장·수정·이동 후 자동 종합·실패 보존·재시도 구현, 실제 모델·브라우저 확인 대기 |
| 타임라인 | 이벤트 갱신 방식 확인과 개선 | 현황 확인 및 갱신 기준 제안 |
| 삭제 | 활동 전체 및 개별 자료 삭제 방법 | 기능 추가 제안, 삭제 범위·근거 처리 미확정 |

이미 구현한 활동 유형 동적 필터와 설정의 DB 전체 삭제는 별도 기능이다. 이번 계획의 신규 활동 승인·Journey 분야·활동별 삭제와 혼동하지 않는다.

## 2. 핵심 원칙

AI는 활동 연결·분류·요약을 제안한다. 사용자가 확정한 뒤 활동 생성과 기록 저장을 수행하는 흐름을 목표로 한다.

`입력 → 분석 → 카드 제안 → 사용자 확인 → 활동 생성/기록 저장 → 발자국 조회 → 필요한 성장 분석`

- 신규 활동 여부와 중요한 변화 여부는 서로 독립적으로 판단한다.
- 첫 자료라는 이유로 Before/After나 성장 이벤트를 만들지 않는다.
- 자료 한 건의 요약과 활동 전체의 요약을 구분한다.
- 원본·분석 초안의 임시 보관과 활동·기록의 확정 저장을 구분한다.
- 기간·역할·성과를 근거 없이 채우지 않는다.
- 원본 HTML과 관련 없는 스타일을 변경하지 않는다. 기존 데이터·수정 파일을 보존한다.

## 3. 부드러운 AI 말투

현재 홈·Journey 프롬프트에는 해요체를 일관되게 사용하라는 규칙이 없다. 모델 출력과 서버·화면 고정 문구를 함께 점검한다.

제안하는 규칙:

- 설명·안내는 ‘~했어요’, ‘~보여요’, ‘~확인해 보세요’ 형태로 작성한다.
- 근거 부족은 ‘아직 확인하기 어려워요’처럼 자연스럽게 안내한다.
- 제목·유형명은 짧은 명사형을 허용하고 과장된 칭찬은 피한다.
- 근거 원문 인용은 말투를 바꾸지 않는다.

예: ‘기능 범위 축소가 확인되었습니다’ → ‘인터뷰를 반영하면서 기능 범위를 줄였어요.’

관련 위치: `ai-api-server/app/prompts/home.md`, `ai-api-server/app/prompts/journey.md`, 홈 카드 및 서버 고정 안내 문구.

## 4. 홈 응답 구분과 카드 제목

### 현재 동작과 원인

`build_reply`는 파일 개수·링크·changes 유무로 응답 kind를 결정한다. 단일 파일에 변화가 없으면 `no-change`가 된다. 프론트도 단일 파일·빈 changes이면 변화 없음 카드를 선택한다. 따라서 신규 활동의 첫 자료와 기존 활동의 변화 없는 자료를 구분하지 못한다. 모든 단일 파일이 무조건 변화 없음으로 처리되는 것은 아니다.

서버의 `reply.content`에는 현재 `result.summary`가 들어간다. 변화 없음·다중 파일 카드는 이를 상단에 사용하므로 AI 요약과 제목이 중복될 수 있다. 변화 있는 단일 파일 카드는 현재 파일명을 제목에 표시한다.

### 제안하는 구분

| 판단 | 표시 | 저장 동작 |
| --- | --- | --- |
| 명확한 신규 활동 | 새 활동 제안 카드 | 사용자 확인 후 새 활동 및 기록 저장 |
| 기존 활동 + 중요한 변화 | 변화 분석 카드 | 기존 활동에 기록 저장 |
| 기존 활동 + 변화 없음 | 자료 보관 카드 | 변화 이벤트 없이 자료 저장 |
| 활동 판단 불충분 | 활동 선택 또는 추가 정보 안내 | 활동 선택/확인 전 확정 저장 금지 |
| 일반 대화 | 일반 채팅 말풍선 | 활동·기록 저장 버튼 없음 |

응답 종류 식별자의 정확한 이름과 JSON 계약은 구현 시 정한다. 신규 활동 여부를 변화 배열이나 파일 개수에서 추측하지 않는다. 다중 파일도 같은 판단 원칙을 적용하되 기존 일괄 저장·자료 확인 흐름을 보존한다. 파일별로 다른 활동이 발견되는 경우의 분할 UI는 미결정이다.

제목은 구조화된 활동명을 사용하고 요약과 분리한다. 예:

- 제목: ‘독서 모임 북클럽봄의 첫 자료를 확인했어요’
- 활동: 북클럽봄
- 자료 유형: 운영 기획안
- AI 요약: 이번 자료의 실제 내용

### 일반 대화

현재 프론트 `ChatReply.analysis`는 null을 허용하지만 실제 홈 모델 계약은 분석 결과를 요구한다. 프롬프트만 바꾸면 충분하지 않으며 모델 스키마·서버 처리·응답 검증·화면 분기를 함께 변경해야 한다.

‘안녕’, ‘고마워’ 등에는 일반 말풍선으로 답하고 활동을 생성하지 않는다. 경험 기록 의도는 있지만 정보가 부족한 경우에도 활동을 억지로 만들지 않고 추가 질문을 할 수 있다. 대화만으로 활동·파일·기록용 초안을 불필요하게 만들지 않는 방향을 제안한다. 일반 대화의 보관 범위와 후속 질문에서 이전 대화를 모델에 전달할 범위는 미결정이다.

관련 위치: `ai-api-server/app/home_analysis.py`, `home_schemas.py`, `chat.py`, `src/services/chat.ts`, `src/types/chat.ts`, `src/components/chat/ChatReplyCard.tsx` 및 파일 카드들.

## 5. 신규 활동 제안과 사용자 확정

### 현재 동작

AI 서버 `SharedDatabase.complete_job`에서 match=new이면 활동을 바로 INSERT하고 match=existing과 실제 ID로 바꾼다. 기록 버튼 이전에도 활동은 남는다. 현재 홈 저장 UI는 기존 활동 ID를 요구하며 수정 모달도 기존 활동·자료 유형 변경에 한정한다.

백엔드에는 `newActivity`를 받아 기록 저장 트랜잭션에서 활동을 생성하는 구조가 일부 있다. 이를 활용하되 기존 동작을 그대로 연결할 수 있다고 가정하지 않는다.

### 제안하는 흐름

1. AI 분석 결과를 신규 활동 후보로 유지한다. 이 시점에는 활동 테이블에 생성하지 않는다.
2. 카드에서 활동명·유형·요약을 보여준다.
3. 최신 요청에 따라 모달 없이 ‘새 활동으로 저장’을 누르면 제안한 이름·유형으로 저장한다. 전체 요약·역할·기간 입력을 요구하지 않는다.
4. ‘기존 활동에 연결’에서 카드 안의 목록을 펼치고 선택한 활동에 자료를 저장한다. 취소하거나 선택만 하면 저장하지 않는다.
5. 사용자 확정 시 활동 생성과 기록 저장을 한 트랜잭션으로 수행한다.
6. 저장하지 않으면 발자국·활동 수·Journey에는 반영하지 않는다.

원본 파일과 초안은 저장 전에도 임시 보관할 수 있다. 미저장 제안의 보관 기간·삭제 방식은 별도 결정한다. 연속 업로드에서 같은 미확정 후보가 여러 번 생기는 경우, 같은 이름의 활동이 먼저 저장된 경우, 중복 클릭·재요청·페이지 복원 시 처리를 검증한다. 이미 생성된 기존 활동을 일괄 삭제하거나 다시 후보로 바꾸지는 않는다.

## 6. 활동 전체 요약·기간·역할

### 현재 동작

발자국·활동 상세는 activities의 summary, role, period 등을 읽는다. 값이 없으면 미설정 또는 요약 미등록 안내를 표시한다. 이번 자료의 `analysis.summary`를 활동 전체 요약으로 자동 누적하는 구조는 아니다.

실제 홈 AI는 현재 활동 유형을 생성하지만 활동 전체 요약·기간·역할을 종합해 채우는 흐름은 연결되어 있지 않다. 백엔드 메타정보 저장 코드는 있으나 현재 홈 수정 UI는 활동 연결·자료 유형에 한정된다.

### 개선 제안

- 전체 요약은 해당 활동의 확정 기록을 종합해 생성한다.
- 자료 요약과 활동 요약을 서로 덮어쓰지 않는다.
- 기간·역할은 입력 자료의 명시적 근거를 바탕으로 제안하고 사용자가 수정·확정할 수 있게 한다.
- 기록 저장 시각을 활동 시작·종료일로 추정하지 않는다.
- 사용자가 확정한 역할·기간을 이후 AI 분석으로 임의 덮어쓰지 않는다.
- 기록 변경·이동·삭제 후 전체 요약의 갱신 필요 상태를 관리한다.

요약을 저장 시 자동 갱신할지, 상세의 별도 버튼에서 갱신할지와 추가 AI 호출 비용은 아직 결정하지 않았다. 메타정보를 직접 비우는 동작도 현재 null 보존 정책과 구분해 설계해야 한다.

관련 위치: `api-server/src/activities.js`, `archive.js`, `src/pages/ActivityArchive.tsx`, `src/components/chat/modals/ActivityReviewModal.tsx`.

## 7. 타임라인 갱신 기준

현재 기록 POST는 `reply.analysis.changes`마다 timeline_events를 생성한다. 변화가 없으면 생성하지 않는다. PATCH에 changes가 포함되면 기존 이벤트를 지우고 다시 만든다. 이 경로는 is_turning_point=0으로 저장하며 Turning Point를 자동 판정하지 않는다. 일반 요약 수정만으로 AI 변화 재분석이 실행되지는 않는다.

개선 시 유지할 기준:

- 단순 업로드·첫 기록만으로 변화 이벤트를 추가하지 않는다.
- 변화 목록을 수정하면 해당 기록의 이벤트를 갱신한다.
- 기록 이동 시 원래 활동과 도착 활동의 조회·요약 상태를 함께 갱신한다.
- 기록·자료 삭제 시 연결 근거를 잃는 이벤트를 정리한다.
- Project Timeline의 활동 변화와 Growth Journey의 성장 분석을 구분한다.

자동 변화 재분석 및 Turning Point 판단을 추가할지는 별도 결정한다. 현재 이벤트를 재생성할 때 ID가 바뀔 수 있으므로 편집 도입 시 상세 참조와 ID 유지 기준도 확인한다.

## 8. 활동 삭제와 개별 자료 삭제

2026-11-06 구현 완료: [활동 전체·자료 개별 삭제](../footprints/활동_자료_삭제.md). 활동명 입력 확인, 마지막 자료와 연결 기록 삭제, 다중 파일의 남은 원본 재분석, 활동 정보 재분석 및 과거 Journey 집계 무효화를 구현했다. 아래는 계획 이력이며 현재 동작은 구현 문서를 우선한다.

### 활동 전체 삭제 제안

활동 상세 화면에서 삭제를 제공하고 활동명·기록 수·자료 수·복구 불가 안내를 확인한다. 해당 활동과 연결된 확정 기록·타임라인·원본·초안 등을 정리한다. 다른 활동에서도 사용하는 원본·분석 초안은 함께 지우지 않도록 참조를 확인한다. DB 외래 키뿐 아니라 JSON 안의 활동·파일·기록 참조도 확인해야 한다.

진행 작업과 충돌하지 않게 하고, 삭제 실패 시 부분 삭제 없이 롤백한다. 다른 활동의 자료를 삭제하지 않는다. 승인 전 초안과 확정 활동의 연결 기준이 바뀌므로 신규 활동 확인 저장 흐름을 먼저 정리한다.

### 개별 자료 삭제 제안

자료 상세에서 삭제를 제공하되 단일 원본 파일 삭제와 기록 전체 삭제를 구분한다. 현재 다중 파일은 한 분석·기록에 묶이고, 요약·변화도 기록 단위다. 파일 하나만 지우면 해당 파일 내용이 요약·근거에 남거나 파일 배열의 순서 매칭이 어긋날 수 있다.

구현 전에 확인할 항목:

- 파일 ID 기반으로 원본과 분석 결과를 안정적으로 연결한다.
- 삭제 자료의 원본 BLOB·메타정보·분류·개수·관련 참조를 함께 정리한다.
- 다중 파일의 나머지 자료와 기록은 보존한다.
- 텍스트·링크 자료는 기록 삭제와 어떻게 구분할지 정한다.
- 마지막 자료 삭제 시 기록도 지울지, 본문만 남길지 정한다.
- 삭제 자료가 포함된 기록 요약·타임라인을 재분석할지 제거할지 정한다.

### Journey 및 브라우저 정리

활동·자료를 삭제하면 그 내용을 담은 Journey 저장 스냅샷과 인용도 처리해야 한다. 단순 stale 표시만으로 삭제한 본문이 결과에 남지 않는다고 보장할 수 없다. 관련 결과를 정리하고 재분석을 안내하는 방향을 제안하며, 과거 스냅샷 포함 삭제 범위는 미결정이다.

삭제 후 활동 수·자료 수·검색·상세·열린 Drawer와 브라우저 채팅 세션의 복원 값을 함께 갱신한다. 삭제한 카드에서 다시 저장하는 동작과 여러 탭에서 오래된 자료가 표시되는 경우도 확인한다.

## 9. Growth Journey 분야 동적 분류

현재 성장 유형(type)은 AI가 생성하지만 분야(axis)는 planning/technology/data/collaboration/other의 고정 enum이다. 화면 표시는 기획 / PM, AI·기술, 데이터, 발표·협업, 기타다.

개선 제안은 실제 확정 기록·이벤트를 바탕으로 분야도 생성하는 것이다. ‘전체 분야’는 서버 또는 화면이 공통 선택지로 추가하고, 모델은 실제 이벤트에 쓰인 분야만 반환한다. 단순히 화면 enum만 제거해서는 충분하지 않다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 활동 유형 | 어떤 종류의 활동인가 | 해커톤, 동아리 |
| 성장 유형 | 어떤 성장이 나타났는가 | 문제 재정의, 피드백 반영 |
| 분야 | 어떤 영역의 경험인가 | 디자인, 데이터, 교육 |

모델·저장 스키마·프롬프트·백엔드 검증·이벤트 참조·필터를 함께 바꾼다. 중복·예약 값·미등록 분야 참조·사용하지 않은 분야를 검사한다. 기존 고정 분야 저장 결과도 읽을 수 있도록 하며, 기존 결과를 조회만으로 유료 재분석하지 않는다.

분야 수 제한, 이름 재사용 범위, 분야 이모지 도입 여부는 미결정이다. 이 계획은 Journey 자동 분석 도입을 포함하지 않는다. 현재 수동 분석/갱신 방식을 요청 없이 바꾸지 않는다.

관련 위치: `ai-api-server/app/journey.py`, `app/prompts/journey.md`, `api-server/src/journey.js`, `src/services/journey.ts`, Journey 타입·화면.

## 10. 권장 구현 순서

아래는 제안 순서이며 사용자 확인 없이 모두 구현하는 지시가 아니다.

1. 홈 응답 구분과 신규 활동 사용자 확인 저장을 설계·구현한다. 일반 대화·신규·기존·미확정 응답 계약을 정리한다.
2. 말투와 카드 제목·요약 중복을 정리한다. 새 카드와 기존 단일/다중 파일 UI를 함께 확인한다.
3. 활동 전체 요약·기간·역할 편집과 갱신 기준을 정한다.
4. 파일별 참조·삭제 범위를 확정한 뒤 활동 삭제와 개별 자료 삭제를 구현한다.
5. Journey 분야 동적 분류와 기존 저장 결과 호환을 구현한다.

각 단계에서 관련 기능 문서·API 계약·현재 작업 인수인계를 갱신한다. 실제 구현을 완료한 항목만 완료로 기록한다.

## 11. 검증 계획

아래는 전체 개선의 검증 계획이다. 1단계 자동 검사 결과는 구현 기록을 따르며, 실제 모델·브라우저 및 후속 기능 검증은 아직 수행하지 않았다.

- 일반 인사·질문은 일반 말풍선으로 표시되고 활동을 생성하지 않는다.
- 신규 활동의 단일 파일은 변화 없음으로 오인하지 않으며 저장 전 활동 수가 늘지 않는다.
- 신규 제안을 기존 활동으로 연결하거나 이름·유형을 바꿔 저장할 수 있다.
- 중복 클릭·재요청·활동명 충돌·통신 실패에도 중복 활동·기록을 만들지 않는다.
- 기존 활동의 변화 있음/없음과 다중 파일·링크·활동 미확정 흐름을 유지한다.
- 제목과 요약이 중복되지 않고 설명은 해요체이며 인용 원문은 유지된다.
- 저장 전 새로고침·홈 재진입 후 후보와 원본 연결을 복원한다.
- 활동 전체 요약은 확정 기록만 사용하고 기간·역할을 추정하지 않는다.
- 변화 수정·기록 이동·삭제에 따라 타임라인과 요약 상태가 일치한다.
- 활동 하나 삭제 시 다른 활동은 유지되고 관련 근거·원본·스냅샷을 정리한다.
- 다중 파일 중 하나 삭제 시 나머지 파일과 분류·근거 연결이 어긋나지 않는다.
- Journey 분야·필터·근거 참조와 과거 결과 호환을 확인한다.
- 오류 시 기존 데이터·분석 결과 보존, 삭제 롤백·진행 작업 충돌을 확인한다.
- 모바일·긴 활동명/파일명·키보드·모달 초점·확인 오류를 브라우저에서 확인한다.

자동 검사는 메모리·임시 DB로 수행하고 실제 공유 DB를 검사용으로 삭제하지 않는다. 실제 모델 호출은 필요한 범위에서만 수행하고 유료 호출·브라우저 확인·자동 검사를 구분해 기록한다.
