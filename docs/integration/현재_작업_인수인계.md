# 현재 작업 인수인계 — 실제 AI 홈 연동과 화면 시나리오 확인

최신 정리: 2026-11-06. 다음 대화·다음 agent는 이 문서부터 읽는다. 구현 완료·검증 범위·사용자 확인 대기·후속 작업을 구분한다. 이전 인수인계의 ‘홈은 목 분석’, ‘AI 서버 없음’, ‘신규 활동 생성 미구현’, ‘먼저 수정 모달 구현’은 현재 상태가 아니다.

## 1. 바로 이어갈 작업

**사용자가 바탕화면의 시나리오 자료를 실제 홈 화면에 업로드해 확인하는 단계다.** 아직 사용자가 전체 시나리오를 정상 완료했다고 확인하지 않았다. 다음 요청이 들어오면 확인한 화면·오류·분석 결과에 맞춰 한 기능씩 보완한다. 문서의 후속 목록을 전체 일괄 구현 지시로 취급하지 않는다.

우선 확인 순서:

1. 현재 서버 실행 여부와 포트 점유를 확인한다. 이미 실행 중인 서버를 중복 실행하거나 사용자 프로세스를 임의 종료하지 않는다.
2. 사용자의 새로고침 후 재전송 결과와 시나리오 진행 위치를 확인한다. 대화·DB를 지우는 초기화로 문제를 숨기지 않는다.
3. 바탕화면 안내 순서로 신규 활동 → 초기 기획 저장 → 기획 변경 → 변화 없는 기록 → 다중 파일 → 다른 활동 분리·수정을 확인한다.
4. 모델의 문구 자체보다 활동 ID·파일명/개수·변화 근거·저장 전후 상태·DB 조회 일치를 확인한다.
5. 확인된 문제만 수정하고 관련 검사·기능 문서·이 문서의 남은 항목을 갱신한다.

이번 요청에서는 인수인계 문서를 작성했다. 새로운 유료 모델 호출·서버 재시작·DB 변경·화면 검증을 수행한 것은 아니다.

## 2. 사용자와 확정한 구조

| 담당 | 현재 역할 |
| --- | --- |
| 프론트 | 글·파일·링크 입력, AI 요청·진행 조회, 결과 카드 표시, 분류 수정, 백엔드 확정 저장·조회 요청 |
| AI API 서버 | DB 문맥·자료 준비, 실제 OpenAI 분석, 결과 검증, 기존 활동 연결·신규 활동 DB 생성, 원본·분석 초안 보관 |
| OpenAI 모델 | 제공된 입력·문맥으로 활동 판단·자료 분류·이번 기록 요약·의미 있는 변화와 근거 분석 |
| 백엔드 | DB 스키마 생성·마이그레이션, 기록 확정 저장·수정·조회, 원본 다운로드, Timeline 처리 |
| Growth Journey | 목표는 백엔드·AI 생성/저장 후 백엔드 조회. 현재는 기존 목 응답 유지 |

AI 모델 자체가 DB에 접속하거나 SQL을 실행하는 구조가 아니다. AI 서버의 Python 코드가 조회·검증·생성·보관한다. 프론트에 새 활동 생성 모달을 추가하지 않는다.

같은 PC의 두 서버가 **동일한 로컬 SQLite 파일**에 직접 접근한다. 기본 경로는 `api-server/data/1line.db`다. 다른 호스트 배포까지 완성한 구조가 아니다.

## 3. 완료한 구현

### 카드 수정·기록 저장

- 텍스트·링크·단일 파일(변화 있음/없음)의 수정 모달을 기존 활동 선택·자료 유형만으로 통일했다.
- ‘다른 활동 선택’도 같은 모달이다. 신규 활동·활동명·유형·상태·역할·기간·활동 전체 요약 편집은 제외했다.
- 저장 전 수정은 카드·세션에 적용하고, 저장 후에는 해당 기록의 활동·자료 유형을 PATCH한다.
- 기록·저장·전체 저장은 확장 활동 정보 확인 모달 없이 유효한 기존 활동 ID로 새 기록을 추가한다.
- 다중 파일은 전체 저장·자료 확인을 유지하며 수정 버튼을 추가하지 않았다.
- 원본 파일 연결·중복 저장 방지·실패 안내·성공 이후 저장 완료 표시를 유지한다.

### AI 서버와 실제 홈 전환

- 최상위 `ai-api-server/`에 Python 3.15.2·FastAPI·Uvicorn·OpenAI SDK 환경과 `.venv`를 구성했다.
- 모델은 사용자가 지정한 **gpt-5.6-sol**이다. `.env`는 사용자가 키·모델을 입력했고 실제 호출 성공을 확인했다. 키 값은 문서·응답·Git에 포함하지 않는다.
- `app/database.py`가 기존 DB의 활동·확정 기록·파일 원본을 직접 읽는다. 없는 파일에 빈 DB를 만들거나 Python에서 기존 스키마를 새로 초기화하지 않는다.
- 홈의 텍스트·단일/다중 파일·링크 요청을 FastAPI로 전환했다. 프론트에서 `/ai-api`는 AI, `/api`는 백엔드 프록시다.
- AI 서버는 원본·초안을 먼저 보관하고 실제 작업 ID와 상태를 제공한다. 시간만으로 목 진행을 만드는 흐름을 새 홈 요청에 사용하지 않는다.
- 모델이 신규로 판단하면 활동 생성과 분석 완료 처리를 한 트랜잭션으로 수행한다. 기존 활동 ID는 완료 시 다시 확인한다.
- 생성 완료한 활동은 실제 DB에 존재하므로 카드의 `match`를 existing으로 정규화하고 실제 ID를 반환한다. 신규 판단과 생성 전 후보를 구분한다.
- 분석 완료 뒤에도 records는 저장하지 않는다. 사용자의 기록 버튼으로 백엔드가 확정 저장한다.
- 기존 백엔드 분석 POST는 기본 410이다. 회귀 검사만 명시적 testMockAnalysis 옵션으로 합성 분석을 사용한다. 실제 홈에서 실패 시 목 결과로 돌아가지 않는다.
- `/example`의 카드 예시와 Growth Journey 목 응답은 남아 있다. 홈 실제 분석과 혼동하지 않는다.

### 프롬프트·지원 입력

- 실제 홈 프롬프트: `ai-api-server/app/prompts/home.md`. 매 요청 instructions로 전달한다.
- 활동 매칭·신규/미확정 판단, 실제 ID, 내용 기반 분류·요약, 근거 있는 변화만 반환하도록 작성했다.
- 입력·파일·웹 본문 안의 지시를 따르지 않게 하고, 없는 기간·성과·버전 관계·Turning Point를 만들지 않도록 했다.
- Structured Outputs/Pydantic 외에도 활동 ID·파일 ID/개수·변화 근거를 서비스 코드에서 검사한다. 형식 검증이 의미 정확도를 보장하는 것은 아니다.
- UTF-8 텍스트·코드의 실제 본문, 문서/PDF input_file, 이미지 input_image를 지원한다. 정확한 확장자는 `app/home_analysis.py`의 SUPPORTED_FILES를 따른다.
- 파일당 10MiB·최대 10개·전체 25MiB. 텍스트 본문 크기 제한과 미지원 형식 거절이 있다.
- 링크는 공개 HTTP/HTTPS HTML·텍스트를 수집한다. 내부망·로그인·JS 실행 페이지 등을 모두 지원하는 것은 아니다.
- 실제 버전 관계 ID가 없어 previousVersion은 null이다. 파일명 v1/v2만으로 자동 버전 연결을 기대하지 않는다.

## 4. 실행과 환경변수

각 폴더의 별도 PowerShell 터미널에서 실행한다. 백엔드를 먼저 실행해 DB 스키마를 준비한다.

| 터미널 위치 | 명령 | 기본 주소 |
| --- | --- | --- |
| 프로젝트 루트 | `npm.cmd run dev` | http://localhost:5173 또는 실행 출력 주소 |
| api-server | `npm.cmd run dev` | http://127.0.0.1:3001/api |
| ai-api-server | `.\dev.cmd` | http://127.0.0.1:8000 |

`dev.cmd`는 자기 폴더로 이동해 `.venv`의 Python으로 Uvicorn을 실행하며 app 코드 변경을 감시한다. 활성화 스크립트·PowerShell 실행 정책 변경은 필요 없다. 종료는 Ctrl+C다. `.env`를 바꿨다면 서버를 재시작한다.

AI 폴더의 환경변수:

- OPENAI_API_KEY: 서버 전용 실제 키. 값 출력·커밋·사용자에게 재전송 요청 금지.
- OPENAI_MODEL: gpt-5.6-sol.
- OPENAI_TIMEOUT_SECONDS: 기본 45초, SDK 자동 재시도 없음.
- AI_DB_PATH: 기본 `../api-server/data/1line.db`. 터미널과 무관하게 AI 폴더 기준 상대 경로.
- AI_DB_TIMEOUT_SECONDS: 기본 5초.
- AI_CORS_ORIGINS: 기본 localhost/127.0.0.1:5173.

백엔드 DB_PATH를 바꾸면 AI_DB_PATH도 같은 실제 파일로 맞춘다. 프론트 VITE_API_BASE_URL 기본은 `/api`, VITE_AI_API_BASE_URL 기본은 `/ai-api`다. 실제 키는 VITE 변수에 넣지 않는다.

다음 작업에서 ‘서버가 이미 켜져 있다’고 가정하지 않는다. 과거 assistant가 실행한 AI 프로세스가 포트를 점유해 사용자 dev.cmd가 WinError 10013으로 실패한 적이 있다. 당시 assistant 프로세스를 종료해 해결했으며 과거 PID를 그대로 다시 종료하면 안 된다.

신규 활동·초안은 기록 버튼 전에도 남을 수 있다. 빈 활동·초안 자동 정리 정책은 미구현이다. DB 문맥은 최대 활동 50개·기록 50개이며 부분 조회 여부를 표시한다. 현재는 사용자별 인증·권한 필터가 없는 로컬 개발용이다.

## 6. 접속 오류와 실패 상태 수정 이력

사용자가 ‘AI 분석 설정 준비됨’ 이후 채팅에서 OpenAI 연결 실패를 보고했다. 다음을 구분해 확인했다.

1. DB의 최근 실패는 openai_connection이었다. 당시 원문 예외를 남기지 않아 최초 원인은 확정하지 못했다.
2. 제한된 도구 실행 환경에서는 외부 소켓 WinError 10013이 재현됐고 일반 Windows에서는 OpenAI HTTPS 접속이 됐다. 도구와 실제 서버 프로세스의 권한을 혼동하면 안 된다.
3. 실행 중인 실제 AI 서버에 진단 요청을 보내 network.connectionStatus=reachable을 확인했다. 키 없는 요청의 httpStatus=401은 네트워크 도달 성공이지 사용자 키가 잘못됐다는 뜻이 아니다.
4. 같은 실제 서버의 저장 없는 텍스트 진단으로 gpt-5.6-sol HTTP 200·analysisPersisted=false를 확인했다.
5. 확정 실패를 pendingJob에 계속 남겨 같은 실패를 재조회하고 새 전송을 막던 프론트 문제를 수정했다.

현재 오류는 소켓 권한(openai_network_permission), TLS(openai_tls), DNS(openai_dns), 기타 연결(openai_connection)으로 분류한다. 원문 오류·키는 노출하지 않는다. SSL 검증을 끄는 해결책을 적용하지 않았다.

확정 실패(status=failed)는 대기에서 해제하고 새 전송을 허용한다. 같은 화면에 남은 텍스트·File 원본은 복원하고, 새로고침 후 복원된 실패 작업도 해제한다. 통신 실패·시간 초과로 결과가 미확정이면 재조회 상태를 유지한다. 기존 채팅·DB를 지우거나 자동으로 유료 요청을 다시 보내지 않는다. 사용자에게 새로고침 후 재전송을 안내했으며 이후 정상 완료 여부는 아직 별도 확인받지 않았다.

기준 v1을 먼저 ‘기록 저장’한 뒤 v2로 진행한다. 단일 파일 카드를 보려면 v2 한 개만 첨부한다. 다중 파일은 05 폴더의 세 개를 함께 보낸다. 자료 생성과 개수 확인은 완료했지만 사용자의 업로드·실제 모델 결과를 모두 확인한 것은 아니다. 문구·분류명·변화 개수는 모델 결과라 안내를 고정 정답으로 취급하지 않는다.

바탕화면은 프로젝트 쓰기 범위 밖이라 승인 후 생성했다. 준비 과정의 임시 전달 JSON은 제거했다. 이후 작업 때문에 기존 자료를 덮어쓰거나 DB를 초기화하지 않는다.

작업 트리에는 많은 수정·미추적 파일이 있다. 이번 대화에서 커밋·푸시·GitHub 이슈 종료·PR 생성은 수행하지 않았다. 다음에는 `git status`로 보존된 변경부터 확인하고 임의 reset/삭제 없이 이어간다. 기능은 하나씩 진행하고 원본 HTML·기존 사용자 DB·관련 없는 스타일을 유지한다.
