## 1. 현재 상태와 다음에 바로 할 일

홈과 Growth Journey의 실제 AI 연동 및 목 실행 코드 제거를 완료했다. 사용자 요청으로 공유 DB의 8개 테이블을 비웠다. 이후 서버 자동 재시작으로 예시 활동 5개가 재등장하여 자동 INSERT 코드를 제거하고 해당 항목도 삭제했다. 이번 문서 갱신 시 읽기 전용 조회로 **8개 테이블 모두 0건**을 재확인했다.

다음은 빈 상태에서 실제 사용자 입력과 화면을 확인하는 단계다. 문서의 목록을 전체 일괄 구현 지시로 해석하지 않는다.

1. 현재 서버·포트부터 확인한다. 기존 서버를 중복 실행하거나 사용자 프로세스를 임의 종료하지 않는다.
2. 나의 발자국에 활동이 없고 Journey가 미분석 상태인지 확인한다. 이전 채팅은 DB가 아닌 탭의 sessionStorage 복원일 수 있다. 요청 없이 세션·DB를 다시 지우지 않는다.
3. 홈에서 실제 신규 활동 자료를 보내 활동 생성·실제 ID 연결을 확인한다. 분석 완료와 사용자의 확정 기록 저장을 구분한다.
4. 바탕화면 시나리오 순서로 초기 기획 저장 → 기획 변경 → 변화 없음 → 다중 파일 → 다른 활동 분리/분류 수정을 확인한다.
5. 저장 후 Journey의 **성장 분석하기**를 실행한다. AI 생성 분류·이모지·요약·이벤트·인용 근거·DB 저장 결과를 확인한다. 성장 근거 부족 시 빈 이벤트는 정상일 수 있다.
6. 기록을 수정한 뒤 Journey 재조회에서 갱신 필요 표시를 확인하고 **분석 갱신**을 실행한다. 필터·상세·실패 시 기존 결과 보존도 확인한다.
7. 발견한 문제만 하나씩 보완하고 해당 기능 문서와 이 문서를 갱신한다.

**자동 성장 분석은 아직 구현하지 않았다.** 화면 진입 시 GET 조회만 자동 실행하고 실제 AI는 버튼에서 호출한다. ‘기록 변경 후 Journey 방문 시 필요한 경우만 자동 분석하고 실패 시 재시도 버튼 제공’은 장단점·호출 횟수만 논의한 제안이다. 사용자가 자동 방식 구현을 확정 요청한 것으로 취급하지 않는다.

## 2. 실제 호출 구조

| 기능 | 현재 흐름 |
| --- | --- |
| 홈 분석 | 프론트 → FastAPI AI API → 공유 DB 문맥 조회 → OpenAI → 활동 생성/연결·원본/초안 보관 |
| 홈 저장·수정 | 프론트 → 백엔드 → DB 확정 저장·수정 |

Journey 프론트는 AI API를 직접 호출하지 않는다. OpenAI 모델 자체는 DB에 접속하지 않고 서버 코드가 읽어 전달한 데이터를 분석한다. 두 서버가 같은 PC의 동일 SQLite 파일에 직접 접근하는 로컬 개발 구조이며 다른 호스트 배포까지 완성한 구조가 아니다.

## 3. 완료한 구현

### 홈 실제 AI·목 제거

- 텍스트·단일/다중 파일·공개 링크를 실제 OpenAI로 연결했다. 기존 모델 설정은 gpt-5.6-sol이다. 키는 출력·문서화·커밋하지 않는다.
- 신규 활동이면 AI 서버가 생성하고 실제 ID를 반환한다. 활동·초안은 기록 버튼 전에도 남을 수 있지만 records는 사용자의 저장 버튼에서 생성한다.
- 수정 모달은 기존 활동·자료 유형에 한정한다. 저장 전은 카드·세션에, 저장 후는 해당 기록 PATCH에 반영한다. 다중 파일은 전체 저장·자료 확인을 유지한다.
- 확정 실패 작업은 대기에서 해제해 재전송을 허용한다. 미확정 통신 실패는 재조회 상태를 유지한다. 목 fallback·유료 자동 재전송은 없다.
- 프론트 홈 목 서비스·분류·진행·상태 예시와 /example 카드를 제거했다. /example은 홈으로 이동한다.
- 백엔드의 목 분석 생성·시간 기반 진행·testMockAnalysis 옵션을 제거했다. 이전 백엔드 홈 분석 POST·작업 GET은 항상 410으로 FastAPI 사용을 안내한다.

### Growth Journey 실제 AI·DB·분석 분류

- 확정 저장 기록만 분석한다. 미저장 초안·기록 없는 활동은 제외한다. 기록 본문·저장된 요약·변화·활동 정보·파일 ID/이름을 읽으며 BLOB을 다시 분석하지 않는다.
- 전용 프롬프트는 ai-api-server/app/prompts/journey.md, 현재 버전은 **journey-v2**다.
- 성장 유형은 고정 다섯 enum 대신 AI가 value·label·icon을 생성한다. 같은 의미를 묶고 실제 이벤트에 쓰인 유형만 최대 8개 반환한다. ‘전체’는 서버가 추가한다.
- 필터 버튼·이벤트 배지에서 같은 이모지를 표시하고 경험 배지도 별도 icon을 쓴다. **분야(axis)는 기존 기준을 유지**했다. 이전 무아이콘 결과도 조회할 수 있다.
- Python·백엔드에서 분류 ID/라벨 중복·예약값 all·미등록 이벤트 유형·미사용 분류·누락 아이콘을 검사한다.
- 요약·배지·이벤트마다 실제 기록 ID와 연속 원문 인용을 검증한다. Before/After는 서로 다른 기록의 근거를 요구한다. 첫 경험은 제공된 기록 범위로 한정한다. 검증이 의미 정확도 전체를 보장하는 것은 아니다.
- journey_analyses에 결과 JSON·원본 해시·기록 수·모델·프롬프트 버전·시각을 저장한다. 홈 기록·Timeline은 수정하지 않는다. 재조회 시 저장 이벤트 ID를 유지하고 재분석은 새 스냅샷이다.
- 분석 시점과 저장 시점의 기록·활동·자료 메타정보가 다르면 409로 저장을 거절한다. 이후 GET에서도 해시로 stale을 계산한다.
- 실제 모델은 분석/갱신 버튼에서만 호출한다. 같은 백엔드의 동시 실행은 409다. 실패 시 이전 결과를 보존한다. 페이지 이탈 후에도 접수된 서버 분석은 완료·저장될 수 있다.
- 요약·배지·AND 필터·상세를 유지했다. 비교 없는 이벤트도 근거가 있으면 상세를 열 수 있다. 날짜는 **근거 기록의 저장 월**이며 실제 활동 발생 시점으로 추측하지 않는다.

### DB 초기화·예시 활동 재등장 방지

- 사용자 요청으로 8개 테이블의 활동·기록·원본·초안·작업·Timeline·성장 결과를 삭제했다. 스키마는 유지했다.
- api-server/src/database.js의 예시 활동 5개 자동 INSERT를 제거했다. 재시작·DB 재오픈으로 활동이 다시 생기지 않는다.
- 재등장한 미연결 예시 5개를 삭제했다. 이후 실제로 생성하는 활동을 자동 삭제하는 정책은 추가하지 않았다.
- 검사 예시는 api-server/test-support/database.js가 메모리·시스템 임시 폴더 DB에만 넣는다. 사용자 DB에서는 실행할 수 없도록 제한했다.
- api-server/test-support/와 tests/fixtures/는 검사 전용이다. src/mocks/의 남은 최근 목록·발자국 예시는 현재 화면에서 참조하지 않는 과거 파일이다.

## 5. 실행·환경

먼저 실행 상태를 확인하고 백엔드부터 실행해 스키마를 준비한다.

| 위치 | PowerShell 명령 | 기본 주소 |
| --- | --- | --- |
| api-server | npm.cmd run dev | http://127.0.0.1:3001/api |
| ai-api-server | .\dev.cmd | http://127.0.0.1:8000 |
| 프로젝트 루트 | npm.cmd run dev | http://localhost:5173 또는 출력 주소 |

- 공유 DB 기본은 api-server/data/1line.db다. 백엔드 DB_PATH를 바꾸면 AI_DB_PATH도 같은 실제 파일로 맞춘다.
- 백엔드 AI_API_BASE_URL 기본은 http://127.0.0.1:8000 이며 Journey 서버 간 호출에 사용한다.
- AI 환경은 OPENAI_API_KEY, OPENAI_MODEL, OPENAI_TIMEOUT_SECONDS(기본 45초), AI_DB_TIMEOUT_SECONDS(기본 5초), AI_CORS_ORIGINS다.
- 프론트 VITE_API_BASE_URL 기본 /api, VITE_AI_API_BASE_URL 기본 /ai-api. 실제 키를 VITE 변수에 넣지 않는다.
- dev.cmd는 .venv Python으로 Uvicorn을 실행한다. 활성화·실행 정책 변경은 필요 없다. 키·모델 변경 시 해당 서버를 재시작한다.
- 제한 환경의 포트 조회에서 실제 Windows 서버가 안 보였던 적이 있다. 빈 조회만으로 서버 미실행을 단정하지 않는다. 기존 프로세스를 임의 종료하거나 과거 PID를 재사용하지 않는다.
- 이번 문서 갱신에서 서버 재시작·유료 호출·DB 변경은 하지 않았다. 실행 여부는 다음 작업에서 다시 확인한다.

## 7. 다음 작업·후속 범위

**우선:** 빈 상태에서 홈 신규 활동 → 기록 저장 → 나의 발자국 → Journey 분석/동적 분류/근거 → 기록 수정 → 갱신 필요 → 수동 갱신을 사용자 화면으로 확인하고 발견한 문제만 보완한다.

**검토 대기:** Journey 자동 분석. 변경 없는 방문에는 모델을 호출하지 않고 미분석/변경 후 방문에만 호출하는 방식은 제안 상태다. 수동 갱신을 드물게 하는 사용자보다 호출이 늘 수 있다는 점을 설명했다. 요청 없이 버튼을 제거하거나 자동 호출을 추가하지 않는다.

**장기 후속:** 성장 범위 분할(현재 기록 100개·JSON 문맥 250000자), 분산 작업 잠금·작업 큐·재시작 복구, 근거 자료 Drawer 이동, 관련성 기반 홈 문맥 조회, 빈 활동/초안 정리, 인증·권한, 최종 협업용 API 명세·ERD·데이터 사전, 외부 배포. 이벤트는 최대 20개·경험 배지 10개다. 한도 초과는 명시적으로 거절한다.

바탕화면의 1Line_AI_시나리오_자료/00_사용안내.md 순서를 따른다. 안내 1개·업로드 자료 9개를 준비한 이력이 있다. 기존 자료를 덮어쓰지 않고 초기 기획 v1을 기록 저장한 뒤 v2로 진행한다. 모델 문구·분류명·이벤트 수는 고정 정답이 아니다.

## 8. 다음 담당자가 지킬 사항

- [개발 규칙](../개발_규칙.md)을 따른다. 기능을 하나씩 진행하고 원본 HTML·관련 없는 스타일을 변경하지 않는다.
- 이번 DB 전체 삭제는 사용자 명시 요청으로 수행한 일회성 작업이다. 다음 작업에서도 삭제가 계속 허용된 것으로 해석하지 않는다.
- git status부터 확인하고 기존 수정·미추적 파일을 보존한다. 커밋·푸시·PR 생성은 하지 않았다. 직전 ‘깃 컨벤션’ 요청은 취소되고 문서 최신화로 전환됐다.
- [Journey API](../journey/성장_분석_API.md), [Journey 상태](../journey/현재_구현_상태.md), [홈 AI 연동](../../ai-api-server/docs/홈_실제_AI_연동.md)을 참고한다. 과거 이력보다 최신 절·코드를 우선한다.
- 명세 갱신은 AI 폴더에서 .\.venv\Scripts\python.exe -m scripts.export_openapi 를 실행한 뒤 루트 npm.cmd run docs:build 순서다. 키·모델 호출 없이 생성한다.
- 유료 검사는 필요한 경우에만 실행하고 검사 DB는 임시 파일을 사용한다. 오류 원문·키·사용자 입력을 불필요하게 출력하지 않는다.
