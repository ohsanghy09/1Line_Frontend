# 다음 작업 — 실제 서버 전환 및 연동 검증

작성일: 2026-11-06. 다음 작업은 백엔드·AI 파트의 구현과 배포를 진행하고, 전달받은 서버 주소로 프론트를 연결한 뒤 실제 기능을 검증하는 것이다. 현재 프론트의 공개 API 계약을 기준으로 진행한다.

## 현재 완료한 범위

- 전달 자료는 [docs/handoff 전체](../handoff/README.md)다. 개발 소스·개인 DB·로컬 가상환경은 제공하지 않는다. 각 파트는 선택한 환경에서 구현한다.
- Journey는 journey-v5다. AI 내부 원문 근거 카탈로그 → 모델의 근거 ID 선택 → 서버의 정확한 원문 복원을 적용했다. 공개 응답의 근거는 기존 {recordId,quote}를 유지한다.
- Python 65개, 백엔드·프론트 Journey 관련 21개 자동 검사를 통과했다. 실제 새 파트 서버·배포 브라우저·실제 모델 연동을 검증한 결과는 아니다.
- 최신 handoff 문서 21개를 바탕화면의 `1Line_handoff.zip`으로 다시 압축하고 기존 ZIP을 교체했다. 압축 내용과 원본 일치를 확인했다. 이후 전달 문서를 수정하면 ZIP도 다시 생성해야 한다.

## 역할과 작업 순서

| 순서 | 담당 | 작업과 완료 조건 |
| --- | --- | --- |
| 1 | 백엔드·AI | handoff의 API·데이터·오류·프롬프트·검증 규칙을 읽고 각 환경에서 구현한다. 계약과 다른 부분은 연결 전에 구체적으로 공유한다. |
| 2 | 백엔드·AI | 문맥·초안·원본·완료 결과 전달, 내부 인증, 스냅샷 검증을 연결한다. 같은 PC의 DB 파일을 공유한다고 가정하지 않는다. |
| 3 | 백엔드·AI | 실제 서버를 배포하고 공개 API 주소·상태 확인 주소·인증 규약·검증 결과·미완료 항목을 프론트 담당자에게 전달한다. |
| 4 | 프론트 | 두 API 기본 주소와 필요한 라우팅·인증 전송 설정을 반영하고 다시 빌드·배포한다. |
| 5 | 전체 | 배포 프론트에서 실제 모델과 저장소를 사용해 아래 기능을 확인하고 실패를 수정한다. |
| 6 | 프론트 | 실제 연동이 안정적으로 동작한 뒤 기존 로컬 개발 서버 의존성의 보관·정리 범위를 검토한다. 연결 전에 삭제하지 않는다. |

서버 간 분리 전달 규격은 [전달 계약](../handoff/common/서버간_데이터_전달_계약.md)에 정의된 새 구현 기준이다. 현재 로컬 개발 서버가 해당 분리 규격을 이미 구현했다는 뜻은 아니다.

## 서버 파트에서 전달받을 정보

- 백엔드·AI 각각의 개발/운영 공개 Base URL과 상태 확인 주소. Base에 `/api`가 포함되는지 명시한다.
- 두 서버 사이의 내부 주소·접근 방식·인증·데이터 전달 구현 결과. 서버 비밀키를 프론트에 전달하거나 노출하지 않는다.
- 배포 프론트 origin을 허용하는 HTTPS·CORS 설정과 업로드·모델·프록시 제한 시간.
- 인증을 적용한다면 헤더/쿠키·사용자 식별·만료/갱신·401/403 처리 규약. 현재 프론트가 그 방식을 이미 지원한다고 가정하지 않는다.
- 기능별 정상/실패 검증 결과, 적용한 Journey 버전, 미검증·미완료 항목과 재현 방법.

## 프론트 연결 작업

| 설정 | 용도 |
| --- | --- |
| `VITE_API_BASE_URL` | 백엔드 공개 API의 기본 주소 |
| `VITE_AI_API_BASE_URL` | AI 공개 API의 기본 주소 |

공개 API의 경로·요청·응답·오류 형식이 문서와 같으면 기본 URL 설정 변경을 중심으로 연결한다. 환경변수는 빌드 시 반영되므로 변경 후 다시 빌드·배포한다. API 기본 주소 뒤에 서비스의 `/journey`, `/chat` 같은 경로가 붙으므로 `/api`를 중복하거나 빠뜨리지 않는다.

로컬 `/api`, `/ai-api`는 Vite 개발 프록시 별칭이다. 정적 배포에서 자동으로 동작한다고 가정하지 않으며 실제 HTTPS 주소 또는 별도로 구성한 배포 프록시를 사용한다. SPA HTML이 아닌 API JSON이 반환되는지 확인한다.

쿠키 인증이면 credentials 등 전송 설정이, 헤더 인증이면 헤더 구성과 만료 처리가 추가로 필요할 수 있다. 계약과 경로 또는 응답이 달라졌다면 URL만 바꾸지 말고 차이를 확인해 수정한다. 상세 기준은 [배포와 서버 연결](../handoff/integration/배포와_서버_연결.md)을 따른다.

## 실제 연동 검증

- [ ] 일반 대화, 텍스트·단일/다중 파일·링크 분석과 진행 상태·실패 처리.
- [ ] 신규/기존 활동 연결과 사용자 확정 저장. 완료 직후 백엔드가 초안·원본을 찾아 저장할 수 있음.
- [ ] 대화로 활동 정보 수정과 자료 저장 후 활동 정보 자동 갱신.
- [ ] 나의 발자국 목록·검색·상세·Timeline·원본 조회.
- [ ] 자료 개별 삭제·활동 삭제·전체 삭제, 실패 시 보존, 삭제 후 재추가.
- [ ] Journey 수동 분석·갱신·저장·필터·원문 근거·이전 결과 보존. 새 결과의 promptVersion은 journey-v5.
- [ ] 빈 상태·중복 요청·연결 끊김·시간 초과·재시작·분석 중 기록 변경과 인증 오류.
- [ ] HTTPS·CORS·업로드 제한·프록시 제한 시간이 실제 배포 브라우저에서 동작함.

각 항목의 상세 기대 결과는 [연동 검증 시나리오](../handoff/integration/연동_검증_시나리오.md)를 따른다. 확인한 항목만 완료로 표시하고 실패·미수행은 구분해 기록한다.

## 완료 판정과 현재 상태

현재는 **전달 자료 준비 완료, 실제 파트 서버 구현·배포와 프론트 전환은 대기** 상태다. 서버 주소를 전달받았다는 이유만으로 연동 완료로 표시하지 않는다.

완료 기준은 배포 프론트에서 새 서버로 입력 → 분석 → 확정 저장 → 재조회가 동작하고, 수정·삭제·Journey 및 실패 보존까지 확인되는 것이다. 기존 홈·공용 컴포넌트는 연동에 필요한 구체적인 변경 사유 없이 수정하지 않는다.
