# 백엔드·AI 개발 서버 분리와 연동 작업 계획

> 재개할 때는 [현재 작업 인수인계](현재_작업_인수인계.md)부터 확인한다. 실행 스크립트·접속 진단·실패 작업 해제와 바탕화면 자료를 포함한 사용자 화면 검증이 현재 단계다. 아래 구현 계획의 완료 여부는 최신 인수인계를 따른다.

최신 완료 범위: 홈의 실제 OpenAI 분석→신규 활동 생성/기존 활동 연결→분석·원본 보관→백엔드 기록 저장→조회까지 연결했다. 실제 텍스트·단일/다중 텍스트 파일·공개 링크 통합 검사를 임시 DB에서 통과했다. [최신 구현·기능 흐름·프롬프트·검증](../../ai-api-server/docs/홈_실제_AI_연동.md)을 먼저 읽는다. 아래 신규 활동·분석 저장 미구현 안내는 이전 단계 기록이다. Growth Journey는 이번 홈 전환과 별도다.

최신 진행: **기존 백엔드와 AI 서버가 하나의 로컬 SQLite에 직접 연결하는 방식으로 구현했다.** 스키마 생성·마이그레이션은 기존 백엔드가 맡고 Python은 별도 접근 모듈로 같은 파일을 조회한다. [DB 직접 연결 안내](../../ai-api-server/docs/DB_직접_연결.md)를 참고한다. 신규 활동 생성·분석 보관·프론트 전환은 후속 작업이며 아래 DB 공유 방식 제안은 이 구현 이전 계획이다.

작성일: 2026-11-06. 상태: 다음 구현을 위한 작업 계획. 이 문서 작성으로 서버 분리·실제 AI 연동·ERD 작성이 완료된 것은 아니다.

최신 기술 결정: AI 서버는 **Python·FastAPI와 실제 OpenAI API**로 구현한다. 기본 서버·텍스트 분석 API·DB 직접 조회를 구현하고 사용자 설정의 `gpt-5.6-sol` 합성 텍스트 호출 1회를 확인했다. [실행 안내](../../ai-api-server/README.md)와 [텍스트 분석 API](../../ai-api-server/docs/텍스트_분석_API.md), [AI 서버 내부 작업 계획](../../ai-api-server/docs/작업_계획.md)을 함께 읽는다. 활동 생성·분석 보관·프론트 연결은 미완료다. 아래 목 분석 활용은 보조 테스트 선택지이며 실제 OpenAI 연결을 대체하는 완료 기준이 아니다.

최신 사용자 확인: **AI API 개발 서버를 먼저 구성하고, 기존 백엔드·AI API 명세를 최신 결정에 맞춰 적용하면서 백엔드·프론트를 연결한다. 직접 동작을 확인한 뒤 검증된 구현 현황·기능 흐름·API 명세·ERD를 다른 파트에 전달한다.** 기존 명세는 출발점이며 이전 구조와 충돌하는 항목은 그대로 구현하지 않는다.

## 목표와 읽기 순서

현재 프로젝트에 백엔드 개발 서버와 AI API 개발 서버를 구성하고 프론트에서 실제 HTTP 요청·DB 저장·조회가 이어지는지 확인한다. 검증된 구현을 기준으로 API 명세·Swagger·ERD·기능 흐름·진행 현황을 정리하여 백엔드와 AI 담당 agent가 이어받을 수 있게 한다.

다음 구현은 이 문서를 먼저 읽는다. [이전 인수인계](다음_작업_인수인계.md)는 결정 배경, [카드 기록·수정](../chat/구현_기능/카드_기록_수정.md)은 최신 카드 동작, [API 계약 안내](API_계약/문서_안내.md)는 계약 초안과 협의사항을 확인할 때 읽는다. 이전 문서의 ‘모달 수정 예정’, ‘프론트 새 활동 생성 진입 필요’는 현재 작업 지시로 해석하지 않는다.

이번 요청은 작업 계획 문서 작성이다. 아래 구현 단계는 아직 실행하지 않았다. 기능은 한 단계씩 진행하고 기존 사용자 DB와 원본 HTML·관련 없는 화면 스타일을 보존한다.

## 1. 사용자 확정 방향과 미확정 설계

### 확정된 방향

- 홈 분석은 프론트가 AI 서비스에 직접 요청한다.
- AI 서비스가 신규/기존 활동을 판단한다. 신규이면 DB에 활동을 생성하고 기존이면 해당 활동을 사용한다. 프론트에는 별도 새 활동 생성 모달을 만들지 않는다.
- 기록·자료의 확정 저장은 프론트가 백엔드에 요청한다. 활동 생성과 기록 확정 저장을 구분한다.
- 나의 발자국·활동 상세·자료 패널·Timeline은 백엔드에서 조회한다.
- Growth Journey는 백엔드·AI가 분석 결과를 생성·저장하고 프론트는 백엔드에서 조회한다.
- 카드 수정은 기존 활동 선택·자료 유형만 제공한다. 저장 전에는 카드·세션에 적용하고 저장 후에는 기록 수정 API를 호출한다.
- 기록·저장·전체 저장은 활동 정보 확인 모달 없이 새 기록을 추가한다. 다중 파일에는 수정 버튼을 추가하지 않는다.

여기서 AI 서비스는 서버 애플리케이션이다. 모델의 판단 결과를 서비스 코드가 검증하고 DB에 반영하며, DB ID·트랜잭션 처리를 모델 출력에 맡기지 않는다.

### 구현 전 정할 상세 사항

| 항목 | 제안 또는 결정할 내용 |
| --- | --- |
| 개발 DB 연결 | 두 개발 서버가 하나의 개발 DB와 공통 DB 접근 모듈·마이그레이션을 사용하는 방식을 우선 제안한다. 아직 구현하거나 최종 확정한 구조는 아니다 |
| 활동 생성 시점 | 분석 완료 전 생성하여 실제 활동 ID를 응답하는 방향. 사용자가 기록을 저장하지 않을 때 남는 빈 활동의 노출·정리 정책을 정한다 |
| 신규 판단과 생성 상태 | ‘새 활동이라고 판단함’과 ‘DB 생성 완료’를 구분한다. 응답 필드명과 상태값은 구현 계약에서 확정한다 |
| 분석·원본 보관 | 분석 ID와 파일 ID를 누가 발급·보관하고 백엔드가 어떻게 읽는지 정한다. AI 서버의 ID만 반환하고 백엔드가 찾지 못하는 구조를 만들지 않는다 |
| 중복 요청 | 재시도·동시 요청 시 활동/분석/기록의 중복 생성 방지 키와 처리 규칙을 정한다. 활동명만으로 동일성을 확정하지 않는다 |
| 오류·진행·복원 | 분석 실패, DB 생성 실패, 저장 실패, 작업 조회, 새로고침 후 재개를 구분한다 |
| 데이터 접근 | 개발용 사용자 범위와 서비스별 읽기/쓰기 책임을 명시한다. 실제 인증·사용자별 권한이 없는 상태를 운영 계약으로 간주하지 않는다 |
| 모델 연결 | 초기에는 기존 목 분석을 독립 서버로 옮겨 통신·DB 흐름을 검증할 수 있다. 실제 모델·공급자·본문 추출·링크 수집은 별도 연결 상태를 표시한다 |

## 3. 목표 기능 흐름

### 분석과 활동 연결

1. 사용자가 글·파일·링크를 전송한다. 프론트는 실제 입력을 AI 개발 서버에 보낸다.
2. AI 서비스는 기존 활동·기록 문맥을 조회하고 분석한다. 목 분석을 사용할 때는 실제 의미 분석과 구분한다.
3. 기존 활동이면 실제 ID를 연결하고, 새 활동이면 서비스 코드가 DB에 생성한다. 생성 실패 상태를 성공으로 반환하지 않는다.
4. 분석 초안과 원본 자료를 계약한 저장소에 보관한다. 프론트와 백엔드가 분석·자료를 동일한 ID로 연결할 수 있어야 한다.
5. 생성/매칭된 활동 ID, 분석 ID, 카드 데이터와 필요한 작업 상태를 반환한다. 비동기라면 접수·진행·완료·실패 계약을 따른다.
6. 프론트는 응답 검증과 화면용 변환 후 카드를 표시한다. 아직 기록 저장 완료로 표시하지 않는다.

### 수정·확정 저장·조회

1. 저장 전 수정은 기존 활동·자료 유형만 카드와 세션에 반영한다.
2. 기록 버튼에서 프론트가 백엔드에 활동 ID·분석 참조·확정 분류를 전송한다. 정확한 요청 필드는 개발 계약에서 확정한다.
3. 백엔드는 활동·분석·자료 참조를 확인하고 원본 파일 연결을 유지하며 새 기록을 저장한다. 기존 기록·활동 전체 요약을 임의로 덮어쓰지 않는다.
4. 변화가 있으면 백엔드가 계약된 Timeline 처리를 수행한다. 변화 없음은 기록만 저장하며 프론트가 이벤트를 생성하지 않는다.
5. 저장 성공 응답 이후에만 완료 상태를 표시하고 관련 목록을 갱신한다.
6. 나의 발자국·활동 상세·자료 패널·Timeline에서 DB 결과를 조회한다.
7. 저장 후 수정은 해당 기록의 활동·자료 유형만 PATCH하고 관련 조회 결과를 갱신한다.

다중 파일은 기존 전체 저장·자료 확인 버튼을 유지한다. 활동 연결이 없는 경우 현재는 오류 안내만 가능하므로, 정상 AI 응답에서 유효한 활동 ID를 보장하고 미확정 결과의 복구 방식은 별도 계약으로 정한다.

## 4. 구현 순서와 완료 기준

### 1단계 — AI API 개발 서버 구성과 텍스트 계약 적용

- 기존 [AI API 명세](API_계약/AI_API_계약.md)와 [백엔드 API 명세](API_계약/백엔드_API_계약.md)를 출발점으로 사용한다. 신규 활동 생성 주체·생성 완료 ID·기록 저장·분류 수정 범위에 남은 이전 계약은 구현과 함께 조정한다.
- AI 개발 서버의 독립 실행·상태 확인·텍스트 분석 접수·결과 조회부터 구성한다.
- DB 접근 모듈, 분석 대상·파일 조회 방법, 활동 생성 시점과 응답 상태를 구체화한다. 백엔드 저장이 AI 서버의 활동·분석 ID를 참조할 수 있는 DB 연결을 준비한다.
- 기존 목 분석을 활용하더라도 기존 활동 조회·신규 활동 생성·분석 보관은 실제 서비스 코드와 DB로 처리한다. 모델 자체가 DB ID나 SQL을 생성해 실행하는 구조로 만들지 않는다.
- 기존/신규 활동의 정상·실패 응답과 분석 참조 기반 기록 저장 요청을 정리한다. 현재 `match: new`에 ID를 허용하지 않는 검증도 생성 완료 상태를 표현하도록 조정한다.
- 활동 생성 후 기록 미저장 상태, 중복 요청, 근거 없는 변화 생성 방지 기준을 정한다. 재시도 시 중복 활동·분석을 방지하고 생성 실패는 노출한다.
- 모델 호출은 교체 가능한 경계로 두고 목 분석과 실제 모델 연결 상태를 구분한다. 실제 모델·공급자 선택은 아직 확정하지 않는다.

완료 기준: 독립 HTTP 서버에서 텍스트의 기존 활동 연결·신규 활동 DB 생성·분석 결과 반환이 동작한다. 활동 ID·분석 ID와 실패 상태가 명세에 설명되어 있다. 이 단계의 성공을 전체 프론트·백엔드 연동 완료로 기록하지 않는다.

### 2단계 — 기존 백엔드 조정

- 기록 저장·분류 수정의 검증기와 라우트를 카드 범위에 맞춘다.
- AI 서비스가 생성한 활동·분석을 백엔드 저장에서 조회할 수 있도록 연결한다.
- 기록·이벤트 트랜잭션, 중복 저장 방지, 오류 처리와 기존 DB를 보존한다.
- 바뀐 요청·응답에 맞춰 테스트와 백엔드 명세를 갱신한다.

완료 기준: 준비된 활동·분석으로 확정 저장·수정·조회가 실제 DB에서 성공하며 잘못된 참조는 실패한다.

### 3단계 — 프론트 연결과 입력 종류 확장

- 분석 요청은 AI 서버, 저장·조회는 백엔드로 연결한다.
- 활동 응답 타입·검증과 저장 대상 ID 선택을 새 계약에 맞춘다. 활동명으로 ID를 추측하지 않는다.
- 진행 상태·실패·새로고침 후 작업 재개·세션 복원을 연결한다.
- 텍스트의 기존/신규 활동 흐름부터 완성한 뒤 단일 파일 → 다중 파일 → 링크 순서로 확장한다.
- 파일과 링크는 실제로 보관·추출·수집한 범위를 표시한다. 파일명·URL만으로 본문을 분석했다고 설명하지 않는다.

완료 기준: 브라우저에서 입력→분석→수정→확정 저장→백엔드 조회가 이어지고 파일 원본·활동·분류가 일치한다.

### 4단계 — 실제 동작 검증

- 두 서버를 독립 프로세스로 실행하고 프론트에서 신규/기존 활동 → 분석 → 수정 → 저장 → 조회를 직접 확인한다.
- 아래 필수 검증 시나리오를 자동 검사와 브라우저 조작으로 확인한다. 파일은 저장 후 다운로드한 원본까지 대조한다.
- 실패·재시도·중복·새로고침 후 복원을 확인하고, 문제를 수정한 뒤 관련 시나리오를 다시 검사한다.
- 수행한 명령·테스트 DB·결과·브라우저 확인 여부·미검증 범위를 남긴다. 목 분석으로 검증한 연결과 실제 모델 분석 검증을 구분한다.

완료 기준: 화면 상태와 DB 저장·조회 결과가 일치하고 확인한 범위에서 정상/실패 시나리오가 동작한다. 미해결 항목은 정상 완료로 기록하지 않는다.

### 5단계 — 검증된 구현의 문서화와 담당 agent 전달

- 구현 중 임시로 정리한 계약을 검증 결과와 대조하고 실제 동작 기준으로 확정한다. 담당자 간 최종 합의가 남아 있는 항목은 별도로 표시한다.
- 검증한 코드 기준으로 API 명세·Swagger·ERD·기능 흐름·진행 현황을 갱신한다.
- Growth Journey의 DB 기반 분석 생성·저장·조회는 핵심 기록 흐름 안정화 후 별도 단계로 구현한다.
- 외부 서버 전환·터널·Vercel 배포는 로컬 두 서버 검증과 구분해서 기록한다.

완료 기준: 다른 담당 agent가 문서만으로 서버 실행·정상/실패 시나리오 재현·구현 범위 판단을 할 수 있다.

## 5. 필수 검증 시나리오

검사는 임시 또는 전용 테스트 DB를 사용한다. 기존 사용자 DB를 초기화하지 않는다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 기존 활동 | 새 활동을 만들지 않고 해당 ID로 새 기록 추가 |
| 신규 활동 | 활동 생성 완료 ID 반환 → 기록 저장 → 활동 상세 조회 |
| 기록 미저장 | 활동만 생성된 상태의 노출·보존이 정한 정책과 일치 |
| 저장 전 수정 | 선택한 기존 활동·자료 유형으로 저장되고 원본 분석/파일 참조 유지 |
| 저장 후 수정 | 해당 기록만 이동·분류 변경, 활동 전체 정보와 다른 기록 보존, 조회 결과 일치 |
| 변화 없음 | 기록·자료는 저장, Timeline 이벤트 없음 |
| 변화 있음 | 근거와 변화 내용 유지, 이벤트 생성·조회 일치 |
| 파일 | 실제 파일명·개수·크기 유지, 저장 후 다운로드 바이트 일치 |
| 링크 | 실제 URL 유지, 수집 성공·실패와 목 처리를 구분 |
| 재시도·동시 요청 | 활동·분석·기록 중복 방지 규칙대로 처리 |
| 잘못된 참조 | 미완료/없는 분석, 삭제된 활동, 없는 파일은 성공 처리하지 않음 |
| 서버 오류 | AI 장애·활동 생성 실패·백엔드 저장 실패를 구분하고 가짜 성공 표시 없음 |
| 작업 복원 | 새로고침·재진입 시 올바른 AI 서버에서 작업 상태 확인, 결과 중복 추가 없음 |
| 회귀 확인 | 기존 아카이브·최근 목록·자료 패널·Timeline 조회와 세션 보관 유지 |

기존 검사 출발점: 루트 build/lint, `scripts/check-chat-api.mjs`, `scripts/check-chat-session.mjs`, `api-server/test/`, `tests/`의 아카이브·Journey 검사. 서버 분리 후 두 서버를 실제로 통과하도록 통합 검사를 조정한다. 자동 검사 통과와 브라우저 조작 확인은 별도 기록한다.

## 6. 담당 agent 전달용 문서와 ERD

아래 산출물은 작성할 목록이며 이 계획 작성 시 모두 생성된 것은 아니다. 기존 문서를 최신화하고 별도 문서가 필요할 때 추가한다.

| 산출물 | 내용·작성 위치 |
| --- | --- |
| 진행 현황·인수인계 | 구현/목/미구현/검증 여부, 다음 작업, 관련 코드. 이 계획과 `다음_작업_인수인계.md`에서 연결 |
| 백엔드 API 명세 | `API_계약/백엔드_API_계약.md`: 실제 경로·필드·상태 코드·오류·저장/수정 책임·이전 계약 처리 |
| AI API 명세 | `API_계약/AI_API_계약.md`: 입력·문맥·활동 생성/매칭·분석 ID·진행·실패·DB 접근 책임 |
| Swagger | `api-server/docs/openapi.js`와 생성 스크립트를 새 구현에 맞게 갱신. 정적 생성물만 직접 수정하지 않음 |
| 기능 흐름 | integration 아래 별도 문서로 사용자 동작·서버 호출·DB 변경·반환 ID·후속 조회·실패 복구 연결 |
| ERD·데이터 사전 | integration 아래 별도 문서로 현재 구현 ERD와 제안 설계 구분, 컬럼·PK/FK·유일성·NULL·삭제 규칙·JSON 구조 설명 |
| 실행·검증 안내 | 각 서버 README와 integration 안내에 실행 순서·포트·환경변수·DB 경로·테스트 데이터·검사 명령·브라우저 재현 절차 기록 |

현재 DB의 ERD 출발점은 다음과 같다. 아래 관계는 현재 코드 기준이며 미래 정규화 설계가 아니다.

| 현재 테이블 | 현재 관계·특징 |
| --- | --- |
| activities | 활동 정보. records.activity_id가 참조 |
| analyses | 입력·대화 ID·분석 reply JSON. files와 records, analysis_jobs가 참조 |
| files | analysis_id로 분석에 연결. 원본은 BLOB |
| records | activity_id로 활동 연결, analysis_id는 nullable·UNIQUE. 독립 미리보기 기록은 분석 참조가 없을 수 있음 |
| timeline_events | record_id로 기록 연결, 기록 삭제 시 CASCADE. 변화는 change_json에 저장 |
| analysis_jobs | analysis_id는 UNIQUE. 현재 started_at/error 기반 목 진행 구조 |

ERD에는 서버별 테이블 읽기/쓰기 범위를 함께 표기한다. 현재 files와 records는 분석 ID를 통해 연결되며 직접 record_id FK가 없는 점, timeline_events의 활동은 records를 통해 조회하는 점을 설명한다. 분석 JSON 안의 활동 값은 관계형 FK와 구분한다. 성장 분석 저장 테이블·실제 사용자 테이블·ID 기반 버전/근거 관계는 현재 구현된 것으로 그리지 않는다.

각 문서는 필드나 동작마다 ‘현재 코드’, ‘개발 계약’, ‘제안’, ‘미확정’을 구분하고 코드 경로·검증 결과를 연결한다. 목 분석으로 통신·DB 흐름을 검증한 결과를 실제 모델 정확도나 운영 연동 완료로 기록하지 않는다.

## 7. 바로 다음에 할 작업

**AI API 개발 서버를 먼저 구성한다.** 텍스트 입력의 기존/신규 활동 두 시나리오부터 기존 명세를 최신 결정에 맞춰 적용한다. AI 서비스의 생성 완료 활동 ID, 분석/파일 보관과 백엔드 참조, 기록 미저장 상태와 재시도 규칙을 구현하면서 구체화한다. AI 서버 구성 → 백엔드 조정 → 프론트 연결·입력 확장 → 실제 동작 검증 → 구현 현황·기능 흐름·백엔드/AI API 명세·Swagger·ERD 문서화 순서로 진행한다.

이 문서 작성에서는 실행 코드·DB·OpenAPI를 변경하거나 검사를 새로 실행하지 않았다. 작성한 마크다운의 상대 링크와 공백만 확인한다.
