## 2026-11-13 — AI 저장소 대조와 백엔드 보완 방향 논의

### 조사 근거

- 프론트·Spring 기준: `05bc0d952d854f3bd93173bb2a3b92d4513d40e2`.
- AI 기준: [GrowthArchive_ai의 조사 커밋](https://github.com/hongdabomi/GrowthArchive_ai/tree/3f2e9907396d728ea37aeafa189bac92c0159a24).
- AI의 버전 응답과 Spring literal 검증이 다름을 확인했다.
- 파일·링크 기록의 빈 message와 AI Text 검증이 맞지 않음을 확인했다.
- 완료 게시 오류 후 AI의 failed 요청에 reply가 남고 Spring이 이를 거절하는 흐름을 확인했다.
- AI 단독 재시작 시 기존 진행 작업의 재개/실패 전환이 없고 Spring은 기동 시에만 복구하는 점을 확인했다.
- 이는 소스·스키마·테스트 정적 대조 결과다. 실제 AI 모델·배포 서버를 호출하거나 해당 AI 테스트를 실행하지 않았다.

### 사용자와 논의한 방향

| 항목 | 현재 정리 |
| --- | --- |
| 구현 파트 | AI 코드 변경 대신 백엔드 중심 대응 희망 |
| 활동 버전 | AI 반환값 기준으로 맞추는 방향 설명. 기존 버전 호환 세부 정책은 미확정 |
| 빈 message | DB는 유지하고 홈 문맥 응답에서 빈 문자열을 null로 보내는 방향 설명 |
| failed reply | status=failed는 유지하고 reply만 null로 정리하는 방향 채택 |
| 작업 만료 | 처음에는 제안이었으며 이후 사용자가 running 5분·queued 10분·검사 30초를 채택. 아래 확정 기록 참고 |

사용자는 failed reply 구현을 요청했다가 코드 조회 직후 “지금 수정하지 말고”라고 중단했다. 해당 시점에 소스는 읽기만 했고 변경하지 않았다. 이후 요청은 작업 설명과 문서 폴더 작성이며 기능 구현 재개 요청으로 해석하지 않는다.

### 보존해야 할 조건

- 완료된 결과를 뒤늦은 failed 요청으로 지우지 않는다.
- revision·입력 검증·원본 검증·종료 상태 보호를 유지한다.
- failed reply 정규화만으로 네트워크 장애나 stale revision까지 해결됐다고 기록하지 않는다.
- SQL NULL과 JSON null을 구분한다. analyses.reply의 NOT NULL 제약을 바꾸지 않고 기존 직렬화 방식을 사용한다.
- AI는 단계 전환 때만 갱신하며 주기 heartbeat를 보내지 않는다. 예시 시각을 실제 정기 갱신 구현으로 해석하지 않는다.
- 프론트의 2분 폴링 중단과 확정한 5분 만료는 다르다. 재조회·복원 시 상태 반영을 검사해야 한다.
- 사용자에게 전달되지 않은 분석 결과의 자동 복원을 보장하지 않는다. 실패 안내와 새 요청을 통한 복구가 포함될 수 있다.

## 2026-11-13 — 작업 만료 시간 확정

- 사용자가 권장한 만료 시간 기준을 채택했다.
- running: 백엔드가 마지막 진행 갱신을 받은 뒤 5분.
- queued: 백엔드 접수 후 10분.
- 검사 간격: 30초.
- README의 제안 상태를 확정·미구현으로 변경하고 시간 결정 체크리스트를 완료 처리했다.
- AI는 단계 전환 때만 갱신하며 주기 heartbeat는 없다. 정상 처리·대기 시간, 서버 시계 차이, 완료와 만료의 동시 실행을 고려하는 조건은 유지한다.
- 이번 변경은 문서의 기준 확정이다. 기능 코드·DB·배포 설정은 변경하지 않았고 테스트·빌드는 실행하지 않았다. 기존 구현 중단 지시를 해제하거나 기능이 이미 적용된 것으로 기록하지 않는다.

## 2026-11-13 — 만료 안내를 백엔드 문구로 처리하기로 결정

- 사용자는 별도 프론트 오류 UI 변경 대신 백엔드가 만료 원인별 문구를 제공하는 방식을 선택했다.
- queued 만료 안내: “분석 요청이 많아 대기 시간이 초과됐어요. 잠시 후 다시 요청해 주세요.”
- running 만료 안내: “분석 진행을 확인할 수 없어 작업을 종료했어요. 다시 요청해 주세요.”
- 정본의 error.code/error.error 구조를 유지하고 AI가 공개 실패 응답으로 전달하면 프론트의 기존 오류 표시 로직을 사용한다.
- 프론트의 기존 2분 폴링 시간 초과는 별도다. 실패 상태를 다시 수신해야 위 문구를 볼 수 있으므로 재조회·복원 동작 확인 조건을 유지한다.
- 문서만 갱신했으며 기능 코드·DB·배포 설정은 변경하지 않았다. 테스트·빌드는 실행하지 않았다.

## 2026-11-13 — 활동 분석 버전 정합화 구현 및 검증

### 적용 정책과 변경

- 사용자가 첫 작업인 활동 분석 버전 구현을 요청했다. 이번 구현은 이 항목만 진행하며 failed reply의 기존 중단 지시와 나머지 미구현 상태는 유지한다.
- AI main의 activity_metadata.py를 다시 읽어 반환값 activity-metadata-analysis를 확인했다. 파일 blob SHA는 `53062290d4d03bf42ac718baca8f4d49028138d4`로 조사 당시와 같다. AI 코드는 변경하지 않았다.
- ActivityMetadata.OUTPUT의 promptVersion literal을 activity-metadata-analysis로 변경했다. activity-metadata-v1·임의 버전을 추가 수용하지 않고 새 AI 응답 기준으로 단일화했다.
- ApiTest 및 ActivityMetadataRequestTest의 AI 응답 대역도 실제 반환값과 맞췄다. 새 검사에서 구버전·journey-v6·빈 문자열·null·필드 누락을 거절하고 마지막 유효 메타정보·기록을 보존함을 확인한다.
- AI OpenAPI의 ActivityAnalysisResult const와 활동 응답 예시, API 정의서·안내·공통 전달 계약을 갱신했다. 프롬프트 정의서의 과거 원문은 보존하고 제목 버전이 이력임을 명시했다.
- 응답 구조·원문 근거·해시·개수·기간 검증, DB 구조·기존 데이터·프론트·요청 본문은 변경하지 않았다. SQL 마이그레이션은 필요 없다.
