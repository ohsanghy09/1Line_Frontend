### 보존해야 할 조건

- 완료된 결과를 뒤늦은 failed 요청으로 지우지 않는다.
- revision·입력 검증·원본 검증·종료 상태 보호를 유지한다.
- failed reply 정규화만으로 네트워크 장애나 stale revision까지 해결됐다고 기록하지 않는다.
- SQL NULL과 JSON null을 구분한다. analyses.reply의 NOT NULL 제약을 바꾸지 않고 기존 직렬화 방식을 사용한다.
- AI는 단계 전환 때만 갱신하며 주기 heartbeat를 보내지 않는다. 예시 시각을 실제 정기 갱신 구현으로 해석하지 않는다.

- 사용자에게 전달되지 않은 분석 결과의 자동 복원을 보장하지 않는다. 실패 안내와 새 요청을 통한 복구가 포함될 수 있다.

### 구현과 정책

- InternalJobExpiry를 Spring Bean으로 등록했다. 기본 queued 600000ms / running 300000ms / 검사 간격 30000ms이며 oneline.internal-job-queued-timeout-ms, oneline.internal-job-running-timeout-ms, oneline.internal-job-scan-interval-ms로 설정한다. 0 이하 값은 시작 오류다.
- internal_chat_publications에 accepted_at_ms와 progress_received_at_ms INTEGER 컬럼을 자동 이관으로 추가했다. AI의 createdAt/updatedAt 대신 백엔드 수신 epoch 밀리초를 사용한다. 최초 게시 때 두 값을 기록하고 유효한 새 갱신 게시 때만 진행 수신 시각을 갱신한다. queued는 항상 최초 접수 시각을 기준으로 한다.
- GET·동일 게시 재전송·expectedRevision=0 중복 접수는 시간을 연장하지 않는다. 기존 DB의 미완료 작업은 기존 server_restarted 복구가 처리하며 완료·원본을 보존한다.
- 만료 시 failed/error와 JSON null reply를 저장하고 revision을 증가시키며 게시 해시를 초기화한다. queue_timeout / analysis_timeout 및 원인별 한국어 재요청 안내를 보관한다. 원본·입력은 유지한다.
- 타이머는 요청과 같은 EventLoop 잠금·DB 트랜잭션을 사용한다. 완료가 먼저 확정되면 보존하고 만료가 먼저 확정되면 이후 완료·진행 게시를 거절한다. DB 실패는 전체 롤백 후 다음 주기에 재시도한다. 종료 시 타이머를 먼저 중지한 뒤 DB를 닫는다.
- 검사 주기 사이의 경과 작업은 완료가 먼저 게시될 수 있다. AI의 미래 시각도 만료를 미루지 않으며 만료 응답 updatedAt은 기존 값보다 뒤로 가지 않게 유지한다.

### 배포 통합 확인 사항

- 네 보완 항목의 백엔드 구현·로컬 검증은 완료했다. 실제 AI 프로세스 종료·재조회·공개 실패 응답·EC2·브라우저 검증은 수행하지 않았다.

- AI는 주기적 heartbeat가 없으므로 정상 모델 분석도 진행 게시 없이 5분을 넘으면 만료된다. 운영 모델 소요 시간을 확인해 설정을 조정한다.
