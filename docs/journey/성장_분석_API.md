# Growth Journey 성장 분석 응답·연결 순서

## 분류 불일치 보완 — journey-v4

2026-11-06 실제 갱신에서 AI 서버의 `502 invalid_journey`(분류 중복/이벤트 불일치)를 재현했다. 최신 기록 3개는 정상 조회됐지만 검증 실패로 기록 1개 기준의 이전 결과가 남아 있었다. 삭제 전 활동 ID의 404는 별도 상세 조회 문제이며 이 실패의 직접 원인은 아니었다.

- 모델 응답을 복사해 이벤트에서 쓰지 않는 유형/분야를 제거한다. 같은 ID·같은 라벨 중복은 하나로 정리한다.
- Unicode NFKC·공백 통합·대소문자 정규화 후 라벨이 정확히 같은 선택지는 첫 ID로 통합하고 이벤트 참조도 함께 치환한다. 의미가 비슷하다는 이유로 임의 추론해 합치지 않는다.
- 같은 ID에 다른 라벨이 연결되거나 이벤트가 미등록 ID를 참조하면 구체적인 오류로 거절한다. 근거·활동 ID·전후 비교·fingerprint 검증은 유지한다.
- 이벤트가 없으면 선택지도 비운다. 이벤트나 근거를 추가/삭제해 분류 개수를 맞추지 않는다.
- 프롬프트는 이벤트 확정 → 사용 분류 추출 → 참조 일치 확인 순서를 명시한다. 자동 모델 재호출 없이 한 번의 응답을 정리한다.
- 프론트 갱신 실패 안내는 오류 원인과 ‘표시된 결과는 마지막으로 저장된 분석’임을 명시한다.

검증: Python 전체 60개, 백엔드 Journey 관련 11개, TypeScript/Vite 빌드 통과. lint 기존 경고 3개. 실제 백엔드 갱신 1회에서 HTTP 200, 기록 3개, 이벤트 1개, `stale=false`, `promptVersion=journey-v4`로 저장되는 것을 확인했다(2026-11-06 18:34 KST). 브라우저 UI 검증은 미수행이며 Swagger는 갱신하지 않았다. 아래 v3의 중복/미사용 분류 일괄 거절 설명은 정리 전 응답에 대한 이전 정책이다. 정리 이후 검증은 여전히 엄격하게 적용한다.

## 성장 분야도 분석 결과로 생성 — journey-v3

2026-11-06 사용자 요청으로 성장 축(분야)의 고정 planning/technology/data/collaboration/other 목록을 제거했다. 실제 모델 출력은 `axisOptions: [{ value, label }]`을 포함하고 각 이벤트의 `axis`는 생성된 분야 ID를 참조한다. 분야는 실제 경험의 영역이고 성장 유형(type)은 성장의 성격이다. 예를 들어 서비스 디자인·교육·문학 등을 기록에 맞게 생성하며 예시는 고정 선택지가 아니다. 분야 이모지는 이번 범위에 추가하지 않았다.

- 실제 이벤트에 쓰인 분야만 최대 8개, 분야명은 40자 이내로 반환한다. ‘전체 분야’는 모델이 만들지 않고 서버가 `{ value: 'all', label: '전체 분야' }`로 추가한다.
- 이벤트가 없으면 모델의 axisOptions=[]이며 화면에는 전체 분야만 표시한다.
- Python과 백엔드는 중복 ID·정규화 후 중복 라벨·예약 값/전체 라벨·누락 또는 미사용 분야·이벤트의 미등록 분야 참조를 거절한다. 기존 근거·해시 검증도 유지하며 실패 시 이전 결과를 보존한다.
- 백엔드 공급자 경계에는 새 동적 분야 검증을 적용한다. 저장 결과 조회는 과거 고정 분야 목록과 사용하지 않는 분야가 포함된 이전 결과도 그대로 허용한다. 기존 DB를 수정하거나 조회만으로 모델을 호출하지 않는다.
- 프론트 필터와 이벤트의 분야 표시는 이미 응답 axisOptions를 사용하므로 새 분야 ID·라벨을 그대로 표시하며 유형/분야 AND 필터도 유지한다. 재분석 성공 시 기존 방식으로 필터를 전체로 초기화한다.
- 프롬프트 버전은 journey-v3이다. 백엔드·AI 서버 재시작 후 ‘성장 분석하기 / 분석 갱신’을 실행하면 새 분야를 생성한다. 이전 캐시를 표시하는 동안에는 이전 분야가 보이는 것이 정상이다.

검증: Python 전체 54개·백엔드 40개(Swagger 전용 검사 제외)·Journey 프론트 서비스/필터 10개와 TypeScript/Vite 직접 빌드 통과. lint는 기존 경고 3개다. 실제 유료 모델 분석·사용자 브라우저 검증은 미수행이다. 사용자 요청에 따라 Swagger 최신화·정적 문서 생성은 진행하지 않았다. 아래 journey-v2의 고정 분야 안내는 이전 동작이다.

## 실제 실행 계약 — 2026-11-06

현재 화면 진입은 GET 조회만 자동 수행하며 모델은 POST 분석/갱신 버튼에서만 호출한다. 기록 변경 후 방문 시 필요한 경우 자동 분석하는 방식은 논의한 제안이고 아직 구현하지 않았다. 실제 공유 DB는 사용자 요청으로 초기화했고 예시 활동 자동 생성도 제거했다. 빈 DB에서 시작하는 화면 검증 순서는 [최신 인수인계](../integration/현재_작업_인수인계.md)를 따른다.

### 성장 유형을 분석 결과로 생성 — journey-v2

성장 유형은 더 이상 고정 enum이 아니다. 모델은 `typeOptions: [{value, label, icon}]`를 생성하고 각 이벤트의 `type`은 그 `value`를 참조한다. 최대 8개이며 같은 의미의 유형을 묶고 실제 이벤트에 쓰인 유형만 반환한다. 이벤트가 없으면 모델의 분류도 빈 배열이다. 서버는 예약 필터 `{value: all, label: 전체}`만 덧붙인다. 분야(`axis`)는 기존 기준을 유지한다.

`icon`은 원본과 같은 이모지 한 개다. 분류명 `label`과 분리하여 필터 버튼과 이벤트 배지 앞에 같은 아이콘을 표시한다. 경험 배지도 `{id, label, icon, evidence}`로 표시한다. 신규 분석에서는 아이콘을 필수 검증하고, 과거 저장 결과는 아이콘 없이도 조회한다. 재분석 전 기존 결과의 분류명이나 문구를 임의로 바꾸지 않는다.

Structured Outputs에서 분류명을 생성하고 Python·백엔드에서 중복 ID/분류명, 예약값 all, 미등록 이벤트 유형, 미사용 분류·누락 아이콘을 검증한다. 필터/배지 표시까지 실제 응답을 사용한다. 근거 ID·원문 인용 검증과 DB 저장 경계는 유지한다.

| 서버 | 경로 | 동작 |
| --- | --- | --- |
| 백엔드 | GET `/api/journey` | 최신 DB 결과 조회. 모델 호출 없음 |
| 백엔드 | POST `/api/journey/analyze` | AI 분석 요청 → 근거·스냅샷 검증 → 결과 저장 |
| AI 서버 | GET `/api/journey/context` | 확정 기록 문맥·기록 수·해시 조회. 모델 호출·DB 변경 없음 |
| AI 서버 | POST `/api/analyze/journey` | 실제 모델 분석·근거 검증 결과 반환. DB 쓰기 없음 |

백엔드 `AI_API_BASE_URL` 기본은 `http://127.0.0.1:8000`이다. 프론트는 기존 `/api` 프록시, AI는 기존 키·모델 설정을 사용한다. 현재는 같은 PC의 동일 SQLite에 직접 접근하는 개발 구조다.

AI POST는 별도 요청 본문 없이 DB를 읽는다. 응답은 `sourceFingerprint`, `recordCount`, `model`, `promptVersion`, `result`다. 실제 모델 출력은 Pydantic으로 검증하고 기록 ID·원문 인용·활동 연결·비교 근거를 추가 검사한다. 서버가 날짜와 이벤트 ID를 정한다.

백엔드 응답은 `source: api`, `summary`, `badges`, `typeOptions`, `axisOptions`, `events`, `analysis`다. 요약·배지·이벤트의 `evidence`는 `{recordId, quote}` 배열이다. `comparison`은 있을 때만 포함한다. `occurredAt`은 근거 기록 저장 월이다. 파일 ID는 입력 문맥에 포함하지만 출력 근거는 기록 단위이며 자료 클릭 이동은 미구현이다.

`analysis`에는 `id`, `generatedAt`, `stale`, `recordCount`, `currentRecordCount`, `model`, `promptVersion`을 담는다. 분석 전 ID/시각/모델/버전은 null이고 이벤트·배지는 빈 배열이다. 분석했지만 성장 근거가 부족한 경우와 미분석 상태는 ID로 구분한다.

결과는 `journey_analyses`에 저장한다. 분석 시점의 확정 기록·활동 정보·파일 메타정보를 현재 DB와 해시로 비교하고 변경되면 409로 저장을 거절한다. 조회도 같은 해시로 stale을 계산한다. 실패는 기존 결과를 유지하며 자동으로 모델을 재호출하지 않는다.

기록 없음·문맥 한도는 422, 동시 실행·분석 중 변경은 409, 호출 제한은 429, 공급자/근거 오류는 502, 설정/DB 오류는 503, 시간 초과는 504다. 모델 제한 시간은 기존 설정(기본 45초), 백엔드 대기는 135초, 프론트 분석 대기는 145초다. GET은 기존 30초다.

확정 기록 100개·문맥 JSON 250000자·이벤트 20개·배지 10개를 지원한다. 한도 초과는 명시적으로 거절한다. 현재 중복 방지는 백엔드 인스턴스 하나 기준이다. 분산 잠금·내구성 있는 작업 큐·재시작 복구는 후속 범위다.

검증은 [현재 상태](현재_구현_상태.md)의 최신 절을 따른다. 실제 검사 명령은 `node scripts/check-live-ai.mjs --journey`이며 임시 DB와 유료 모델 호출을 사용한다.

## 이전 API 초안·연결 이력

아래 source=mock·목 공급자·미구현 설명은 변경 이전 이력이다.

작성: 2026-11-04. 기존 기능처럼 화면용 응답 계약과 후속 구현 순서를 정리했다. **개발 단계의 계약이며 정식 AI 공급자 명세가 아니다.** GET `/api/journey`와 프론트 HTTP 연결을 구현했다. 서버 응답은 목 분석이며 DB 분석·실제 AI·성장 결과 저장은 아직 구현하지 않았다.

## 현재와 다음 연결 경계

현재는 `GrowthJourney.tsx` → `getGrowthJourney(signal)` → 기존 request 헬퍼 → Vite `/api` 프록시 → GET `/api/journey` → 서버 목 응답이다. 화면·필터·상세 펼침을 유지했다.

다음 연결 목표는 화면 → 프론트 서비스 → 개발 API → 분석 공급자다. 개발 API는 기존처럼 Vite `/api` 프록시를 사용하고, 실제 AI 연결 전에는 서버 목 공급자를 사용한다. 실제 AI 공급자의 응답 형식이 달라도 프론트 서비스/서버 공급자 경계에서 변환해 화면 구조를 유지한다.

조회 경로는 `GET /api/journey`다. 전체 데이터를 한 번 조회하고 현재의 프론트 AND 필터를 유지한다. 유형·분야 필터 변경으로 API/AI를 재호출하거나 전체 요약을 다시 생성하지 않는다. 페이지네이션·분석 실행/갱신 API는 이번 계약에 포함하지 않는다. 서버는 공급자 응답 검증 실패 시 500을 반환한다. 프론트는 모든 실패를 오류로 표시하며 ‘다시 불러오기’로 재조회한다.

## 화면에 전달할 응답

현재 [GrowthJourneyData](../../src/types/journey.ts)를 개발 연결 기준으로 사용한다. 아래는 응답 형태를 설명하는 예시이며 실제 사용자의 분석 결과가 아니다.

```json
{
  "source": "mock",
  "summary": {
    "title": "서비스 기획 경험 → PM 역할 확장",
    "description": "여러 활동에서 나타난 역할의 변화를 정리한 예시입니다."
  },
  "badges": [
    { "id": "first-pm", "label": "🌱 첫 PM" }
  ],
  "typeOptions": [
    { "value": "all", "label": "전체" },
    { "value": "ability", "label": "🧩 능력 확장" }
  ],
  "axisOptions": [
    { "value": "all", "label": "전체 분야" },
    { "value": "planning", "label": "기획 / PM" }
  ],
  "events": [
    {
      "id": "growth-pm-example",
      "occurredAt": "2026-10",
      "activity": { "id": null, "name": "1호선톤" },
      "type": "ability",
      "axis": "planning",
      "title": "PM 역할 수행 및 팀 프로세스 수립",
      "description": "기획 담당에서 일정과 협업을 관리하는 역할로 확장한 예시입니다.",
      "comparison": {
        "before": "기획 담당",
        "after": "PM + 기획",
        "evidence": ["회의록", "역할분담표"]
      }
    }
  ]
}
```

| 필드 | 기준 |
| --- | --- |
| source | `mock`은 예시/목 분석이다. 서버 HTTP 호출로 바꿨다는 이유만으로 `api`로 바꾸지 않는다. 실제 분석값일 때만 `api`를 사용한다. 사용자 요청으로 화면의 예시 데이터 배지는 제거했으며 필드는 유지한다. |
| summary | 전체 활동의 성장 흐름 제목·설명. 활동 하나의 기록 요약을 그대로 전체 성장 요약으로 쓰지 않는다. 분석 결과가 없으면 아직 분석된 성장 흐름이 없다는 안내를 반환한다. |
| badges | 확인된 첫 경험 배지 배열. 결과가 없으면 `[]`. 목 응답의 예시 배지와 실제 첫 경험 판정은 구분한다. |
| typeOptions / axisOptions | `value`는 조건 비교용 ID, `label`은 표시 문구. `all` 선택지를 포함하며 이벤트의 type/axis는 해당 선택지에 존재해야 한다. |
| events | 전체 성장 이벤트 배열. 없으면 `[]`. 응답에는 필터를 적용하지 않는다. |
| events[].id | 필터 전환/재조회에도 같은 이벤트는 같은 ID를 사용한다. 배열 인덱스를 ID로 사용하지 않는다. 실제 분석 이벤트의 ID 부여·보존은 서버 연결 단계에서 구현한다. |
| occurredAt | 현재 화면 계약은 `YYYY-MM`. 확인되지 않은 날짜를 덧붙이지 않는다. 일 단위 시각이 필요하면 타입·표시·검증 계약을 함께 확장한다. 오래된 순·같은 월은 응답 순서로 표시한다. |
| activity | 확인된 실제 활동 ID와 이름. 예시·해결되지 않은 ID는 null이며, 이름만으로 실제 활동에 연결하지 않는다. |
| type / axis | 선택지 value. 분석 결과가 불명확하면 임의로 분류해 이벤트를 만들지 않는다. |
| title / description | 해당 활동에서 확인된 성장의 제목·설명. 파일명만으로 성장했다고 판단하지 않는다. |
| comparison | 전후 상태가 모두 있을 때만 포함한다. 없으면 필드를 생략한다. null·빈 Before/After를 실제 비교처럼 표시하지 않는다. |
| comparison.evidence | 현재는 근거 이름 문자열 배열이다. 근거가 없으면 `[]`. 파일 링크가 아니며 임의 ID를 생성하지 않는다. |

근거 파일 클릭 이동을 구현하는 단계에서는 자료 ID·활동 ID를 갖는 근거 객체로 계약을 별도 확장하고 타입·서비스·카드를 함께 수정한다. 현재 문자열 계약으로 실제 파일 이동까지 완료했다고 기록하지 않는다. 비교 없이 독립적인 근거만 표시해야 하는 경우도 별도 응답/화면 확장 범위다.

## 성장 유형·분야 기준

우선 서버 목 연결은 현재 화면과 같은 분류를 사용한다.

- 유형: ability(능력 확장), achievement(성과 향상), experience(경험 축적), efficiency(효율성), transfer(경험 전이).
- 분야: planning(기획 / PM), technology(AI·기술), data(데이터), collaboration(발표·협업).

위 값은 **원본 화면 호환용 개발 기준**이다. 기능명세의 팀 협업 개선·반성/재시도 등과 같은 의미라고 자동 매핑하지 않는다. 실제 성장 분석을 구현하기 전에 원본/기능명세 중 최종 분류 기준을 사용자와 정리하고 공급자·검증·선택지를 함께 맞춘다. 이번 문서 작성으로 최종 분류가 승인됐다고 간주하지 않는다.

## 실제 저장 자료와 분석값 구분

DB 연결 단계의 분석 대상은 확정 저장된 기록과 그 활동/자료다. 미저장 분석 초안은 포함하지 않는다. 실제 기록 ID·활동 ID·입력 내용·자료명과 AI가 판단할 성장 유형·성장 분야·전후 상태·요약·첫 경험을 분리한다.

기존 timeline_events를 모두 합쳐 사용자 성장 분석이라고 표현하지 않는다. 변화 없음 자료의 저장, 일반 변화 이벤트의 저장만으로 Journey 이벤트나 첫 경험 배지를 자동 생성하지 않는다. 파일 본문 추출과 분석이 없는 단계에서는 실제 파일 내용을 읽었다고 표시하지 않는다.

조회 실패는 빈 성공 결과나 예시 데이터로 대체하지 않는다. 실제 AI 결과의 저장 방식, 갱신 시점, 수정/활동 이동으로 근거가 바뀔 때 처리, 분석 중/완료 상태는 실제 공급자 연결 전에 별도로 설계한다. 아직 정해지지 않은 실행 경로를 이 문서에서 구현된 API처럼 기록하지 않는다.

## 다음 작업 순서

1. **완료 — 개발 서버 목 조회 API:** GET `/api/journey`와 공급자 응답 검증을 추가했다. AI 분석·DB 변경 없이 HTTP 경계를 구성했다.
2. **완료 — 프론트 API 연결:** `getGrowthJourney(signal)`을 기존 request 헬퍼를 사용하는 API 호출로 바꾸고 응답 형식·취소·오류를 검사한다. `source: mock` 응답값과 필터·펼침을 유지하고 오류 재시도를 추가했다. 화면의 예시 데이터 배지는 후속 사용자 요청으로 제거했다. 브라우저 조작은 아직 미검증이다.
3. **실제 DB 문맥 연결:** 확정 기록·활동·자료 ID를 분석 공급자에 전달할 문맥을 구성한다. 기존 DB를 보존하고 테스트는 임시 DB를 사용한다. 목 분석값을 실제 저장 자료에 근거한 결과로 위장하지 않는다.
4. **실제 AI 계약·분석 연결:** 최종 성장 분류와 분석 범위·저장/갱신 방식을 정리한다. 공급자 호출·응답 검증·근거 관계를 구현한다. 성장 요약·이벤트·배지는 검증된 결과로 교체한다.
5. **근거 자료 연결·검증:** 실제 근거 ID가 확인된 경우 기존 활동 상세/자료 Drawer와 연결한다. 기록 수정·이동 후 관계 처리와 브라우저 동작을 확인한다.

1~2번은 이번 요청에서 완료했다. 다음 제안 범위는 **3번, 확정 저장 기록의 분석 문맥 구성**이다. 실제 AI나 DB 분석까지 한 번에 진행하지 않는다.

화면 동작 검증은 사용자가 맡는다고 확인했다. 현재 화면·개발 목 API 이후의 작업은 실제 백엔드/AI 연결이며 결과 저장·갱신과 근거 자료 연결도 이에 포함한다. 이 담당 구분을 브라우저 검증 완료로 기록하지 않는다.

## 검증 기준

구현 시 서버/프론트 모두 응답 구조, 필수 문자열, 월 형식, 중복 이벤트 ID, 선택지 참조, 비교 유무를 검사한다. 목 응답의 source가 mock으로 유지되는지 확인한다. 정상·빈 결과·서버 실패·잘못된 응답·요청 취소를 검사하고 기존 AND 필터와 이벤트 ID별 펼침을 유지한다.

이번 API 연결 후 build/lint와 Journey 통합/필터/서버 검사 12개, 서버 전체 검사 15개가 통과했다(서버 Journey 3개 중복). 실제 사용자 DB에 테스트 기록을 넣지 않았다. 구현 범위와 검증 한계는 [현재 상태](현재_구현_상태.md), 전체 배경은 [작업 안내](README.md)를 따른다.

## 실행

프로젝트 루트에서 `npm.cmd --prefix api-server run dev`와 별도 터미널의 `npm.cmd run dev`를 실행한 뒤 `/journey`에 진입한다. 서버가 watch로 재시작되지 않았다면 재시작해 새 GET 경로를 반영한다. 기본 Vite 프록시는 `127.0.0.1:3001`이다. 실제 AI 키 설정은 이번 단계에 필요 없다.
